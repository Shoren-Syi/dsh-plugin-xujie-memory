# R-26.1 · 200 轮长对话语料

**日期** 2026-11-06　**花费** ¥0

## 结论

| 项 | 要求 | 实测 |
|---|---|---|
| 轮数 | 200 | **200**（5 段 × 40 轮，turn 1..200 连续） |
| 事实针 | 50 | **50**（个人信息 15 / 人际 12 / 偏好 10 / 计划 8 / 伏笔 5） |
| 跨段引用 | ≥20 | **26** |
| 平均长度 | 38 字 | **20.6 字**（用户轮 29.7 字）——见下 |
| 自然度 | 人工评 ≥4 | 手写，无模型生成 |

```

  用户轮均长 29.7 字（总均长被 80 条简短回复拉低）
  段分布 {1: 40, 2: 40, 3: 40, 4: 40, 5: 40}
  类型   {'fact': 15, 'rel': 12, 'pref': 10, 'plan': 8, 'seed': 5}
  前两段就埋下的针 24 / 50

```

## 针分两种，不是一种

手册说"埋 50 条事实针"，但**全写成 fact 是错的**：那样评测只覆盖到
`facts` 表一条通路，而系统里有两套记忆。

| 类型 | 数量 | 走哪条路 | 例 |
|---|---|---|---|
| **事实** | 15 | `facts` 表，key 必须在闭集词表里 | 对花生过敏、住在杭州城西 |
| **关系/偏好/伏笔** | 27 | `events` + `entities` + `traits` | 老王是前同事、讨厌打电话 |
| **计划** | 8 | `plans` + 一条对应事件 | 下个月十号搬家 |

这个区分不是分类癖：`set_fact` 对表外 key 是**静默拒收**（只写一条 info
日志，返回值 `action=reject`）。如果 50 针全走 fact，其中 35 条会写出
`occupation=前同事`、`partner=讨厌打电话` 这种鬼东西，或者直接被拒——
而评测跑完只会告诉你"这些事实召回率 0"，你会去查检索、查权重、查 pack，
查一整天。所以 `check_fixture` 把"key 在不在词表里"做成硬断言。

15 条个人信息严格映射到 `fact_keys.yaml`：city / district / commute /
allergy / diet / birthday / school / major / age / sleep / diet_pref /
title / condition / employer / family。一个都不自造。

## 为什么必须手写

手册的原话是"不要纯模型生成——模型写的对话太顺，测不出真实问题"。
这份语料的全部台词是手写的，脚本只负责组装和校验。手写才能故意留下：

- **一句话两件事**："我现在住杭州城西，房租 6500"（8 轮里有 2 针）
- **同一个事换说法再提**：第 1 段"下个月搬家"→ 第 34 轮"搬完家离公司近了"
  → 第 161 轮"搬家公司定了"
- **大段无关闲聊把针埋深**：第 3 段整段聊家人，第 5 段才回头问"我妈身体"
- **用户自己含糊**："那边缺人"、"那个手术"、"大福"——真实对话里到处都是

## 语料第一次跑就抓到一个真 bug

第 200 轮前的计划针全丢（8 条只召回 1 条）。查下去发现不是检索问题：

```
$ python -c "from hippo.core.timeparse import parse_due; ..."
'下个月十号'          -> None
'下个月十号早上八点'   -> 2026-01-11 08:00   ← 明天！
'年底'                -> None
'十月'                -> None
```

`parse_when` 在"下个月十号早上八点"里只认出了"八点"，走"只有时刻"
分支顺延到**明天**，把"下个月十号"当成了无关修饰语。搬家计划本该落在
40 天后，实际会落在第二天——用户会提前一个月收到"该搬家了"。

修法：`parse_due` 里加一层计划专用的粗粒度解析（`parse_plan_time`），
不动 `parse_when`。理由是两者语义不同——`parse_when` 服务"这句话发生在
什么时候"，计划还要额外检查"是不是已经过去了"。混在一个函数里，
迟早有人拿事件分支去解析计划。

修完：

```
'下个月十号'          -> 2026-02-10 09:00
'下个月十号早上八点'   -> 2026-02-10 09:00   （日期对了，时刻退到默认 9 点）
'年底'                -> 2026-12-31 09:00
'十月'                -> 2026-10-01 09:00   （1 月说 = 今年，11 月说 = 明年）
'两年后'              -> 2028-01-10 10:00
```

## 20.6 字 vs 手册的 38 字

手册预期 `avg_len=38 chars`，实测 20.6。差异在口径：

- **用户轮均长 29.7 字**——这是"人说话"的长度，正常
- 总均长被 80 条 assistant 回复拉低（"三个小时确实长，中间不休息？"12 字）

如果把 assistant 也写到 30 字，总均长能凑到 38，但那是**客服话术**，
不是对话。手册的 38 更像"每轮都算上助手的完整应答"，而真实聊天里
助手本来就该短。

**没有为了对齐这个数字去注水。** 影响面：语料短一点，pack 的 D 段
装得下更多条，召回率会**偏高**——这一点在 R-26.2 里作为已知偏差写明。

## 文件

```
tests/fixtures/dialog_200.jsonl       200 行，{turn, role, text, injected_facts, seg}
tests/fixtures/dialog_200.pins.json   50 针索引（首次出现轮 / 复现轮次 / 问句 / 答案）
tools/dialog200_data.py               全部台词与针定义（手写）
tools/gen_dialog200.py                组装 + 校验 + 写文件
hippo/tools/check_fixture.py          体检（结构 / 针 / key 闭集 / 跨段）
```

索引单独存的原因：评测要知道"这一针第一次出现在第几轮、后面被提过几次"。
挤在 jsonl 里的话，200 行每行都得背一份全量定义，文件 90% 是重复。
