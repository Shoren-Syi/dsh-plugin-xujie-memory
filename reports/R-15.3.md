## 一、手册这一段自相矛盾，得先定口径

原文两条要求，互相排斥：

> 2. 动作：`ATTACH` 一个 `mem-archive-YYYY.db`，把行 `INSERT ... SELECT` 过去，主库删除
> ……改为在归档函数里标记 `archived=1`，主库保留瘦身版：只留 id/keywords/summary，
>    raw 移到归档库

后半句在现有 schema 上**做不到**：

```sql
raw TEXT NOT NULL,
CHECK (length(raw) > 0),
CREATE TRIGGER trg_events_raw_immutable BEFORE UPDATE ON events ...  -- 拦一切 UPDATE raw
```

把 raw 清空会被数据库自己拒绝，而"raw 移到归档库"的本质就是"主库这份 raw 没了"。

所以取**前半句：物理搬走**。它同时满足三条 DoD：

| DoD | 物理搬走 | 标记 archived=1 + 瘦身 |
|---|---|---|
| 体积降 ≥20% | raw 真的不在主库了 ✓ | raw 还在，一个字节都不少 ✗ |
| 可还原 | 归档库有完整行（含原 id）✓ | 要靠 UPDATE 塞回 raw，被触发器拦住 ✗ |
| 仍可检索 | `recall --deep` / `restore` ✓ | ✓ |

代价是「归档事件不再参与正常召回」。这是**口径变更，在此写明**：跨库自动召回
意味着每轮对话都要 ATTACH 一个数量可变的库文件，让 99% 的查询为 1% 的可能性付磁盘 IO。
归档的语义本来就是"这东西我不用了"；真要找的时候显式问。

`test_archived_not_found_by_recall`（默认召回看不见）和
`test_archived_still_findable_in_archive`（显式问看得见）两条一起钉住这个口径。

## 二、触发条件：三个条件缺一不可

```python
SELECT id FROM events WHERE tier = 3 AND weight < ? AND kind = 'event'
  AND archived = 0 AND coalesce(last_access, ingest_time) < ?
```

- `tier = 3`（cold）：还在 warm 里的东西随时可能被问起。
- `weight < 0.05`：衰减到几乎没有召回价值（M14 的半衰期公式算出来的）。
- `coalesce(last_access, ingest_time) < cutoff`：**这一条我差点写错。**

`last_access` 为 NULL 时如果直接 `last_access < cutoff`，NULL 比较恒为假，
**从没被想起来过的事件永远不归档**——而"从没被想起来"恰恰是最该归档的那一类。
反过来如果 `last_access IS NULL` 就一律归档，刚写进来的冷事件会在同一天被搬走。

正确语义是"从写入那天开始算它多久没被碰"：`coalesce(last_access, ingest_time)`。
`test_null_last_access_uses_ingest_time` 钉住这条。

`kind = 'event'` 排除 fact/plan：那是结构化记忆（`key=value`），删了没法从原文重建。
`test_facts_and_plans_never_archived` 把 `fact / plan / regret` 三种 kind 都试一遍。

## 三、搬家的顺序：先写后删，写完验数

```
ATTACH → CREATE TABLE IF NOT EXISTS → INSERT OR IGNORE
       → SELECT 回来核对 count（少一条就抛）
       → INSERT archive_meta
       → 置 maint_flags.allow_event_delete='1'
       → DELETE FROM events
       → 清 flag
       → DETACH → VACUUM
```

### 为什么必须验数

```python
missing = sorted(set(ids) - set(got))
if missing:
    raise StoreError(f"归档校验失败，缺 {len(missing)} 条：{missing[:5]}")
```

不验数就删，等于在"写失败"时删掉唯一一份。这是整个 M15 唯一可能造成
**永久数据丢失**的路径，值得多一次 COUNT 查询。

唯一的风险窗口是"INSERT 成功但 DETACH 前崩溃"：归档库多一份副本，主库还完整。
下次归档靠 `INSERT OR IGNORE` 跳过，不会重复。

### 关于不可变触发器

M6 写的 `trg_events_no_delete` 早就留了正门：

```sql
WHEN coalesce((SELECT value FROM maint_flags WHERE key='allow_event_delete'), '0') <> '1'
```

所以归档不是"绕过"append-only，是走设计时就预留的维护通道。flag 的置位和清除
**必须在同一个事务里**——中途崩溃留下 `'1'`，那就真的没有删不掉的防线了。

`test_archive_failure_keeps_main_intact` 制造写失败（拿一个**目录**当归档库路径），
断言主库一行不少。这里踩了个坑：第一版用 `chmod 500` 制造失败，但测试以 root 跑，
**root 无视权限位**，测试是空转的——它一直"通过"，因为什么也没发生。

## 四、体积：`db_bytes` 的两个口径，和 `getsize` 的坑

```python
live=True   → (page_count - freelist_count) × page_size    # 活数据
live=False  → page_count × page_size                        # 文件大小
```

### 坑一：`os.path.getsize` 在 VACUUM 之后读旧值

第一版：

```python
before = os.path.getsize(path); vacuum(); after = os.path.getsize(path)
```

实测 `before=432KB, after=432KB`，而 `du` 显示 220KB。原因是 VACUUM 之后紧接着
`stat` 拿到的是**旧的 st_size**（同进程内的元数据缓存）。

症状极其恶劣：**"归档后变小了多少"这个数永远是 0**，看起来像归档没生效，
而实际上数据已经搬走了。改用 `page_count × page_size`（SQLite 文件除 100 字节头
之外全是页，这就是文件大小的定义）。

### 坑二：`page_count` 不含 freelist 的变化

删行不缩文件，被删的页进 freelist 等复用。所以：

```
删掉一半数据 → live 降 50%，page_count 一页不少
```

**只报文件大小会得出"归档没生效"的结论；只报活数据会得出"VACUUM 没用"的结论。**
两个数都要能拿到，回答的是两个不同问题。`hippo stats --disk` 现在一次报三个：

```
库文件 /tmp/demo/mem.db  228 KB
  页 57 × 4096B   活数据 228 KB   空闲页 0（0 KB 可回收）
  归档库 1 个文件  92 KB   主库 228 KB
    mem-2026.db                   92 KB
```

### 一个必须说的实话：这条 DoD 在小库上测的是基线

空库（0 条事件，只有 schema / 索引 / 触发器）就有 **225,280 B ≈ 220KB**、55 页。
所以：

```
可降比例的上限 = 1 - 220KB / 总体积
```

- 120 条 / 308KB 的库：**上限 28.6%**，实测降到 228KB（-26%），已经贴着上限。
- 200 条 / 332KB 的库：上限 33.7%，实测 -27.7%。
- 真机库塞 300 条**短文本**事件 / 344KB：只降到 290KB（**-15.5%**）——
  每条 raw 才 20 来个字，占比太小，够不到 20%。

也就是说"体积降 ≥20%"这条线，在小于约 1MB 的库上**基本在考 schema 开销**，
而不是考归档效果。手册预期结果里那个 `mem.db 142MB -> 108MB`（-24%）才是这条线
设计的规模。这一点写在这里，免得以后有人在测试库上看到 15% 就以为坏了——
应该看的是"活数据降了多少"。

## 五、还原：三个必须一起做对的事

```python
restore_from(ids, archive_dir) → list[int]
```

1. **跨所有 `mem-*.db` 找**。一条事件属于哪一批是历史决定的，用户不该知道。
   `INSERT OR IGNORE`：主库已有同 id 时跳过——那只可能是"上次恢复过一半"，
   重试不该报错。
2. **保留原 id**。换 id 会让所有引用（`event_entities`、`superseded_by`、
   `consolidation_log.member_ids`）断掉。
3. **重建倒排**。归档库没有 `kw_index`（`CREATE TABLE ... AS SELECT` 会丢索引）；
   主库的倒排里也早就没有它了。不补这一步，事件"活了但搜不到"——
   **症状和"没恢复"完全一样**，排查极费时间。

最后一点顺带解决了：还原之后归档库里那份要删掉，否则同一条事件存在两个地方，
下次 `search_archive` 会返回一条其实已经在主库里的记录。

`test_restore_rebuilds_inverted_index`、`test_restore_brings_back_verbatim`、
`test_restore_is_idempotent`、`test_restore_from_any_batch` 各钉一条。

## 六、归档事件仍可检索：`recall --deep`

手册验收 #2。做成**显式询问**而不是自动召回：

```python
store.search_archive("甲状腺", limit=5)
→ [{archived_id, event_time, raw, summary, keywords, file}, ...]
```

用 `LIKE` 而不是倒排，理由是归档库本来就该是"死档案"：

- 它没有索引（见上），几万行以内全表扫一遍是毫秒级，为此维护一套倒排不划算。
- 归档库的价值在于"还能找回来"，不在于"每次参与排序"。

多词是**任一命中**，不是"全都要"：用户在命令行打的是自然语言
（`hippo recall 我搬家的事 --deep`），归档里写的是"从朝阳搬到海淀"——
要求全词命中等于永远查不到。`test_deep_search_matches_any_token` 钉住。

```
$ hippo recall 旧事 --dir /tmp/h2 --deep
--- 归档库 --- 命中 5 条（不参与正常召回，要拉回来用 `hippo restore --id`）
  [344] 2024-11-05 两年前的一条旧事第299号，内容无关紧要
  ...
```

## 七、一个命名陷阱（留给自己下次看）

`archive_to` 的返回值里：

```python
{"moved": 120, "bytes_before": ..., "bytes_after": ...,
 "file": "/…/mem-2026.db",     # ← 归档库路径
 "file_size": 233472}          # ← 主库的文件大小，不是上面那个文件的大小
```

`file` 和 `file_size` 挨着，但指的不是同一个文件。没有改名是因为 `cli.py` 和
测试里都已经按"主库文件大小"在用（`drop = 1 - file_size / before`），
改名的收益不抵风险。写在这里，比默默留着好。
