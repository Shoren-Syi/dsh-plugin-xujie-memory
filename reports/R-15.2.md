## 二、手册四条，逐条对上

### 1. 选主记录：weight 最高，平手取 event_time 最早

```python
members.sort(key=lambda r: (-r.weight, r.event_time, r.id))
```

`id` 是第三键，不是装饰：weight 和 event_time 都相等时（同一轮抽出来的两条），
没有第三键排序就不稳定，同一份数据两次跑可能选出不同主记录——而"聚类确定"
是 M15.1 的验收项，主记录不确定等于整个结果不确定。

平手取"最早"的理由是手册那句"第一次提到通常信息最全"：后来的复述是压缩过的。

### 2. 非主记录 `superseded_by`，不删除

这是整个 M15 的地基。原文一条都不删，所以"合并错了"永远可逆。

`UPDATE ... WHERE superseded_by IS NULL` 带了条件：已经指向别人的事件不会被改指。
重复跑巩固时这条条件保证幂等（第二轮 `rowcount = 0`）。

### 3. 主记录 `raw` 逐字不动

`merge_into` 的 UPDATE 语句里**没有 `raw` 这一列**，物理上就不可能改到它。
不是靠"记得别改"，是靠语句里没有。

`test_master_raw_is_byte_identical` 比对的是 `repr()` 而不是 `==`，
连首尾空白和全角空格都钉住。

### 4. 摘要重生成：喂全部 raw，禁止拿摘要再摘要

```python
def build_summary_prompt(cluster):
    """把簇内**所有原文**一起喂给模型。"""
```

prompt 里明确写了"只根据下面这些原话，不要推测，不要补充没提到的信息"。
禁止摘要再摘要的理由在手册 §M6 已经写过（逐层失真），这里补一个实测证据：

真机库 1 号簇的**旧摘要**是"用户答应帮老王喂猫，但自己其实怕猫，小时候被猫挠过一次"。
如果拿这份旧摘要去和新成员的摘要合并，会永远丢掉这两条细节：

```
"近多了，走路二十分钟"       ← 只在 2 号原文里
"老王常飞，对此无所谓"       ← 只在 39 号原文里
```

而重生成的摘要把两条都写进去了（见第四节）。**旧摘要已经是压缩后的残影，
在残影上再压缩，丢的东西再也找不回来。**

## 三、两条自加的规则

手册没写，但不做会出真问题。

### 1. `recall_count` 取 `max`，不取 `sum`

手册原文是"`recall_count` = 簇内总和"。**这条是错的**，R-14-Gate 里就留了交代。

`recall_count` 的作用是延长半衰期（M14.1：`hl_eff = hl × (1 + 0.25 × min(rc, 5))`）。
如果取和：一条"我不吃辣"被反复说了 8 次、合并成一条，`rc = 8`，
半衰期直接顶到 ×2.25 的上限——**而它只是一句忌口**。反过来，真正重要的事
往往只说一次（"我妈确诊了"），拿不到任何加成。

求和等于把"啰嗦"当"重要"。取 max 是"这一簇最多被想起过几次"，
语义更接近"这条记忆的活跃度"。

### 2. 关键词必须取并集（上限 12）

合并把成员从检索结果里摘掉了。它们的说法如果不同步到主记录，**那些词就再也搜不到**——
原文还在库里，但检索层看不见。这是合并最隐蔽的损失，比摘要失真更难发现，
因为数据没丢、只是查不到了。

```python
def merged_keywords(self):
    ...
    return " ".join(seen[:12])   # 上限 12：再多倒排就退化成"全命中"
```

上限 12 是个真实取舍：一条记忆挂 40 个关键词，它会在几乎任何查询里都命中，
倒排索引就失去筛选作用了。

扣分点都记一下，因为它们是"下次能改"的具体项：

- #1 把三件不相关的事写进了一句（喂猫 / 走路近 / 老王常飞）。摘要本身没有失真，

## 五、摘要失败不能连坐合并

```python
try:
    new_summary = ...
except Exception:
    rep.summary_fail += 1        # 只记数，不抛
```

`merge_into` 的三个字段（`keywords` / `summary` / `recall_count`）都是可选的，
就是为了这个：结构变更（supersede）必须成，内容变更（摘要）失败了就保留旧摘要。

反过来也不对：摘要失败就把 supersede 回滚，等于这一轮白跑——而下一轮还会撞上
同样的模型故障，巩固永远做不成。

`test_summary_failure_does_not_block_merge` 用一个必然抛异常的 summarizer 钉住：
合并照样完成，`summary_fail == 1`，主记录摘要保持原样。

## 六、修掉的一个真 bug：`frozen` 只检查了第一层

`CORRECTION` 正则（`不对|说错|其实是|更正|记错|不是这样|搞错|改主意|反悔|算了`）
命中的事件要"冻结"，不参与合并——它的价值就在"改过"这个动作本身。

第一版只在强判据循环里检查：

```python
for a, b in pairs:                      # 强判据
    if a.id in frozen or b.id in frozen: continue
    ...
for row in singles:                     # 弱判据  ← 这里忘了
    for cluster in clusters:
        ...                             # 直接把 frozen 事件挂上去了
```

实测后果：

```
33 我今年二十八
35 哦不对，我二十九了          ← 含"不对"，应该被冻结
```

35 被弱判据捡回去挂到 33 的簇上，摘要变成"用户今年二十八岁"——**把更正抹平了，
而且抹成了错的那个值**。这是本次唯一的"数据被弄错"级别的 bug。

修完误合并从 2 处降到 1 处。`test_correction_is_never_merged` 用弱判据能过的样本
（覆盖率 0.5、2 词共享 1 个）专门钉这条路径。

顺带说明"算了"为什么收进正则：它在改变主意的语境里几乎总意味着"推翻前面说的"
（"我现在就想辞职…算了，先忍着吧"）。加它的风险是把"算了，就这样"这类无争议的话
也冻结——而冻结的代价是**漏合**，不是错合，可以宽容。

## 七、撤销：`unmerge`

```sql
UPDATE events SET superseded_by = NULL WHERE superseded_by = ?;
```

然后**按 `events.keywords` 重建倒排**。

为什么必须重建：`merge_into` 把成员的 `kw_index` 条目删了（它们的词已经进了主记录
的并集，留着只会让每轮检索多捞一批注定被过滤掉的 id）。撤销时不重建，
事件活了但搜不到——**症状和"没恢复"一模一样，排查起来极费时间**。

这些都能撤销，是因为原文一条没删、关键词存在 `events` 表里而不是只在倒排里。
`test_unmerge_twice_is_noop` 钉住二次调用不报错（用户会手抖连按两次）。

## 八、`consolidation_log`：为什么值得单独一张表

```sql
CREATE TABLE consolidation_log (
    id INTEGER PRIMARY KEY, ts INTEGER NOT NULL, session TEXT NOT NULL,
    master_id INTEGER NOT NULL REFERENCES events(id),
    member_ids TEXT NOT NULL, n_merged INTEGER NOT NULL,
    strong INTEGER NOT NULL, score REAL NOT NULL,
    summary_old TEXT NOT NULL DEFAULT '', summary_new TEXT NOT NULL DEFAULT '',
    tokens INTEGER NOT NULL DEFAULT 0, cost REAL NOT NULL DEFAULT 0,
    undone_at INTEGER, ...);
```

手册说"存在 metrics 表即可"。单独建表而不是塞进 metrics，理由是三条查询都是
按会话、按时间范围扫的，而 metrics 是 KV 形状（key-value-ts），塞进去要
序列化整个清单才能查"上周合并了哪些"。

`summary_old` / `summary_new` 同时存，是为了回答那个一定会被问的问题：
"这条记忆的摘要是谁改的、原来写的什么"。只存新的，撤销就只能靠猜。

`undone_at` 而不是删除行：撤销本身也是历史。
