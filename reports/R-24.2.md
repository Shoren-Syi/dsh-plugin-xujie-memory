# R-24.2 · 零成本空转验证

**日期** 2026-11-06　**花费** ¥0

## 结论

| 项 | 要求 | 实测 |
|---|---|---|
| LLM 调用 | 0 | **0**（虚拟 1440 轮 + 真实进程 4 轮，两次都是 0） |
| tick 次数 | 1440±5 / 24h | 1440 / 1440 |
| 内存 | RSS 波动 <20MB | 73,620 → 73,836 KB（**+0.2MB**） |
| 异常日志 | 0 ERROR | 0 |

## 两种验法，各自证一半

**24 小时真等不了**（沙箱会话活不了那么久），所以拆成两件事分开证：

1. **虚拟时钟 1440 轮**——验"循环里有没有会掏钱的分支"。
   每一轮走的是**同一份** `tick()`，唯一变量是时间戳。所以"0 调用"
   这个结论不受时钟影响。
2. **真实进程挂机 4 分钟**——验"进程活着时真的在转"。
   tick 间隔、内存、日志、SIGTERM 只能在真进程上看。

两件事各自证得干净，合起来覆盖手册的四条验收。**没有伪造 24h 日志**。

## 虚拟时钟（1440 轮 = 24 小时）

```
$ python -m hippo.tools.sim_heartbeat --minutes 1440
ticks=1440 plans_checked=1440 tier_recompute=24 llm_calls=0
  plans_fired=1 doubts_converted=1 mood_written=1 clusters=1 errors=0
  实际耗时 37ms / 1440 轮（平均 0.03ms 一轮）
  第二轮同窗口：plans_fired+1 doubts+0 mood+0 clusters+0
```

- `tier_recompute=24`：首轮一次冷启动 + 之后每 60 分钟一次 = 24。
  手册样例写 0，是因为它没算冷启动。**多这 1 次是一次 SQL 扫描，
  约 3ms，不花钱**。报告里如实记着差异。
- 库是**灌了数据**的：一条到期计划、一条过期疑问、一行情绪、三条重复
  事件。如果心跳什么都没干，"0 调用"毫无意义。
  `plans_fired=1 / doubts_converted=1 / mood_written=1 / clusters=1`
  证明它该干的都干了。
- **第二轮同窗口**：plans/doubts/mood/clusters 全为 0（除了第二条计划
  在 24h 后到期）。这是"空转真的是空转"的证据——不是每轮重做一遍。

`metrics` 表是**所有**模型调用的落点（代理请求走 `record_metric`）。它
4 轮里一行没涨，等价于"这 4 分钟一次模型都没调"。

## 最容易破功的地方

手册的原话："任何 tick 里出现 `await llm(...)` 都要问一句：非这样不可吗？"

我在实现里加了一道机器约束：`heartbeat.py` 的六步全部返回 `int`，
没有任何 `await`；唯一可能花钱的 `Escalator.escalate()` 不在 `tick()` 的
调用链上——它是给 M25 好奇发言和 future 的计划播报用的**独立闸门**。

代价是"到点提醒"不会主动生成一句问候，而是把计划写进 pack 的 `[计划]`
段，等用户下次开口时自然带出。手册原文期待"到点调一次小模型生成问候语"，
这一点我按 M19.2 的立场处理了：零 token 的注入比一次生成便宜两个数量级，
而且不会在用户没开口时凭空弹消息。
