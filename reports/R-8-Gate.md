## 二、这一轮的核心不是"能写进去"，是"该拒的拒掉"

手册的 M8 写的是"把居住城市、职业这类结构化事实单独存"。照字面做，
`set_fact` 早就在了（M1.3），只需要加个 key 词表。

先测分布，8 个窗口看到的是：

```
11 条 fact，11 个不同的 key
饮食忌口 = 吃不了辣（微辣可以，中辣不行）、不喝冰的（胃不好）、讨厌香菜
通勤     = 新家离公司走路二十分钟
```

两个问题都不是"少写了什么"，是"多写了什么"：

1. **key 发散**：`居住城市` 和 `居住地` 是同一件事的两个名字。
   系统把它们当两件事，用户搬到上海只顶掉一个，另一个永远 active。
   同一件事有两个当前值，比没有事实更糟——模型会二选一地瞎猜。
2. **值是句子**：句子无法参与比较。下次说"我改坐地铁了"，
   "走路二十分钟"和"地铁"判不出矛盾，只能并存。

所以 M8.1 的一半工作量在**约束**上：30 个 key 的闭集 + 六类值归一 +
数据库级的"single 槽只有一个 active"。真机上 key 越界从 11/11 降到 0/28，
平均值长从 20+ 字降到 3.5 字。

## 三、地图一：值归一是矛盾检测的前提，手册没写

"矛盾检出率 ≥95%"如果没有值归一，会靠**假矛盾**刷上去：

```
上海 / 上海市 / 沪      → 每次都"你搬家了？"
字节 / 字节跳动          → "你换工作了？"
三岁 / 3岁              → "你猫多大了？"
```

按 type 分开处理（place 剥行政后缀、org 剥机构后缀、number 转数字、
text 一个字都不动），再加 facets 处理"北京（海淀）"这种复合值。

`more_specific` 用前缀包含，但加了通名守卫：

```
字节 ⊂ 字节跳动       → 细化，对
北京 ⊂ 北京银行       → 另一家机构，错（remainder 含"银行"）
```

这条守卫是写的时候想到的，不是测出来的。没有它，用户从北京银行跳槽，
系统会判成"还是那家，只是说得更细"，"你什么时候换的工作"永远答错。

## 四、地图二：误报比漏报贵，所以语料必须两头都有

35 条用例：15 条真矛盾 + 20 条"看着像但不是"。对照组把判定换回 M8 之前的
字符串相等实现：

| 实现 | 检出 | 误报 |
|---|---|---|
| 朴素（字符串相等） | 18/18 | **11/15** |
| 当前 | 18/18 | **0/15** |

检出率一模一样。**只看检出率的话，这两个实现的评分相同**——
这就是为什么这一节的验收必须是两个数一起报。

误报的代价不对称：漏一条只是记忆里留旧值（下次还会被纠正），
误报一条会把"我搬到了海淀"记成"你搬家了"，并把旧值 `valid_to` 写死，
之后查"我以前住哪"给出一个从未结束的区间。

## 五、真机抓出的两个东西

### 1. 同一窗口内的改口，模型自己归纳掉了

`probe_contradiction` 第一次跑（10 轮，改口在第 5 轮）：

```
模型输出：city=上海，employer=腾讯        ← 全是最终状态
```

模型看到"上个月搬到上海了"，直接输出 `city=上海`，**不写北京那条**。
所以矛盾检测根本没机会触发。这不是 bug，是模型行为：
**同一窗口内的改口不留痕，矛盾只在跨窗口累积时出现。**

把改口挪到第 8 轮（隔一个窗口）重跑，替换正常发生：

```
#1  city  北京  [11-05 → 10-01)
#8  city  上海  [10-01 → -)
```

这一条必须写进报告，否则下一轮会有人问"为什么真机 0 条矛盾"。

### 2. 负区间：结束早于开始

同一次跑出来 `北京 [11-05, 10-01)`。成因是新值带了"上个月"（回溯），
旧值按写入时间估。替换时 `valid_to = 新值开始`，区间倒挂。

真相是"知道它什么时候结束，不知道什么时候开始"，所以把这种旧值的
`valid_from` 置 0（早于所有记录）。加了一条全域不变量测试：
任何历史事实都不许 `valid_to < valid_from`。

**这个 bug 只有真机才会暴露**——单测里我给两个值都传了显式 `when`。

## 六、地图三：时间从"点"变成"区间"

M5 的 `parse_when` 只够算 `plans.due_at`。"去年冬天"压不成点，
硬压就是 12 月 1 日 9 点整——一个从未存在过的时刻。

`parse_span` 返回 `[start, end)`，`events.event_time_end` 接上了
（这列 001 里就有，手册记成"落在 002"，M5 一直没写）。

44 条用例全过之后，我拿 16 个**没为它们写过代码**的表述扫了一遍，
错了 4 个（25%）：

| 表述 | 原来 | 问题 |
|---|---|---|
| 两天前 / 半个月前 / 两年前 | None | M5 只做了"X 后"（给计划用的），事件全在过去 |
| 春节 | 3~5 月 | `春` 无边界，命中"春节" |
| 半个月前 | 当月 | `round(0.5)=0`，方向反了 |
| 下下个月 | 下个月 | 前缀表没有它 |

顺带修了两个："上周三"匹配不到"上"前缀，落到下周（差 13 天）；
"大前天"被当成"前天"（词表两个方向不对称）。

**这六个才是 M8.3 的真实产出**，100% 不是。

## 九、下一步

M9 是检索 L1 分类层，**P1 写入阶段到此结束**。留给 M9 的三件事：

1. **事实注入的 token 预算**：真机 28 条 fact / 14 会话 = 2 条/会话，
   但一个长期会话会有 10+ 条。M9 要按 `card=single` 优先、`multi` 截断。
2. **`valid_to IS NULL` 是唯一该进候选集的条件**，`fact_as_of` 只给
   "以前"类问题用。这条要在检索层写死，不然历史事实会混进当前状态。
3. **doubt 会干扰检索**：低置信度冲突留下的疑问，如果被当成"事实"注入，
   模型会拿一个"不确定"当既定前提。M9 要显式排除。
