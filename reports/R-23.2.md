# R-23.2 · 反馈识别与结算

**日期** 2026-11-06　**花费** ¥0

## 做了什么

1. **抽取侧**：`ExtractResult` 加 `neg_feedback` / `pos_feedback`（≤120 字，
   空串 = 没表态）。提示词加规则 13：只收"用户对 AI 上一轮做过的事"的评价，
   抱怨自己的生活不算。
2. **结算**：`ledger.settle(feedback, actual)` →
   先作废过期 → 取 3 天内待结算 → 按相关度选 1 条 → `rpe = actual - predicted`。
3. **persist 接线**：一轮的所有写入完成后，在同一事务里结算。
   负反馈优先（"这个不错，但你不该动我配置"——夸的那半句多半是客套）。
4. **失败隔离**：结算抛异常只记日志，不回滚记忆入库。结账是支线，
   不能因为它出错把主线赔进去。
5. **`hippo stats --ledger`**：待结算/已结算/平均 RPE/懊悔数。

## 关键决定

- **选"相关度"不选"最近"**。实测：用户说"谁让你改我配置的"，若库里有
  "改配置"（早 1 小时）和"发消息"（晚 1 分钟）两条，按时间取会结算错。
  相关度用 M18.3 的实义块覆盖率，取双向最大值（单向会被长度差吃掉）：
  `改配置` 0.33 / `发消息` 0.00，区分得开。
- **相关度全为 0 才退化成"取最近"**。`max(key=(rel, ts))` 天然实现，
  不需要单独分支。
- **过期先于选候选**。反过来的话，三天前的动作还在候选里，今天一句
  无关抱怨就会把它结算成 -1——凭空造一条教训。
- **`settle_ledger` 拒绝二次结算**（抛 `StoreError`）。用户连骂两句是常态，
  第二句若也结算，RPE 算两遍、懊悔记两遍。
- **负反馈优先但不双结算**：一轮只结一条。两条都结等于批量误伤——
  另一条根本没被提到。

## 实跑

```
$ python -m hippo.tools.sim_ledger
 1. OK   改配置被骂        rpe=-1.85 regret=1
 2. OK   发消息被谢        rpe=+0.70
 3. OK   按相关度选旧的      结算=旧的
 4. OK   过期不猜         settled=-1
 5. OK   提议被否         kind=propose
 6. OK   翻目录被批评       kind=explore
 7. OK   没落差就不懊悔      rpe=-0.10
 8. OK   不重复结算        regrets=1
 9. OK   负反馈优先        actual=-1
10. OK   无关联也只结 1 条   settled=1

结算正确率 10/10 = 100%
```

## 验收对照

| # | 要求 | 结果 |
|---|---|---|
| 1 | 10 组结算全对 | 模拟器真建库真调 API，10/10；单测另 11 例 |
| 2 | 过期不猜 | 4 天前动作 + 今天抱怨 → `settled=-1`、`actual/rpe` 保持 NULL |
| 3 | 只结算 1 条 | 两条待结算，结算后另一条仍为 0 |
| 4 | RPE 符号正确 | 被骂恒为负；`predicted=0.9` 被骂 = -1.9，`-0.9` 被骂 = -0.1 |
