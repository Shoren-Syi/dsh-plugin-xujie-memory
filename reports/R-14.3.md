# R-14.3 召回加固

> 里程碑：M14.3
> 日期：2026-11-05
> 产出：`pack()` 接入 `touch_events`、`Store.touch_events`（M1 已有，本轮接入）、
> `tests/test_m14_3_recall.py`（14 例）
> 结论：**达标**。8 条事件批量更新 **0.02ms**（要求 <5ms），不需要异步。

## 一、手册那句话，拆开是两件容易做错的事

> 只对真正注入上下文的事件计数。

**错法一：拿 `items` 全量当"注入"。** `items` 是"检索到了"，不是"发出去了"。
真机库跑 `我搬家了你记得吗`：L2 返回 8 条，D 段预算裁掉 3 条，实际只渲染 5 条。
按 `items` 全量加固，那 3 条从没出现在 prompt 里的记忆也会 `recall_count += 1`。

为什么这件事严重：`recall_count` 会延长半衰期（M14.1）。
"被考虑过"比"被想起来"更容易被长期记住，方向反了。

修法：数 D 段里还剩几个 `[记忆 · ` 头。裁剪是"从后往前砍行"，活下来的
一定是前缀，所以 `items[:n]` 就是真正发出去的那几条。

**错法二：复用路径拿 `new_ids` 当注入。** 复用的是**上一轮的字节**，
这一轮真正进 prompt 的是 `last_pack_ids`。记 `new_ids` 会去加固那些
"这一轮检索到了但一个字都没发出去"的事件。

## 二、连带发现：`last_pack_ids` 存错了

修 M14.3 时发现的真 bug，在 M13 就埋下了：

```python
# M13 的写法
store.set_state(session, "last_pack_ids", " ".join(str(it.id) for it in items))
                                                              ^^^^^ items 全量
```

`last_pack_d` 存的是**裁剪后**的 D 段字节，`last_pack_ids` 存的是**裁剪前**的
`items`。两个状态不同步。

后果不只是加固错对象，D80 的重合判定也受影响：拿"检索到 8 条"和
"下一轮检索到 8 条"比，实际装上的是 5 条和 8 条——重合率算高了，
本该重新装配的轮次被判成"可以复用"。

改成存 `inj_ids`（真正渲染的）。同一个 id 列表既做 D80 的重合判定，
又做 M14.3 的加固对象——两件事的定义都是"上一轮真的装了什么"，
用同一份数据才对。

`test_last_pack_ids_records_rendered_only` 钉死：状态里的 id 全部
`recall_count == 1`，不在状态里的全部 `== 0`。

## 三、复用到底该不该计数：一个我自己推翻过的判断

第一版我写的是"**复用不计数**"——理由是复用的语义是"沿用"，不是"重新想起"，
而且每轮刷新 `last_access` 会让权重永不衰减，退化成滑动窗口。

写完测试才想清楚不对：

1. 复用发生的前提是**检索触发了、且结果重合 ≥60%**。说明用户确实还在
   这个话题上，这些记忆确实还在起作用
2. 内容确实在 prompt 里被模型读到了。手册说的是"注入上下文"，不是"重新检索"
3. 如果复用不计数，M13 实测 57% 的轮次完全不给加固，
   `recall_count` 只反映 43% 的轮次，这个数就没法解释了
4. "话题持续一个月 → 权重不衰减"不是 bug。这一个月里它**确实是重点**

所以改成计数（加固对象是复用的那批 id）。这个判断改了两次，
记在这里是因为：**"复用省了钱，所以记忆不该得到加固"——把缓存优化
和记忆动力学耦合在一起，是错的直觉。**

## 四、不做异步

手册要求"异步更新，不阻塞响应"。实测：

```
touch 8 条   0.02ms   （要求 <5ms）
```

0.02ms。异步要多一个线程、一次队列、一个"写库晚于响应"的竞态，
换来 0.02ms。**收益为负**。

而且加固失败已经包在 try 里（`pack.touch_failed` 只记日志），
不影响这一轮回复——真正需要的"不阻塞"已经由这一点保证。

`test_touch_8_events_under_5ms` 里先预热一次再计时：第一次会建语句缓存，
不预热会量到 0.4ms 然后误以为要优化。

## 五、加固只动两个字段

`touch_events` 只改 `recall_count` 和 `last_access`，**不直接改 `weight`**。

weight 只由 `recompute` 写。两个地方都能写的话，出问题时无法判断
是谁写的——而这类问题（"权重莫名涨了"）本来就极难复现。

`test_touch_does_not_change_weight_directly` 守这条。
加固的效果通过**下一次重算**体现：`last_access` 归零 → decay 回 1，
`recall_count +1` → 半衰期变长。两个都作用在公式的输入上。

## 七、留给 M15 的话

1. **`recall_count` 现在会被"复用"持续推高**。M15 合并事件时，
   合并后的 `recall_count` 用 `max` 而不是 `sum`——求和会让一条被
   合并了 50 次旧事的记忆直接顶到 cap，半衰期 ×2.25 白送
2. `last_access` 每轮刷新意味着**活跃话题的记忆不会变冷**。M15.3 归档
   如果按 `last_access` 判"多久没动"，活跃话题永远不会被归档——
   这可能正是想要的，但要确认
3. 加固是**每轮写一次库**。如果以后要支持多进程并发写，这里会先撞上
   `SQLITE_BUSY`。目前单进程够用
