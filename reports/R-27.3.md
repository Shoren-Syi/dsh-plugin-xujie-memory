## 一、三条降级规则，有一条要改（D81）

手册：停止抽取 / 检索只取 top-1 / pack 只用 A + C 块。

**后两条在实现上互相取消**：pack 只装 A（人设）和 C（钉住），D 段不存在，
top-1 检索出来也没有落点。要么保留 D 装 1 条，要么承认"不检索"更省。

选后者，理由是能算的：D 段 600 token 是每轮最大的一笔，整块砍掉省 55%；
砍到 1 条（80 token）只省 47%，还要付检索的 SQL 时间。**降级是为了活着到明天，
不是"记得少一点"。**

但 A + C 不完整——**时间锚必须留**。没有它，AI 不知道今天是几号，
"明天提醒你"会直接说错。那不是变笨，是说错。锚只有 20 token。

```
DEGRADED_BLOCKS = ("persona", "pinned", "anchor")
```

这条差异写在这里，不藏在代码里。

## 二、链路：三个点，各管一段

```
请求进来
  └─ budget.check()          读 metrics + extract_runs，两次聚合（走索引）
       ├─ 正常 → pack(degrade=False)
       └─ 超限 → pack(degrade=True)    只装 A/C/锚，不检索、不读卡片
  └─ app.state.degraded = 结果
       └─ _schedule_extract()  降级中直接 return（抽取是后台的第二笔钱）
```

- **每轮都查**，不缓存：预算是钱，钱的账必须落盘。两条聚合查询在
  8000 条事件 / 50 条 metrics 上是亚毫秒；`extract_runs` 为此加了
  `idx_runs_created`（016）。
- **检查失败不降级**：预算读不出来是统计的毛病，不该因此让人失忆。
- **抽取不是丢弃**：攒着的 turn 在预算恢复后还在，下一轮一次抽完。

## 三、计数：两个账本，一个都不能少

```
对话   metrics.prompt_tokens + completion_tokens
抽取   extract_runs.prompt_tokens + completion_tokens
```

只读 `metrics` 的话，重度用户每天 20 次抽取的成本完全看不见——那和
对话本身同量级（R-27.2 第五节）。`prompt_tokens` 已含缓存命中部分，
不重复加 `cached_tokens`。

## 四、四个边界，都是"默认值会伤人"的地方

| 情况 | 处理 | 为什么 |
|---|---|---|
| `daily_tokens: 0` | **不限**，不是零额度 | 当零额度的话，任何没写 budget 段的旧配置一升级就全体降级 |
| `on_exceed: off` | 只告警不降级 | 有人就是想知道花了多少，不想被改行为 |
| `hippo budget reset` | 写时间戳，**不删账** | 删 metrics 会让"这个月花了多少"永久失真 |
| 跨天 | `since = max(day_start, reset_at)` | 昨天的重置标记今天自动失效，不用清理任务 |

`until` 参数不是对称好看：熔断测试要用固定时刻回放，只给 `since` 会把
"今天晚些时候"的行也算进来，于是测试里永远超限、线上却提前一天触发。

## 五、降级到底长什么样

```
正常  [ctx-v3f2a] 人设… / 角色卡… / 钉住… / [记忆 · 3 条] / [心情] / [现在 …]
降级  [ctx-v91b7] 人设… / 钉住… / [现在 2026-11-06 12:00]
```

两个细节：

1. **不写 `last_pack_d` / `last_pack_ids`**。降级那几轮 D 段是空的，写进去
   会让恢复后的第一轮"复用"成一个空记忆块——M13 反复强调的
   "状态回填错一步，下一轮静默失忆"。有专门用例守这条。
2. **`[ctx-v]` 版本号只哈希 A+C**，和正常模式（A+B+C）不同，所以模式切换
   那一次必然掉一次缓存。这是取舍：降级期间去读 B 段（遍历实体 + 特征）
   只为让版本号一致，省下的钱不够付那几毫秒。

## 六、测试覆盖的 12 条

计数 8：本地午夜 / 两本账 / 昨天和明天不算 / 超限降级（并断言状态文字含
"降级中"）/ 0=关 / off=只告警 / 重置不清账 / 跨天恢复。

装配 3：只装 A/C/锚（钉住和锚必须在）/ 不污染复用状态 / 代理超限仍 200 且
请求里没有记忆段。

调度 1：降级中不排抽取任务（monkeypatch `create_task`，一旦被调用即失败）。

## 已知局限

1. 降级期间心跳仍跑（纯 SQL，不花钱），好奇仍会入队但不会插进回复
   （D/E 段不装）。恢复后队列里的旧问题可能已过期，由 `pending_hours` 兜住。
2. 日额度是"总 token"，不区分输入/输出/缓存。按钱算更准，但那需要
   把价目表搬进熔断，而价目表会变——用 token 是稳定的代理指标。
3. 多进程（多个代理共用一个库）下计数是准的（都读库），但"降级"是
   各进程各自判断，切换有几秒不同步。单机单进程是默认部署，不处理。
