> 里程碑：M12.1
> 日期：2026-11-05
> 产出：`hippo/core/topic.py`（`user_keywords` / `relate` / `jaccard`）、
> `hippo/core/store.py`（`kw_lookup` / `co_occur`）、迁移 `010_session_state.sql`

## 一、关键词集：用库里的词表当分词器

手册说"实体名 + 名词短语（用 M4 的规则抽取）"。M4 的规则是正则，认不出名词短语。
而引 jieba 与"即插即用"冲突（30MB，且分词错一次就漏一条，M10 已否过一次）。

实际做法：把句子切成 n-gram，**只保留在 `kw_index` 里真的出现过的那些**。

```
"房租涨了多少" → 房租 租涨 涨了 了多少 房租涨 租涨了 …
                 ↓ 查 kw_index
                 {房租}
```

这等价于"用这个系统自己的语言做分词"：库里的关键词就是它的词典。
零依赖、零模型、一次 SQL（走 PK，0.01ms）。

代价：库里没有的新词进不了关键词集。但这不是缺陷——新词恰恰是**新话题**的信号。

## 二、先把 Jaccard 量出来，再说它行不行

手册写的是 `J = |A∩B| / |A∪B|`，预期"老王跳槽"→"老王新公司" J≈0.5。

99 轮真实口吻的对话上跑：

```
相似度分布：J=0:99  （其余五档全 0）
th=0.10  触发率 100%  漏 0%   误 100%
th=0.15  触发率 100%  …
th=0.35  触发率 100%  …          ← 五档完全一样
```

**J 恒为 0。** 原因不是实现错了，是语言：

```
"老王不是让你帮他喂猫"  →  关键词 {喂猫, 老王}
"对，他下周去深圳出差"  →  关键词 {深圳, 出差}
                          ↑ 用"他"，不重复"老王"
```

真实对话里第二句**几乎不重复第一句的实体**，全用代词。Jaccard 在这种数据上
不是"偏低"，是"恒等于零"——五档阈值给出同一个结果，那就不叫判据。

## 三、决策 D75：覆盖率替代 Jaccard

```
coverage = |本轮词 ∩ 上轮词| / |本轮词|
```

两个理由：

1. **分母不该含上一轮的规模。** Jaccard 的分母是并集：上一轮 pack 装了 8 条
   记忆、30 个关键词，J 就被压到 1/30。也就是说 **话题越丰富，越容易被判成
   换话题**——方向是反的。覆盖率只看"这一句有多少落在刚才的话题里"。
2. **空集不除零，且有语义。** 本轮没有内容词时不是"相似度 0"，是"这句话
   没有信息"，要分情况处理（见下）。

### 五种依据

| basis | 条件 | 分数 | 例子 |
|---|---|---|---|
| `coverage` | 两边都有词 | 交集/本轮词数 | "老王跳槽"→"老王新公司" = 1.0 |
| `anaphora` | 本轮无词 + 有代词 | 1.0 | "对，他下周去深圳" |
| `elliptical` | 本轮无词 + 疑问 + 无主语 + ≤5 字 | 0.8 | "什么品种" "去几天" |
| `ask` | 本轮无词 + 有主语的完整问句 | 0.0 | "你养猫了吗" |
| `idle` | 本轮有词、上轮空 | 0.0 | 没有可复用的上下文 |
| `cooccur` | 无共同词但同属一条事件 | 0.9 | "我搬家了"→"房租涨了多少" |

`elliptical` 那条值得单独说：中文里**省略主语就是在说"接着上面那句"**。
"什么品种"离开上文根本不成句。判成切换纯属浪费。而"你养猫了吗"有主语、
是完整的新问题——所以判据不是长短，是有没有主语。

## 四、决策 D76：共现扩展（同一条事件里的词算同一话题）

覆盖率也救不了这个：

```
"我昨天搬家了，从朝阳搬到海淀，房租涨了两千"
  ↓ 下一句
"房租涨了多少"     ← 关键词 {房租}
```
上一轮的关键词是 {搬家, 朝阳, 海淀}，一个都不重合。但它们是**同一条记忆**。

所以加了 `store.co_occur(a, b)`：两组词有没有在同一条事件的 keywords 里出现过。
一次 `kw_index` 自连接（走 `idx_kw_event`），命中就判 0.9。

这是"语义相似"的廉价替代：不用 embedding，不用聚类，用**已有的共现结构**。
M15 夜间巩固会把这套共现做成正式的话题簇，那时这里可以退役。

## 五、会话状态为什么单独建表

`last_pack_keywords` 跨轮有效、跨会话无效。既不该进 `events`（不是记忆），
也不该进 `metrics`（不是计量），更不该往 `turns` 加列（会让 M2 的写入路径
变成"顺便维护一堆无关状态"，一处失败全轮失败）。

迁移 010 新建 `session_state(session, key, value, updated_at)`。
value 用 TEXT 而不是 JSON 列——用 JSON 会引诱人往里塞结构化对象，
然后这张表就成了第二套 schema。

M13 的 pack 复用、M18 的存疑冷却都要用它。

## 六、验收

| # | 要求 | 预期 | 实测 | 结论 |
|---|---|---|---|---|
| 1 | 相同话题 J 高 | ≈0.5 | coverage **1.0** | 达标 |
| 2 | 换话题 J 低 | ≈0 | **0.0** | 达标 |
| 3 | 计算 <1ms | 0.1ms | **0.05ms**（`should_retrieve` 全程） | 达标 |
| 4 | 空集不除零 | 返回 0 | `jaccard(set(), x) == 0` | 达标 |

```
$ python3 -m pytest tests/test_m12_1_jaccard.py
19 passed in 0.21s

should_retrieve  best=0.05ms p50=0.05ms
user_keywords    best=0.01ms p50=0.02ms
```

`should_retrieve` 比手册要求快 2 倍，是因为关键词集只查一次 SQL、
其余全是集合运算。这层的成本可以完全忽略——**它管的是 token，不是 CPU**。
