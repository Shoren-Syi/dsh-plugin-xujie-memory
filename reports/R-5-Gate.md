```
$ python -m tools.e2e_extract

上游调用   聊天 0 次 / 抽取 1 次 / 错路径 0 次

[main]
  [  0-9  ] ok       ev=5 fact=1 trait=1 5ms ¥0.0028
  [ 10-19 ] skipped  prescreen

入库
  events          5
  entities        2
  card_traits     1
  facts           1
  event_entities  1
  extract_runs    2

抽取统计  {'ok': 1, 'skipped': 1, 'total': 2, 'attempted': 1,
          'success_rate': 1.0, 'events': 5, 'verbatim_fail': 0}

抽到的记忆（前 5 条）
  #1 t2 w=0.50 [搬家 朝阳 海淀] 我昨天下午搬家了，从朝阳搬到海淀，房租涨了两千
  #2 t2 w=0.50 [深圳 出差 老王] 近多了，走路二十分钟。对了老王说他下周要去深圳出差
  #3 t2 w=0.50 [] 是啊，他上个月还在广州待了半个月
  #4 t2 w=0.50 [] 我下周得请他吃个饭，顺便把借他的书还了
  #5 t2 w=0.50 [加班] 最近公司项目赶得紧，天天加班到十点

✅ 端到端通过
```

**这 20 轮里发生了什么**：

- 10 轮有内容 → 切成 2 个窗口（每窗 5 轮）
- 第 1 窗抽了 5 条事件 + 1 条事实（居住地=海淀）+ 1 条特征（老王经常出差，证据指向 #2）
- 第 2 窗 5 轮全是寒暄 → 预筛挡掉，**0 次 API 调用**
- 20 条 turn 全部标记已抽，pending 清零
- `verbatim_fail=0`：5 条 raw 全部是原文切片

**这个脚本能测出什么、不能测出什么**：

能测：URL 拼接、`/v1` 重复、header 大小写、`response_format` 是否真的发出去、200 但 content-type 不对、httpx 的 timeout 参数位置写错。——这些 MockTransport 全测不出来，因为它根本不做 URL 解析。

不能测：模型抽得准不准。

## 4. 未验证清单 —— **已于 2026-11-05 全部补测，见 [R-5.5](./R-5.5.md)**

| # | 项 | 计划补验成本 | **实测结果** |
|---|---|---|---|
| U-1 | 真实模型 schema 合法率 | 1 次调用 | **100%**，但这是 `response_format` 强制的，**不是质量指标** |
| U-2 | 真实模型遵守"raw 逐字"的比例 | 20 次调用（约 0.1 元） | **100%（44/44）**，含 4 个负样本窗口，有区分度 |

| U-4 | 真实 30s 超时的行为 | 需构造慢响应 | 不用构造了：**实测 15–22 秒是常态**，30s 阈值必然超时 → 已改 90s |
| U-5 | 上下文缓存命中率 | 连续 5 次调用 | **97.79%（17408/17801）**，前缀匹配生效，TTL ≥ 225s |

实际总花费 **¥0.13**（70 次调用），比预算的 0.1 元多 30%，因为中途跑了 4 遍评测（第一版语料没有负样本，作废重写）。

**补测推翻了两个原有判断**：

1. **U-4 原以为"要构造慢响应才能测"** —— 实际上不需要构造，真实模型本来就慢。30s 的设计阈值是从 DeepSeek 的经验搬来的，在 mimo 上直接不成立。
2. **成本优化的方向搞反了** —— 原计划把 D13（固定前缀）当作省钱主力，实测输入只占总成本 **5.5%**，输出占 **97.4%**。也就是说把输入优化到 0 也只能省 5.5%。

## 5. 已知缺陷

| # | 缺陷 | 严重度 | 计划 |
|---|---|---|---|
| 1 | 关键词/实体都空的事件搜不到（端到端里是 2/5） | 中 | M6.1 |
| 2 | `timeparse` 不认"下个月""有空的时候" | 低 | M19 |
| 3 | 无日期的计划被丢弃，没降级成事件 | 中 | M19 |
| 4 | 聊 3 轮就关掉的尾巴不会自动抽 | **高** | M21 心跳 |
| 5 | `trait.confidence` 写死 0.6，不区分 observed/inferred | 低 | M7.2 |
| 6 | `EntityIndex` 不自动失效（同窗口新实体识别不到） | 低 | 无害（先抽完再写库） |
| 7 | 不设 `X-Hippo-Session` 时，跨天开新对话会分裂成多个 session | **高** | M2 设计问题，见下 |

第 4 条要展开：`every_n_turns=5` 意味着不足 5 轮不抽。用户聊 3 轮就关掉，那 3 轮留在 pending 里，直到下次再聊。如果他一去不回，这段对话就没进记忆。

现在的补救只有 `hippo extract --force`（手动）。M21 的心跳子代理会周期性扫 pending 并补抽——那是正确的解法，但现在没有。

**这是"无感"这条约束上最明显的缺口。** 必须在 M6 之前想清楚：是降低阈值（比如 3 轮），还是让心跳提前到 M6。

第 7 条要展开：`session.identify()` 在没有显式头时，按**首条 user 消息的 hash** 归并。这对"同一个客户端连续追问"成立，对"每天开一个新人对话"不成立——每天的第一句话不同，就是新 session，昨天的记忆全部看不见。

写 M5.4 测试时被这件事绊了一下（5 轮进了 5 个 session），才发现它不是测试问题，是**默认路径的真实行为**。

普通用户不会设 `X-Hippo-Session`。所以"即插即用"这个卖点，在跨天场景下是打折的。

可能的修法（M6 之后）：
- 默认 session 改成"固定值 + 可切换"，即不传头就全部归到 `main`，用 `/v1/models` 或 CLI 切换
- 或者按"客户端 IP + UA"归一，但多设备就串了

这不是 M5 的活，但必须在 M9（检索）之前定，因为它决定了"记忆是按会话隔离还是按人隔离"。

## 8. 下一步：M6 之前必须先决定的事

M6 是"三级表示"（关键词质量 / 摘要质量 / 原文保真）。它的所有指标都建立在"抽取出来的东西是对的"这个前提上。

但 U-2（raw 锚定通过率）没验证。如果真实模型只有 70% 能锚上，M6 的评测就是在一个漏了 30% 的样本上做的。

**建议顺序调整**：M6 之前插一个 M5.5「真机抽样验证」——有 key 时花 0.1 元跑 20 个窗口，把 U-1/U-2/U-3 补上。没有 key 就先做 M6，但报告里必须挂这个债。

我倾向后者（先做 M6），因为 M6 的产出不依赖具体数值，只依赖"输入是合法的 ExtractResult"。但 `verbatim_fail` 这个指标会一直挂在 `hippo stats` 里，等有 key 的那天，一眼就能看出来。
