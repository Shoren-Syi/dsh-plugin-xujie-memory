# R-9.3 候选集上限保护

> 里程碑：M9.3
> 日期：2026-11-05
> 数据：`tests/test_m9_3_cap.py`（7 例）
> 结论：**达标**。这一节自己没什么逻辑，难的是让截断**可见**。

---

## 一、`LIMIT cap + 1`

上限保护唯一需要想清楚的事：**怎么区分"刚好 800 条"和"超过 800 条"**。

用 `LIMIT 800` 拿回来 800 条，无法判断是"正好"还是"砍掉了"。
于是每次都当截断处理 → 日志永远在报警 → 报警久了没人看 →
真正超限的那次被淹没。

多取一条就能区分：

```python
params.append(int(cap) + 1)
ids = [...]
if len(ids) > cap:
    return ids[:cap], True
return ids, False
```

`test_exactly_at_cap_is_not_truncated` 造正好 800 条，断言 `truncated is False`。

## 二、截断按 weight，不是按 id

按 id 截断的表现是"它只记得最初那 800 件事"——最近的事一件都不记得。
这种 bug 在任何冒烟测试里都看不出来，用两个月才会被用户发现，
而且用户会说"它记性变差了"，不会说"检索有 bug"。

```sql
ORDER BY e.weight DESC, e.event_time DESC, e.id DESC
LIMIT ?
```

`test_truncation_keeps_highest_weight` 造 1200 条权重递增的事件，
断言权重最低的 400 条一条都没留下。

## 三、截断必须留痕

```python
if truncated:
    log.warning("retrieve.l1.truncated", extra={"fields": {
        "session": session, "cap": cap, "entities": len(query.entity_ids),
        "mode": query.mode, "ms": round(elapsed, 2)}})
```

`entities` 和 `mode` 两个字段是给调优用的：
截断发生在"有实体"时说明这个实体关联的事件太多（主角实体，M15 该给它做摘要聚合）；
发生在"无实体"时说明这次查询压根没认出人（R-9-Gate 第三节的问题）。

测试里要注意 `hippo` 根 logger 的 `propagate=False`（log.py 里刻意的，
避免污染宿主程序），所以 pytest 的 `caplog` 收不到，得直接挂 handler。

## 四、数字

```bash
$ python -m tools.bench_retrieve --stage L1 --repeat 30
历史意图   8000 ->  800 candidates (10.0%) in 2.81ms  p50=2.87ms
无实体    8000 ->  800 candidates (10.0%) in 2.85ms  p50=2.95ms
```

**10% 不是压缩失败，是上限保护在工作。** 手册 DoD 说"压缩到 5% 以内"，
那说的是"查询提到了人"的情况（实测 2.5%）。没提到人时 L1 无从下手，
能做的只有"给权重最高的 800 条"——这时候 10% 是硬上限，不是结果。

## 五、一个没做的优化

8000 条无实体查询要 2.85ms，其中约 2ms 花在 `ORDER BY weight DESC` 的排序上。
加一个部分索引可以省掉：

```sql
CREATE INDEX idx_events_live ON events(session, weight DESC)
WHERE superseded_by IS NULL AND archived = 0;
```

**没加。** 理由是 2.85ms 已经在 DoD（<5ms）之内，而多一个索引要多一次写放大——
M9 是读路径，但表是写路径的。等 M13 pack 之后如果整体延迟超预算，再回来加，
那时才有真实的分段数据（而不是我现在拍脑袋估的"排序占 2ms"）。
