# R-6.3 原文不可变

> 里程碑：M6.3
> 日期：2026-11-05
> 测试：`tests/test_m6_3_immutable.py`（18 例）
> 结论：**达标，且发现手册写错了一条**。

---

## 一、为什么这条是铁律

`events.raw` 是唯一真相源。整个系统的可信度建立在一条前提上：

> 你三个月后看到的那句话，是用户当时真的说过的那句话。

一旦允许修改，任何一次"顺手润色"都会让这条前提失效，而且**事后无法分辨**
哪条被改过。这跟"日志能不能改"是同一类问题——不是权限问题，是可信度问题。

所以约束放在**数据库层**，不放在代码层：

| 层 | 强度 | 谁能绕过 |
|---|---|---|
| 代码约定（"别改 raw"） | 弱 | 半年后的我，任何一个新调用方 |
| 数据库触发器 | 强 | 只有显式打开维护开关 |

## 二、实现的四道闸

```sql
-- 1. 拒绝 UPDATE raw。用 IS NOT 而不是 <>：NULL 与非 NULL 比较时
--    <> 的结果是 NULL（假），会漏掉"把 raw 改成 NULL"这一种破坏。
CREATE TRIGGER trg_events_raw_immutable
BEFORE UPDATE OF raw ON events
WHEN OLD.raw IS NOT NEW.raw
BEGIN SELECT RAISE(ABORT, 'events.raw is immutable'); END;

-- 2. 拒绝 DELETE。维护操作（清空测试库、用户 wipe）需要删，
--    用显式开关放行，而不是留个后门表——开关本身也会被审计。
CREATE TRIGGER trg_events_no_delete
BEFORE DELETE ON events
WHEN coalesce((SELECT value FROM maint_flags WHERE key='allow_event_delete'),'0') <> '1'
BEGIN SELECT RAISE(ABORT, 'events is append-only ...'); END;
```

| # | 闸 | 位置 | 拦的是 |
|---|---|---|---|
| 3 | 写入期子串校验 | `Store.add_event(source_text=...)` | 一开始就写了个模型润色过的句子 |
| 4 | 只读连接 | 无（本次未做） | —— |

第 3 道最重要，也最容易漏：**触发器防的是"事后改"，它防不了"一开始就写错"。**
`raw` 是模型给的，而模型天生喜欢把话说通顺。所以 `add_event` 增加了
`source_text` 参数，传入时要求 `anchor_raw(raw, source_text) == raw`——
锚不上或锚上的片段与入参不一致，直接 `StoreError`。

## 三、手册写错的地方：`INSERT OR REPLACE`

手册的「常见坑」写着：

> 触发器会让 `INSERT OR REPLACE` 变成 UPDATE，从而被拒。

**这是错的。** 实测：

```
$ python3 -c "..."
UPDATE raw   ❌ 被拦: events.raw is immutable
DELETE       ❌ 被拦: events is append-only ...
OR REPLACE   ⚠️ 成功，raw 变成 '被替换的原文'  ← 绕过成功
```

SQLite 的 `OR REPLACE` 是"**先删后插**"，不是 UPDATE。
而 `recursive_triggers` 默认是 **OFF**，此时这次内部删除**不触发** BEFORE DELETE，
连 FTS 的 `events_ad` 也不响。于是一句

```sql
INSERT OR REPLACE INTO events(id, session, event_time, ingest_time, raw)
VALUES (1, 's', 1, 1, '被替换掉的原文');
```

就能把原文换掉，**所有触发器保持沉默**。

打开 `PRAGMA recursive_triggers = ON` 之后，内部 DELETE 会触发
`trg_events_no_delete`，整条约束才真正闭合。

这个 PRAGMA 是**连接级**的，不是库级，所以放在 `db.connect()` 里，
每个连接都会设一次。测试里专门锁了这条：

```python
def test_recursive_triggers_is_on_for_every_connection(tmp_path):
    for _ in range(2):
        c = connect(db)
        assert c.execute("PRAGMA recursive_triggers").fetchone()[0] == 1
```

如果哪天有人为了性能把它关掉，`test_or_replace_cannot_bypass_immutability`
会立刻红。

## 四、一个容易误判的地方

BEFORE DELETE 是**行级**的。空表上执行 `DELETE FROM events` 不触发任何触发器，
看起来像"没拦住"。写测试时我先踩了这个：

```python
store.delete_event(999999)          # 表里一条数据都没有
with pytest.raises(...):
    store.conn.execute("DELETE FROM events")   # 不抛
```

不是漏洞（本来就没东西可删），但会让人误判自己的测试有效性——
和 M5.0 那次"实体 id 只到 3，LIKE 和 = 行为一样"是同一类错误：
**测试数据不具备触发条件，所以它绿了，但它什么都没测。**

现在两条测试并存：有数据时被拦、空表时不报错（并解释为什么）。

## 五、维护开关不漏

`delete_event()` 在同一事务里开开关、删、关开关。删除失败（包括删不存在的 id）
时事务回滚，开关不会残留。

开关残留的后果比崩溃严重：库会长期处于"可以删"的状态，而没人知道。

## 七、没做的

- **没有只读连接**。如果进程被注入，攻击者仍可以在一个连接里打开维护开关
  再删数据。这一层需要 OS 级文件权限，超出当前范围。
- **`bulk_import_events` 不受子串校验保护**（它直接 executemany 写裸 SQL）。
  它只用于归档还原，来源是已经校验过的库；但这是一个理论上的缺口，
  如果以后有"从外部 csv 导入"，必须补。
