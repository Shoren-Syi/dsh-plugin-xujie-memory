# R-7.2 trait 与证据链

> 里程碑：M7.2
> 日期：2026-11-05
> 数据：`reports/data/eval_m7.json`（14 窗口 / 13 trait / ¥0.026）
> 结论：**达标**。证据覆盖 13/13，槽位 100% 填充；但"矛盾失效"这条靠槽位实现，而槽位词表是开放的，长期会发散。

---

## 一、四条规矩怎么落地

| 规矩 | 实现 | 反面 |
|---|---|---|
| 无证据不许落库 | `add_trait` 里 `if not evidence: raise NoEvidenceError` | 静默丢弃 → 角色卡凭空长出特征 |
| 重复不膨胀 | 同文本 → 合并 evidence，`confidence += 0.1`，上限 0.95 | 每次提到就插一条 → 卡变成流水账 |
| 矛盾要失效 | 同 `slot` → 旧条 `valid_to = now`，**不删** | 删掉就查不到"他以前在哪工作" |
| 证据可回溯 | `evidence` 存 event_id 数组，`hippo traits` 直接打印 `#1024` | 存一段文本摘要 → 查不回原文 |

第三条需要一个"槽位"概念，这是手册没写、但不加就做不出来的东西：

```
旧：在字节做后端
新：在创业公司做后端
```

这两句话字面毫无关系，字符串相似度 0，唯一能比的是**它们在回答同一个问题**。
所以 007 迁移给 `card_traits` 加了 `slot`，并建了部分唯一索引：

```sql
CREATE UNIQUE INDEX idx_traits_slot_active
    ON card_traits(entity_id, slot)
    WHERE valid_to IS NULL AND slot <> '';
```

`slot = ''` 被排除在外。这条留白很关键：模型给不出槽位的特征（"话少但心细"）
如果也占一个槽，它们会互相覆盖，一张卡最后只剩一条。

## 二、修掉的那个"假确定"

第一版按模型给的原样写入。`tools/probe_alias.py` 的真机输出暴露了问题：

```
王哥今天又加班到十点…  trait: 老王｜工作常加班、常出差
对了老王说他下周…      trait: 老王｜工作常加班、常出差
我叫他王哥是因为…      trait: 老王｜工作常加班、常出差
隔壁老王这人挺热心的…  trait: 老王｜工作常加班、常出差
王建国说他女儿…        trait: 老王｜工作常加班、常出差
```

模型把同一条 trait 挂在**每一条事件**上。`add_trait` 的去重逻辑正常工作
（只留一条），但每次都 `confidence += 0.1`：0.6 → 0.7 → 0.8 → 0.9 → **0.95**。

一次抽取，模型只是复述了五遍，系统就认定"极其确定"。

修法是在 `persist` 里先按 `(entity, trait)` 去重，合并 evidence，再写一次：

```python
merged_traits: dict[tuple[str, str], tuple[Any, list[int]]] = {}
```

修完之后同一个探针只剩 2 条 trait，confidence 停在 0.6。

**这个 bug 的本质是把"重复表达"当成"重复证据"。**
用户说五遍"我不吃辣"确实提高了置信度——但那是五个**不同事件**。
同一次抽取里的五条复述，是一个证据被数了五遍。

## 四、13 条 trait 撑不起一张卡

14 个窗口、45 条事件，只产出 13 条 trait，平均每个实体 0.48 条。
手册 M7.3 示例里那张卡（"在创业公司做后端"+ "可能对现状不满"）看着很丰满，
真实数据里大部分人是 `traits=0`。

原因不是抽漏了，是**规则 12 把"事件"挡在门外**：

```
老王下周去深圳出差     → event，不是 trait
老王经常出差           → trait（但这是 AI 说的，用户没确认，不能记 observed）
```

真正的稳定特征（在哪工作、养什么、性格）本来就要聊很多轮才出现一次。
所以 0.48 条/实体是正常水位，不是缺陷。

但有个副作用要登记：**空卡的人也在候选池里**。27 个实体里 14 个是 person，
其中 8 个是"用户"（每 session 一个），真正有内容的人只有 3-4 个。
M9 注入时必须按"有没有 trait"过滤，不能按实体数量算 token。

## 五、槽位会发散

真机跑出 10 种槽位，其中 `financial`、`travel_pref`、`schedule`
不在我写的示例里。`schema._SLOT_ALIASES` 做了别名收敛
（job/work/company → employer，location/home → city），但覆盖不了长尾。

两种做法都不对：

- 硬白名单：把 `financial` 映射成空 → 这条 trait 退化成"不占槽"，
  悄悄失去冲突检测能力，**比多一个长尾槽更糟**
- 完全开放：模型这次写 `travel_pref`、下次写 `travel`、再下次 `trip`，
  三条"喜欢旅行"同时 active，矛盾检测形同虚设

现在的选择是：**别名表 + 保留未知槽**。代价是长尾会慢慢变长，
需要在 M15 巩固阶段做一次槽位普查（从库里 group by slot 看分布），
把出现 ≥3 次的合成正式槽位。这件事现在没做。

## 六、和手册不一致的地方

| 项 | 手册 | 实现 | 理由 |
|---|---|---|---|
| 矛盾判定 | "如'在字节' vs '在创业公司'" | 靠 `slot` 判定，不靠文本 | 文本判不出矛盾，模型也判不准 |
| 表结构 | 无 slot 列 | 007 加 `slot` + 部分唯一索引 | 不加就做不出验收第 3 条 |
| trait 去重粒度 | 未提 | 批次内先按 (entity, trait) 合并 | 模型会复述，复述不等于证据 |

## 七、这节没做到的

1. **没有"该有哪些 trait"的标注。** 只能说"写进去的都有证据"，
   不能说"该记的都记了"。这和 M6 关键词是同一个问题。
2. **13 条样本太少。** `inferred` 一条都没有（0%），意味着 M7.3 的前缀
   链路在真实流量里没被走过——见 R-7.3 §二，我单独做了探针。
3. **槽位没有人工复核。** `personality` 那两条是"工作常加班、常出差"
   和"性格热心"揉在一起的一条，槽位给了 personality，其实应该拆成
   `employer` + `personality`。这是模型的拆条能力问题，不是槽位机制问题，
   但会直接降低矛盾检测的准确率。
