## 3. 为什么不做模糊匹配（手册要求 >0.8 相似度）

手册 M4.2 写"trigram 相似度 >0.8 命中别名"。**我没做，这是一个明确的拒绝，理由是不可逆。**

```
"小李" vs "老李"   字符相似度 0.67
"王哥" vs "老王"   字符相似度 0.67
"张三" vs "张二"   字符相似度 0.67
```

调低阈值到 0.6 就能让前两条命中——但"小李"和"老李"在中文里是两个不同的人。
一旦合并，这个人的所有记忆都会挂到另一个人身上，**而且没有任何办法拆回来**：
你在库里看到的是 30 条互相矛盾的事实，无法判断哪条属于谁。

"王哥"="老王"这个知识从哪来？
**从对话里来。** 用户会说"王哥，就是老王"，或者上下文本身就把它俩并列。
M5 抽取器听到这类句子时，把"王哥"写进 `entities.aliases` —— 这是有证据的归并，
错了也能改（删掉一条 alias 即可）。字符相似度没有证据。

**规则：别名只从证据来，不从字形来。**

## 4. 性能设计

```
文本 30 字 → 去重后约 20 个不同首字 → 命中 20 个桶
1000 实体 / 中文常用首字 ≈ 150 桶 → 桶内平均 6.7 条
实际比较次数 ≈ 20 × 6.7 = 134 次子串判断 → 0.04ms
```

对照：不分桶时 1000 次子串判断 ≈ 0.4ms。10 倍差距，而且实体数是会长的：
一年后 8000 实体，不分桶就是 3.2ms——预筛反倒成了每轮最慢的一步。

分桶的代价是 `_buckets` 占内存（约 1000 × 60 字节 = 60KB），可以忽略。

## 5. 调用约定（很重要，M5 必须遵守）

`EntityIndex.from_store()` 每次调用都会 `SELECT * FROM entities`。
**M5 里必须一个窗口建一次，不能每句话建一次**——否则一次预筛就多 5 次查询，
把 0.04ms 变成 2ms。

```python
idx = EntityIndex.from_store(store, session)   # 一个窗口一次
for turn in window:
    prescreen(turn.content, entities=idx)      # 复用
```

## 6. 一个尚未解决的隐患

`EntityIndex.from_store` 只在构建时读一次库。如果同一个窗口处理期间，
M5 往库里写了新实体，索引就是旧的——新提到的人不会命中。

当前无害：一个窗口的处理是"先抽完再写库"，中间不会读。
但如果将来做成流式抽取（边聊边写），这里会静默漏掉新实体。
届时需要给 `EntityIndex` 加 `revision` 字段（比对 `MAX(entities.id)` 自动失效）。
