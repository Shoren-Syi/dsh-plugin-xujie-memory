# R-10.1 关键词倒排

> 里程碑：M10.1
> 日期：2026-11-05
> 数据：`tests/test_m10_1_kwindex.py`（19 例）、`tools/bench_retrieve.py --stage L2`
> 结论：**达标**。8000 条、带 800 候选时 **2.60ms**，全库 **4.79ms**，都低于手册的 8ms。
> 但真正的工作量不在倒排本身——在**查询侧的分词**，那一层一开始根本不存在。

---

## 一、问题的形状

手册说得很直白：

> SQLite FTS5 的 `trigram` 分词器要求 token 至少 3 个字符。"老王""猫粮""杭州"
> 这些 2 字词，trigram 索引不到。中文里 2 字词占多数。

这句话我知道，但它只描述了**索引侧**。真正让 M10 卡住的是**查询侧**：

- `kw_index` 里存的是**词**（`搬家`、`房租`、`老王`）
- 用户给的是**句子**（"我上次搬家那个事"）

倒排只做精确匹配。拿句子去查词，一个都命中不了。M9 收工时 CLI 里那句
`tokens = query.replace(",", " ").split()` 就是现状——中文没有空格，
整句是一个 token，永远查不到。

所以 M10.1 有一半的活是"把句子切成词"，而这件事没有免费的解法。

## 二、不用 jieba 的三个理由

**决策 D62：用 n-gram，不引分词器。**

1. **依赖**。用户的第一条硬约束是"即插即用"。jieba 加词典 30MB，
   而整个插件现在只有几百 KB。
2. **错一次就漏一条，而且漏得无声无息**。分词切错（"我/上次/搬家"切成
   "我上/次搬家"）会让整条记忆检索不到。n-gram 不会漏——它宁可多查。
3. **噪声可以被倒排自然消化**。垃圾片段（"次搬""家那"）命中不了任何 token，
   代价只是几个占位符。分词错误不能消化，它是静默丢失。

代价写在 `lexicon.py` 里：一句 12 字的话出 ~30 个片段，
SQLite 的占位符上限是 999，扣掉 L1 的 800 只剩 199，所以 `MAX_QUERY_TOKENS = 48`。

**截断顺序**：2 字、3 字先保，4 字后给。短片段是召回主力（中文词以 2 字为主），
长片段是精度（"字节跳动"）。反过来截会把"搬家"砍掉留下"我上次搬"。

## 三、两段式 SQL：为什么不是一条 join

第一版写的是最自然的那条：

```sql
SELECT e.*, COUNT(k.token) AS hit
FROM kw_index k JOIN events e ON e.id = k.event_id
WHERE e.session = ? AND k.token IN (...)
GROUP BY e.id ORDER BY hit DESC LIMIT 40
```

8000 条、800 候选，**4.23ms**，看起来能过。但换了不带候选集的情况（全库）：

```
带候选 800: 40 条 4.23ms
全库:       40 条 21.78ms
```

21.78ms，超了 8ms 预算两倍多。`EXPLAIN QUERY PLAN` 说出了原因：

```
SEARCH e USING COVERING INDEX idx_events_session_tier (session=?)
SEARCH k USING COVERING INDEX idx_kw_event (event_id=? AND token=?)
```

**它先按 session 扫 8000 条事件，再对每一条回查倒排索引。** 8000 次索引查找，
而倒排聚合本身只要 2.01ms。

拆成两段之后就对了：

```
SELECT event_id, COUNT(*), group_concat(token, char(31))
FROM kw_index WHERE token IN (...) [AND event_id IN (...)]
GROUP BY event_id ORDER BY hit DESC LIMIT ?
```

这一条只看 `kw_index`，走 PK 索引的范围扫描；拿回几百个 id 之后
再用主键取事件行。

## 四、第二步又踩了一次：`session` 条件放进 SQL 就慢 16 倍

拆完之后还是 8.99ms。分段测：聚合 2.06ms，取行 6.34ms。

```sql
SELECT * FROM events WHERE id IN (160 个) AND session = ? AND archived = 0 ...
```

计划器又选了 `idx_events_session_tier (session=?)`——按 session 扫全表。
它估计"160 个 IN + session"里 session 更便宜，但实际是 8000 行 vs 160 次主键查找。

**修法：session 条件移到 Python 里过滤。**

```python
rows = conn.execute(f"SELECT * FROM events WHERE id IN (...) AND archived=0 ...")
out = [e for e in rows if e.session == session]
```

`INDEXED BY` 也能逼它走主键，但那样依赖 SQLite 的内部索引名
（`sqlite_autoindex_events_1`），升级就可能失效。Python 过滤是行为确定的。

这条教训值得记：**"把条件都写进 WHERE"是直觉，不是优化**。
查询计划器对"两个条件谁便宜"的估计会错，尤其在 `IN` 列表这种它没有统计信息的地方。

## 五、还有一个不是 SQL 的瓶颈：`Event.from_row` 每个 19.7µs

取 160 行 → 9.3ms，profile 显示 100% 在 `Event.from_row`：

```
ncalls  tottime  cumtime  filename:lineno(function)
  1600    0.032    0.093  models.py:15(from_row)
```

原因在 `_Row.from_row` 里那句 `for name, field in cls.model_fields.items()`。
`cls.model_fields` 每访问一次都走 pydantic 的属性描述符，20 个字段 × 160 行 = 3200 次。

**修法：把字段元信息缓存到类级别（`lru_cache`）。**

```
from_row  19.7us → 7.3us
```

这是全局改动，所有 DAO 读路径都受益。跑全量测试确认没有行为变化（522 passed）。

## 七、与手册的两处差异

**① `LIKE :p || '%'` 换成范围比较。**

手册写的前缀兜底是 `token LIKE :p || '%'`。SQLite 里 LIKE 默认大小写不敏感，
**用不上 BINARY 排序的索引**，每个前缀都会退化成全表扫。

改成：

```sql
token >= '老王' AND token < '老王' || char(0x10FFFF)
```

UTF-8 的 memcmp 序与码点序一致，所以"以 p 开头"等价于
`p <= token < p + U+10FFFF`，而这是纯范围查询，能走索引。

**② 前缀兜底只在精确命中不足 3 条时才跑（决策 D64）。**

手册把它写成"再加一条"，读起来像是每次都跑。但它是兜底：
范围扫描扫的行比精确查询多一个量级，常态路径不该付这个代价。

## 八、留给下一节的话

1. **`kw_search` 返回的 `hit` 是"命中了几个词"，不是"命中了几个字"**。
   一条事件的关键词是 `字节跳动`，查询片段是 `字节`/`节跳`/`跳动`——
   三个片段都命中同一个 token，但 `GROUP BY` 之后 `COUNT(*) = 1`。
   这是对的（去重成词级），但**长词的权重被压平了**。M26 调参时如果发现
   "长词查询排不上来"，先看这里。
2. **占位符上限是真的会撞**。48 + 800 = 848，离 999 不远。
   如果哪天把 cap 提到 1000，`sqlite3.OperationalError: too many SQL variables`
   会出现在用户发消息的路径上，而它看起来像"库坏了"。
3. **`kw_vocab()` 不缓存是刻意的**，但它是 O(词表大小)。
   真机上词表到 5 万时（约 50 万条事件），每次错字兜底要扫 5 万行。
   到那时再加缓存，并且用 `PRAGMA data_version` 做失效，不要靠"记得清缓存"。
