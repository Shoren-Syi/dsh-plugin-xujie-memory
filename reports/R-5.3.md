## 3. 下标映射：一行代码的静默故障

模型给的是：

```json
{"events": [
   {"raw": "编的话，锚不上"},      // 下标 0，会被丢弃
   {"raw": "真的话"}               // 下标 1，入库
 ],
 "traits": [{"entity": "用户", "trait": "爱说话", "evidence": [1]}]}
```

`evidence: [1]` 指的是**这次输出的第 1 条 event**。而第 0 条被锚定校验丢了。

天真写法：

```python
for ev, eid in zip(kept_events, event_ids):   # kept_events 已经丢了第 0 条
    ...
```

`zip` 把"原下标"抹掉了。于是 `evidence=[1]` 会挂到"kept_events 里第 1 条"——也就是原第 2 条，或者越界。

正确写法是**保留空洞**：

```python
index_to_id: dict[int, int] = {}     # {原下标: 真 event_id}
for i, ev, anchored in kept:
    ...
    index_to_id[i] = event_id        # 只有成功入库的下标才出现

ev_ids = [index_to_id[i] for i in t.evidence if i in index_to_id]
if not ev_ids:
    stats.traits_dropped += 1        # 证据全丢 → 这条特征也不要
```

这个 bug 不会报错，只会让角色卡慢慢长出错误的特征。症状是三个月后 AI 说"你讨厌猫"，而用户从没说过——**而且查不出来**，因为 evidence 指向的那条事件确实存在，只是不支撑这个特征。

`test_evidence_index_keeps_holes` 钉住了它。

## 4. 时间解析的基准点

第一版：

```python
parsed = parse_when(ev.event_time_hint)     # 默认 base = now()
```

测试立刻炸了：

```
E   assert 1793667600 < 1760000000
E    where 1793667600 = Event(...).event_time
```

对话发生在 2025-10-09（ts=1760000000），"昨天"被解析成 2026-11-03——平移了一整年。

**"昨天"不是"相对于现在"，是"相对于说话那一刻"。** M15 巩固、M24 归档回放都要重跑历史对话，这个 bug 会让所有历史记忆的时间轴整体错位，而且不报错（时间戳看起来都合法）。

修法：

```python
base_dt = datetime.fromtimestamp(ingest, ZoneInfo(tz))   # ingest = 那条 turn 的 ts
parsed = parse_when(hint, base=base_dt, tz=tz)
```

这类 bug 只在"回填历史"时暴露。如果只测"刚聊完马上抽"，永远发现不了。

## 5. timeparse：最小实现，明确会被替换

M19 会做完整版（重复规则、模糊时段、跨时区）。现在只需要支撑 `plans.due_at NOT NULL`。

覆盖：

| 输入 | 输出（基准 2026-11-04 22:12 周三） | guessed |
|---|---|---|
| `明天8点` | 11-05 08:00 | 0 |
| `明天早上八点` | 11-05 08:00 | 0 |
| `今晚` | 11-04 20:00 | 1 |
| `下周一下午3点` | 11-09 15:00 | 0 |
| `八点半` | 11-05 08:30（已过 → 顺延） | 1 |
| `下午两点半` | 11-05 14:30（已过 → 顺延） | 1 |
| `3小时后` | 11-05 01:12 | 0 |
| `下个月` | `None` | — |
| `随便什么时候` | `None` | — |

**解析不了就返回 None，不猜。** `due_at` 是 NOT NULL，所以 `plans_dropped` 计数并跳过——宁可少一个闹钟，也不要定在错的时间。

"今晚"原本被解析成 09:00（默认时刻），是测试时肉眼看出来的。加了 `_DAY_DEFAULT_HOUR`："今晚/明晚 → 20:00"、"今早/明早 → 08:00"。用户说"今晚提醒我"，21 点才提醒等于没提醒。

## 6. 情绪增量

`affect` 表是**状态**（0~100 的六个值），抽取给的是**增量**（-20~+20）。

```python
after = {m: clamp(before[m] + delta[m], 0, 100)}
```

两个细节：

**全 0 的 delta 不写库。** 否则每抽一次就建一行 affect，`get_affect` 永远不为 None，而 M20 的"没聊过天时用基线"逻辑就失效了。

**夹到 0~100。** 不夹的话连续 5 次 `joy +20` 会把 joy 推到 160，渲染情绪条时溢出。`test_affect_clamped` 就是跑 5 次加到底。

## 7. 关键词为空时的兜底

模型有时给 `["事情", "问题", "那个"]`，被 `clean_keywords` 全清掉，事件就没有关键词了。

`kw_index` 是**唯一能命中 2 字中文词的通道**（FTS5 trigram 只索引 ≥3 字符）。没有关键词的事件，用户搜"搬家"搜不到。

兜底：

```python
kws = ev.keywords or [r.name for r in ev.entities][:3]
```

退回到实体名。端到端演练里能直接看到效果——桩模型给 `["对话"]`（被清空）后，事件的关键词变成 `[]`，因为那条事件也没提到任何已知实体。这是兜底也救不了的情况，只能靠 M6.1 的关键词质量。

**如实记：这条兜底救不了"既无关键词又无实体"的事件。** 这类事件占比在端到端演练里是 2/5。

## 8. 事务边界

```
锚定（事务外，纯文本计算）
  ↓
BEGIN IMMEDIATE
  entities → events → traits → facts → plans → doubts → affect
COMMIT
  ↓
降级兜底事件（单独事务，只在抽取失败时走）
```

**锚定必须在事务外。** 它要遍历窗口所有 user 文本做子串查找，窗口大时几十毫秒。放进事务会让写锁多持有几十毫秒，而代理的结账正在等这把锁——用户会感觉到"最后一个字之后卡了一下"。

`store.tx()` 是可重入的（M5.0 引入），所以 `add_event` / `add_trait` 内部自己的事务不会和外层冲突。

## 9. 事故：`has_pending` 把两件事混成一个标志

`slice_windows` 的 `has_pending` 有两个来源：

```python
flush(tok < min_tokens or buf[-1].role == "user")
#      ↑ 太短              ↑ 不完整
```

M5.4 第一版直接用它：

```python
if w.has_pending:
    skip("incomplete")      # 不标记
    continue
```

结果：**5 轮寒暄被当成"不完整"反复重扫**，永远留在 pending。`test_prescreen_blocks_chitchat` 的红灯：

```
E   AssertionError: assert 0 == 1
E    +  where 0 = len(calls)
```

`calls` 是 0 是对的（没花冤枉钱），但 `pending_turn_count` 没清零，下次结账还会再扫一遍这个窗口，永远扫、永远不清。

修法是拆开：`Window.complete` 只看"最后一条是不是 assistant"。

```
不完整 → 跳过，不标记（下次还要抽）
完整但太短 → 预筛决定（过就抽，不过就标记放弃）
```

顺带把 `min_tokens` 从"是否抽取"里摘出来了。它现在只影响"要不要单独成窗"，不再影响"值不值得抽"——因为"值不值得"是预筛的职责，一个规则做一件事。
