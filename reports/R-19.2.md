## 二、两个偏离手册的决定（都要交代）

**1. 自写 asyncio 循环，不引 APScheduler。**
调度器的全部工作是"每 60 秒一次 SQL + 几行 UPDATE"。手册明确
"APScheduler 或自写 asyncio 循环，2 个依赖都行"——选后者，依赖账
（约束⑤）算不过来就不引。

**2. 到点不调模型生成问候语。**
手册说"有结果 → 调一次小模型生成问候语（≤300 token）"。我们的
架构是 pack 装配上下文：到点事件由 pack 的 [计划] 段带进下一轮
（M19.3），模型响应用户消息时自然带出。零 token 的 tick 比小模型
便宜两个数量级，而且不会在用户没开口时凭空弹消息——"主动打扰"
的最后一环留给 M24 心跳统一管。

## 三、三个正确性细节（都有测试钉住）

**1. sweep 的 missed 不能被 tick 洗掉。**
sweep_missed_plans 标 missed=1（不标 fired——晚到的提醒还是要发），
tick 触发时若用 mark_plan_fired 的默认 missed=False 会把它洗回 0，
"这条晚了"的说明就丢了。tick 传 `missed=bool(p.missed)` 原样保留
（`test_tick_preserves_missed_flag`）。

**2. 周期计划复用同一行推进。**
`advance_plan` 把 due_at 推一个周期、fired 拨回 0，不插新行。
daily 计划一年 365 条文本几乎一样的行没有检索价值——计划的价值在
"未来什么时候做什么"，不在"过去触发过几次"。fired_at 保留上次
触发时间。

**3. grace 的语义。**
到点 5 分钟内触发算正常延迟；超过说明进程死过，sweep 标 missed
认账。sweep 在启动时和每轮 tick 前都跑——进程死过重启的场景由
每轮 sweep 兜底，不只靠启动那一次。

## 四、sim_plan 实测

```
$ python -m hippo.tools.sim_plan --delay 90 --tick 15
planned 23:39:18 fired 23:39:18 delay=0s
```

delay=0 是 tick 边界恰好对齐计划时刻；一般情形 delay ∈ [0, tick)。
生产 tick=60s，误差上界即手册要求的 60s。模拟脚本跑真实时钟
（asyncio 循环），单测用注入的虚拟 now——不真 sleep。
