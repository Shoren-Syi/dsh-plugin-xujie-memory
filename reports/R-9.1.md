# R-9.1 实体过滤

> 里程碑：M9.1
> 日期：2026-11-05
> 数据：`tests/test_m9_1_entity_filter.py`（10 例）、`tools/bench_retrieve.py`
> 结论：**达标**。8000 条 → 200 条（2.5%），0.94ms。
> 但"2.5%"这个数字有个前提——**查询里提到了人**。没有实体时 L1 一条都砍不掉，
> 详见 R-9-Gate 第三节。

## 一、先定一件事：查关系表，不查 JSON 列

手册 M9.1 写的是：

> 命中实体的事件 + `events.entities` 包含该 id 的事件，取并集。

实际库里这两份数据是同步的：`002_event_entities.sql` 用触发器把
`events.entities`（JSON 缓存）写进 `event_entities`（关系表），
并在文件开头写明"event_entities 是唯一真相源"。

取并集在这里不是"更保险"，而是**掩盖故障**：如果同步触发器坏了，
关系表少一半数据，JSON 列看起来完全正常，并集会悄悄把关系表的缺口补上，
于是"实体挂错人"这类事故又会回到 `LIKE '%3%'` 命中的老样子。

**决策 D59：只查 `event_entities`，并加一条不变量测试守住同步。**

```python
# tests/test_m9_1_entity_filter.py
def test_json_column_never_drifts_from_relation(store):
    ...
    assert from_json == from_rel == sorted([a, b])
```

这条测试是 M9 里最便宜的一条，也是唯一能在触发器被改坏时立刻红的一条。

## 二、最长优先 + 占位

一句话里可能同时出现"老王"和"王"。两个都命中会返回两个实体，
候选集凭空翻倍，而且翻倍进来的那部分（"王"关联的事件）按 weight 排序，
会把真正的"老王"挤到后面。

做法是排序后逐个 `find`，命中后把字符区间标记为已占用：

```python
pairs.sort(key=lambda p: (-len(p[0]), p[1]))     # 长名先来
for name, eid in pairs:
    while (i := src.find(name, start)) >= 0:
        j = i + len(name)
        if not any(i < b and j > a for a, b in taken):   # 没被长名占了
            taken.append((i, j)); hit_ids.append(eid)
        start = i + 1
```

`test_longest_name_wins_and_short_name_does_not_double_hit` 守这条。

## 三、单字实体一律不认（MIN_ENTITY_LEN = 2）

`canonical='妈'` 的实体，在"我妈今天住院了"里当然出现了。
但同样会出现在"妈妈""姨妈""姑妈""大妈"里——而后者每一个都是**别的实体**。

命中一次的代价不是"多一条记忆"，是候选集从 3 条变成全库，
然后排序把真正相关的挤掉。这类错误在单测里看不出来（测试库小），
真机上表现为"它开始答非所问"。

代价写进了测试：

```python
def test_single_char_entity_never_matches(store):
    """代价是"我妈"捞不到 canonical='妈' 的实体。收益是"妈"不会命中"姨妈"。"""
```

实际影响不大：M7 建实体时 `normalize_name` 会把"我妈"的"我"去掉，
而抽取器给的实体名通常是"妈妈"而不是"妈"。

## 四、性能

```bash
$ python -m tools.bench_retrieve --stage L1 --repeat 30
库 8000 条事件    cap=800    repeat=30
有实体    8000 ->  200 candidates ( 2.5%) in 0.94ms  p50=0.96ms
实体+时间  8000 ->    0 candidates ( 0.0%) in 0.85ms  p50=0.87ms
历史意图   8000 ->  800 candidates (10.0%) in 2.81ms  p50=2.87ms
无实体    8000 ->  800 candidates (10.0%) in 2.85ms  p50=2.95ms
PASS
```

best 与 p50 差 0.03ms，没有抖动。走的是 `idx_ee_entity(entity_id, event_id)`
反查 + 主键回表，没有全表扫。

**为什么测试里不写 `assert elapsed < 5ms`**：事故 46 已经踩过一次——
CI 机器慢 4 倍时那条断言会红，而它红的时候并不代表代码变慢了。
测试里比的是"带实体 vs 不带实体"的比值，比值可移植，绝对秒数不可移植。

## 五、真机：5 条查询里只有 2 条命中实体

`tools/eval_l1.py` 在 15 个窗口抽出来的 44 条真实事件上跑：

```
必留 [老王最近怎么样]  候选   7  recent  实体[老王]  命中
必留 [老王要去哪出差]  候选   7  plain   实体[老王]  命中
必留 [老板骂我那次]    候选   2  plain   实体[老板]  命中
必留 [我老婆是做什么的] 候选   1  plain   实体[老婆]  命中
必留 [小李怕坐什么]    候选   4  plain   实体[小李]  命中
必留 [我几点睡]        候选  44  plain   实体[-]     命中
```

有实体的查询压到 1~7 条；没有实体的（"我几点睡""我吃辣吗""我在哪上班"）
候选 = 全库 44 条，压缩率 0。

这不是 bug，是 L1 的能力边界：它只会看"这句话提到了谁"。
用户问自己的事时不提名字，L1 就帮不上忙。**那条路要靠 M10 的关键词倒排。**

## 六、一个必须记下来的现场

`eval_l1` 第一次跑出来的是"候选 41~44 条 / 44"，压缩率全线失败。
原因是语料被切成 15 个 session，而 M7 的实体表是 `UNIQUE(session, canonical)`：
narrative 里的"老王"和 multiperson 里的"老王"是两条记录（缺陷 22）。

于是对 multiperson 会话问"老王最近怎么样"，实体认不出来 → 不加实体条件 →
返回该会话全库。**检索静默退化成全表扫。**

评测装置里加了 `unify_session()` 把 15 个窗口并成一个（合并了 13 个重复实体），
才量出真实的 2.5%。缺陷 22 本身仍然开着——它会在 M12（话题切换）和
M15（长期摘要）上继续咬人，现在记一笔。
