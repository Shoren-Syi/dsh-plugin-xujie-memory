# R-11.2 引用格式

> 里程碑：M11.2
> 日期：2026-11-05
> 产出：`hippo/core/drill.py`（`format_event`）
> 数据：`tests/test_m11_2_format.py`（**29 例**，手册预期 9 例）
> 结论：**达标**。三档格式快照通过，时间/来源齐全 100%，长原文截断带 `…`。
> 这一节真正的产出是**三条不让模型读错的规矩**，见第二、三、四节。

---

## 一、三档共用一套外壳

```
[原话   · 2026-11-04 · 用户] "我昨天下午搬家了，从朝阳搬到海淀，房租涨了两千，累死了"
[记忆   · 2026-11-04 · 用户] 用户昨天下午从朝阳搬到海淀，房租涨了两千，搬家很累
[关键词 · 2026-11-04 · 用户] 搬家 朝阳 海淀 房租
```

`深度 · 时间 · 来源` 三段固定，只换前缀和正文来源。好处是 M13 装配时
不用为"这条是原文那条是摘要"写两套逻辑——遍历 items，取 `depth`，调一次。

三档的用途：

| 深度 | 什么时候用 | 成本 |
|---|---|---|
| `raw` | 用户问细节 / 事件被钉住 | 33~400 token |
| `summary` | 默认。8 条 80 token 封顶 | 40~80 token |
| `kw` | 预算极紧（剩不到 100） | 5~15 token |

`kw` 档没有关键词时退回摘要前 40 字，**不给空**：空条目占了位置却不给信息，
比不给更糟。

## 二、决策 D73：时间按 `time_precision` 写，不写满

```
minute → 2026-11-02 10:30
hour   → 2026-11-02 10时
day    → 2026-11-02
week   → 2026-11-09~11-15
month  → 2026-11
year   → 2026
```

一律写 `%Y-%m-%d` 看起来更整齐，但那是在**编造精度**：

> 用户说"去年冬天搬的家"，抽取器给了 `precision=year`、`event_time=2025-01-01`。
> 注入时写成 `2025-01-01`，模型会算"已经过了 672 天"。
> 实际上可能是 2025 年 11 月，只过了 370 天——**差了整整一年。**

模型不会质疑这个日期，它会拿它当事实去推"你现在应该已经适应新家了"。
精度写粗一点，模型就会说"去年冬天"；写细了，它就说"去年 1 月"。
**后者是错的，而且听起来更可信**——这种错误最难被发现。

### 猜出来的时间打 `?`

`time_guessed=1` 时后缀加一个 `?`：

```
[记忆 · 2026-11-04? · 用户] 用户昨天下午从朝阳搬到海淀……
```

一个字符的成本，换模型一句"大概是"。不打这个问号，模型会把
"昨天下午"当成"11-04 09:00 整"去算时间差（真机库里 `event_time` 就是
`11-04 09:00` —— 那是 `parse_span` 把 day 精度归零的结果，不是用户说的时刻）。

### 半开区间不能直译

库里的 `event_time_end` 是**半开边界**：

```
"11 月 4 日这一天"  →  event_time=11-04 09:00, event_time_end=11-05 00:00
```

按日期比较会显示成 `11-04~11-05`，看起来是两天。真机库第一条就是这个形状，
第一版 CLI 输出里多出一个 `~11-05`，像跨了两天。

修法：`end` 落在 0 点时先减一秒，变成"最后一天"再比较。
现在"一天"显示为一天，跨 6 天显示 `10-30~11-04`。
（`test_half_open_range_is_one_day` 守这条。）

## 三、来源不许伪造

```
user → 用户      ai → AI      third → 第三方      其它 → 原样输出
```

最后一条是刻意的：未知来源原样输出 `· system]`，**不硬翻成"用户"**。
把 AI 自己说的话标成"用户说的"，模型下一轮就会把自己的推测当成用户的陈述，
再下一轮就变成"事实"。这条链一旦开始，人工很难发现——
因为每一句单独看都很合理。

## 四、决策 D74：原文单行化 + 内层引号替换

两件事，都是"格式被内容破坏"：

| 内容里的东西 | 不处理会怎样 |
|---|---|
| `\n` 换行 | 一条记忆变成两行，注入格式按行解析时被当成两条 |
| 半角 `"` | 提前闭合外层引号，模型以为原话到此结束 |

```
输入：他说"我不去"，然后就走了
输出：[原话 · 2026-11-04 · 用户] "他说”我不去”，然后就走了"
```

内层引号换成全角 `”`。不换成 `\"` 转义：模型看到的 `\"` 是代码，`”` 是文字。

## 五、截断必须留痕

长原文截到 400 token，末尾加 `…`。

不留痕的后果：`[原话] "我昨天下午搬家了，从朝阳搬到海淀，房租涨了"` ——
模型会把"房租涨了"当成完整信息，而原话是"房租涨了两千，累死了"。
**半句话比没有更危险**，因为它看起来完整。

有了 `…`，模型会说"你当时大概是这么说的"，而不是复述一个被截断的事实。

参数化：`max_tokens` 可覆盖默认（raw 400 / summary 80）。
`summary_max_tokens=80` 是手册的数：一条记忆超过 80 token，
说明模型在写摘要而不是在提炼，M13 的 600 预算装不下 3 条。

## 六、决策 D72：只有一条截断路径

`format_event` 有个 `body` 参数：传了就用它，**且不再截断**。

为什么需要：M11 的 `drill` 已经按**剩余预算**截过一次（可能只有 41 token，
因为剩的就这么多）。如果 `format_event` 再按 400 截一次，两处上限不一致时
会出现"预算里明明装得下、注入的却是半句"——而且只在预算紧张时才出现，
平时测试全绿。

只有一个地方决定"截到多长"，账才对得上。`body=it.raw_text` 一传到底。

字段是对的，拼起来才错。
