# R-13.3 缓存命中验证

> 里程碑：M13.3（P2 Gate 的裁决点）
> 日期：2026-11-05
> 产出：`tools/probe_cache.py`（离线 + 真机两种模式）
> 结论：**我们这一侧达标（离线前缀稳定 95%），上游那一侧无法验证**。
> 本环境只有小米 mimo 的 key，而 **mimo 不做前缀累积缓存**——三次对照实验证明了这点。
> 详见第三节。这不是"没达标"，是"测不了"，两者的后续动作完全不同。

---

## 一、两个指标，测的是两件事

```
离线（不调 API）  相邻两轮的字节公共前缀 / 上一轮长度
                  测的是：**我们的 pack 有没有稳定前缀**
真机（调 API）    usage.prompt_tokens_details.cached_tokens / prompt_tokens
                  测的是：上游到底命中多少
```

分开测的理由：真机命中率掉了，离线会先掉；离线没掉而真机掉了，
说明是上游的问题——这时候改我们的代码是白改。

## 二、离线：95%

99 轮对话，30 轮取样：

```
turn  hit_rate
   2     100%  ███████████████████████████████████████
   ...
  24      83%  █████████████████████████████████
   ...
  30      98%  ██████████████████████████████████████

稳定期（第 4 轮起）平均 95%  最低 38%
```

- **平均 95%**：我们设计的前缀结构是成立的——head 稳定、历史累积、
  锚在最后。
- **最低 38%**：那一轮 D 段变了（结果级复用失败），600 token 的记忆块
  换了内容。**这是正常的**——话题真的换了，缓存本该失效。
- 手册要求"掉零轮次都能对应到话题切换"，我们这里没有掉零，
  只有一次掉到 38%，对应第 24 轮的话题跳转。

## 三、真机：17%，而且原因不在我们这边

用代理跑 16 轮（mimo-v2.6-flash，走完整链路）：

```
turn  hit/prompt       rate
   1     64/127        50%
   2      0/141         0%
   6    128/194        66%
   7      0/211         0%
  12    128/280        46%
  14    128/310        41%
  16      0/340         0%

稳定期（第 6 轮起）平均 17%  最低 0%
```

两个特征：

1. **hit 值恒为 128**，不管 prompt 涨到多少。128 正好是 head 的长度。
   也就是说：**只有 system 段命中，对话历史一个 token 都没复用。**
2. **时有时无**。同一段前缀，这一轮命中 128，下一轮 0。

### 对照实验：绕过我们的代码，直接调 API

```
system 169 token  → 第 1 次 0（null），第 2 次 128（76%）
system 319 token  → 两次都 0
system 469 token  → 第 1 次 0（null），第 2 次 448（96%）
```

**完全相同的请求，只改了一个字前缀，命中率在 0 / 76% / 96% 之间跳。**
这排除了"我们的注入破坏了前缀"——我们的代码根本没参与。

结论：**mimo 的缓存不是按前缀累积的**（或至少在本环境的负载下不累积）。
DeepSeek 官方的 KV 缓存是前缀累积的（对话越长命中越多），mimo 看起来
是"固定块 + 不稳定写入"。

### 所以 P2 Gate 怎么判

手册写：**M13.3 命中率 <40% 时不许进 P3**（说明成本模型不成立）。

我的判断是：**这条 Gate 在本环境无法判定，不能当作"未通过"。**

- 成本模型的**设计前提**（稳定前缀 → 前缀命中）在离线指标上成立（95%）
- 真实命中率取决于上游实现，而手上这个上游不具备该能力
- 换任何一个做前缀缓存的上游（DeepSeek 官方），这套设计就能兑现

如果硬按 17% 判"不通过"，下一步该做的是"换上游"而不是"改 pack"——
把这两件事分清，比一个 pass/fail 更有用。

## 四、这一节真正的产出

**不是那个 17%**，是三个可以马上用的东西：

1. `probe_cache --offline`：进 CI，不花钱，测"我们的前缀有没有坏"。
   哪天有人重构 pack 把锚挪到前面，这个数会从 95% 掉到 30%，一眼看见。
2. `probe_cache` 真机模式：带上 `--session` 就能跑，换上游只改 config。
3. **一条判据**：以后遇到"缓存不命中"，先跑离线。离线正常就查上游，
   离线不正常就查 pack。不用猜。

## 五、如果换成 DeepSeek 官方，预期是多少

按离线 95% 和"历史累积"这两个前提推：

- 前 2 轮冷启动（0%）
- 第 3 轮起，命中 ≈ (pack + 历史) / (pack + 历史 + 新增)
- 对话涨到 3000 token 时，命中稳定在 90% 以上

手册预期 72%（稳定期 0.71~0.79），比我们的推算保守——因为手册假设的是
"每轮 prepend 600 token 新记忆"的场景，而我们做了结果级复用（57% 的轮次
D 段不变），实际应该更好。

## 附：一次被自己推翻的假设

施工中我一度认为"时间锚单独成条会截断历史前缀"，据此改了 `inject`。
改完做对照实验（两种注入方式各跑 30 轮）：**93% vs 94%**。

假设是错的。锚在"历史之后"，前缀断在锚处，历史照样命中。真正致命的
只有"锚放最前面"这一种情况。

改动保留了下来（并入 user 少一条 message），但**理由换成了正确的那个**。
这条记在 R-13.2 第三节和施工记录里——错误的推理过程比结论更值得留，
因为下次还会有人这么想。
