# R-22.3 · 记录与能力边界

**日期** 2026-11-06　**花费** ¥0

## 做了什么

1. **`record()`**：弃权落 `kind=giveup` 的 cold 事件
   - `summary = "做不了：{task} / 原因：{reason}"`（手册原文格式）
   - `tier=3`、`w0=0.1`、`source="ai"`（是 AI 的弃权，不是用户说的）
   - 迁移 013 加 `giveup_level` 列——level 是结构化字段，塞进
     keywords 等于让每个查询做字符串解析（M9 定过"结构进列不进串"）
2. **`store.giveup_stats()`**：SQL 聚合 `(level, reason)` 次数降序 top-N
3. **`hippo stats --giveup`**：输出与手册样例逐字一致
4. **同 reason ≥5 次提醒一次**：`giveup_warn_once`，判据是"这条
   reason 是否提醒过"（set_state 存集合），不同 reason 各自算

## 关键决定

- **不进常规检索/注入**：`_EXCLUDE_KINDS` 加 `giveup`（"idle/raw"
  之后第三项）。能力边界是**统计给用户看的东西**，不是模型该在
  对话里提的事——每次 prompt 塞"我上次做不了 X"等于让 AI 反复道歉。
  测试钉死：建了记录后 `l2_search` 不返回、`pack` 里不出现其文案。
- **聚合放 SQL 不放 Python**：事件可能几万条，GROUP BY 一次扫描，
  全量拉进内存是几百毫秒起。
- **提醒一生一次**：历史不会消失，同一个 reason 反复提醒只会变成噪声。
  和 pin_warn_once 的差别在这里——pin 的条数会降（用户清理），
  giveup 的计数只增。

## 实跑

```
$ hippo stats --giveup
能力边界（弃权记录）
  decline: 缺少文件权限 (5)
  ask_help: 需要确认目标格式 (3)
```

## 验收对照

| # | 要求 | 结果 |
|---|---|---|
| 1 | 全部记录 | 三种 level 全落库，字段契约断言 |
| 2 | 可聚合 | top10 排序正确、top 限制生效 |
| 3 | 重复提醒一次 | 6 次只提醒 1 次（第 5 次）；不同 reason 独立 |
| 4 | 不影响正常检索 | 检索 0 命中、pack 0 出现 |
