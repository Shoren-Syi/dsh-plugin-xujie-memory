## 二、手册的预算数字对不上，原因是 raw 的定义不同

手册三处数字放一起看，装不下：

```
pack.memory_tokens          600
rank.memory_budget_ratio    0.6   → L2 用 360
                            剩 240 给 L3
M11 预期 avg_raw_tokens     312
max_raws                    2     → 需要 624
                             624 > 240   ❌
```

按这个数，`max_raws=2` 永远用不上。真机上量完才知道为什么：

| 项 | 手册 | 真机实测（44 条） |
|---|---|---|
| 单条 raw | 200~500，平均 **312** | 20~48，平均 **33** |
| L2 实际占用 | 360（上限） | **175**（8 条摘要装不到上限） |
| L3 可用 | 240 | **425**（600−175） |
| 两条原文 | 624 > 240 ❌ | 66 < 425 ✓ |

**差 10 倍，因为 raw 不是一回事。**

手册假设 `raw` 是"窗口原文"（几百 token 的一整段对话）。我们库里不是：

```
raw = "我昨天下午搬家了，从朝阳搬到海淀，房租涨了两千，累死了"
```

这是 M5 的 `anchor_raw` 干的活：一条事件一条**句子**，锚定到用户原话里
对应的那一句，不是整段窗口。

### 这个差异的两面

**好的一面**：原话层比手册设想的便宜 10 倍。19% 触发率下，平均每轮多 33 token，
一天 20 轮就是 660 token——不到一次抽取的 1%。

**代价**：原话层给的是"这一句原话"，不是"当时的整段对话"。
用户问"我们当时聊搬家聊了多久"，一条句子回答不了。
要回答得回 `turns` 表按 `ingest_time` 取窗口——那是另一条路径，本里程碑不做。

所以 D70 那条"第二条按 60 token 判定"在真机上是安全余量，不是刚需
（425 装两条 33 绰绰有余）。留着，因为换成 `raw` 更长的库
（有人把整段对话写进 raw）时它就开始起作用了。

## 三、判据 19% 是**上限**，不是实际花费

同一份 100 条查询，三个数：

| 口径 | 值 | 含义 |
|---|---|---|
| 判据触发 | **19%** | 有多少句话在要细节 |
| 有候选 | 100% | 44 条的小库，L1 给了候选 |
| **关键词命中** | **47%** | L2 真的命中了（`degraded` 为空） |
| 实际下钻 | **5%** | 前两者 + 预算 + max_raws 都过 |

**问细节的句子，恰恰更容易命中不了关键词。**

```
"我当时怎么说的来着？"     n-gram 出来是：当时/怎么/说的/来着
                          → 全是停用词和泛词，一个都命中不了
"搬家那天具体怎么说的"     → 命中「搬家」，正常下钻
```

19 条判据触发里 14 条 `degraded`。这不是检索坏了：用户说"我当时怎么说的"
的时候，本来就**没给任何可检索的内容**。要靠上文（上一轮在聊什么）才能知道
"当时"指哪件事——那是 M12 话题切换的活。

所以在 M12 之前，原话层的实际触发率就是 5% 上下。这个数字会随着 M12
把上下文接进来往上走，走到 10~19% 之间。**现在不用为它调参**。

## 四、三条事故

| # | 现场 | 修法 |
|---|---|---|
| 63 | `recall "我当时怎么说的来着" --raw` 命中 0 条，却把"老板骂我"两段原文贴给了用户 | `degraded` 时不下钻（pinned 除外） |
| 64 | 库里 `event_time_end` 是半开边界，"11-04 这一天"显示成 `11-04~11-05` | end 落在 0 点先减一秒 |
| 65 | `max_raws=2` 是死配置，而基准只报"平均 raw token"，看不出每轮几条 | 基准加下钻条数分布；门槛改成只管开闸 |

**63 的共同形状**和 M10 的 59/60/61/62 一样：不崩不报错，只是给了错的东西。
模型拿到一段无关的"原话"，会非常自信地编一个和它相关的回答。
这类缺陷只能靠"人肉看一遍输出"发现——所以 CLI 加了 `--- 注入预览 ---`，
以后每个里程碑都要看一眼最终注入的文本长什么样。

**65 是**指标设计问题**：`avg_raw_tokens=41` 这个数，在"每轮拉 1 条"和
"每轮拉 2 条"下是一样的。指标不区分，就等于没测。加了 `[1条×1 2条×4]`
才看出 max_raws 一直没生效。

## 五、这一轮的账

- 两节都实现，579 测试全绿，8 项验收全部达标，**¥0**
- 最大的产出是**量清了 raw 的真实长度**（33 token，手册设想 312），
  以及由此引出的预算重算
- 判据设计上做了一次**有意识的取舍**：不强求 100% 准确，
  而是让错误停留在 3 条、且每条都能说清为什么错
- 自己的失误：63 号事故是我先写完 CLI 才发现的。如果 M11 一开始就有
  "注入预览"这个出口，写 `drill` 的时候就会看见。

## 六、留给 M13 的话

1. **装配直接用 `it.raw_text`**，走 `format_event(e, depth, body=...)`。
   不要自己再截一次——两处上限不一致时会出现"预算够、注入半句"（D72）
2. **`kw` 档还没人用**。它存在的意义是"预算剩不到 100 时的退路"，
   M13 的裁剪要给这条退路，否则它只是一段没人走的代码
3. **`memory_tokens=600` 现在只用了 175**（8 条 × 22）。空着 425 token 就是浪费。
   M13 该考虑：装不满时是"多装几条"还是"把摘要写长一点"——
   前者增加召回，后者增加信息密度，是两个不同的方向
4. **pinned 的原文下钻没测过真实场景**。真机库 44 条没有一个 pinned，
   `test_pinned_drills_without_detail` 是造出来的。M13 之前要造几条 pinned 数据
