## 一、开工前先测了分布

手册要求"key 用固定词表（约 40 个）"。这 40 个不能由我列——M7 的教训是
先把现状量出来。`tools/probe_facts.py` 跑 8 个窗口，看模型自己写什么：

```
模型输出 fact 11 条，落库 11 条
key 分布：
  居住城市 1   通勤 1   宠物 1   饮食忌口 1   作息 1   房贷剩余年限 1
  工作单位 1   居住地 1   年龄 1   职业 1   健康状况 1
```

两个问题当场暴露：

**① 11 条 fact，11 个不同的 key。** `居住城市` 和 `居住地` 同时存在，
都指向"住哪"，但系统把它们当两件事。用户搬到上海，只会顶掉其中一个，
另一个永远 active —— **同一件事有两个当前值，比没有事实更糟**。

**② 值是句子，不是值。**

```
饮食忌口 = 吃不了辣（微辣可以，中辣不行）、不喝冰的（胃不好）、讨厌香菜
通勤     = 新家离公司走路二十分钟
宠物     = 养猫（下周出差期间由用户代喂）
```

这种值**无法参与任何比较**。下次用户说"我改坐地铁了"，系统看到
"走路二十分钟"和"地铁"，判不出矛盾，只能并存两条然后随机挑一条喂给模型。
M8.2 的"矛盾检出率"在真机上会一直是 0，而 0 看起来像"用户没改口"。

## 二、key 闭集

`hippo/data/fact_keys.yaml`，30 个 key。每条含 `cn`（给模型看的中文名）、
`card`（single/multi）、`type`（place/org/enum/number/date/text）、`aliases`。

匹配两轮，顺序不能反：

1. **精确**（含别名精确）。`工作单位` 必须落到 `employer`，
   不能被"包含 `工作`"抢去 `occupation`。
2. **包含**。模型爱加修饰词（`房贷剩余年限`、`用户的居住城市`），
   只认最长的别名；两个不同 key 的最长别名一样长就返回 None（有歧义，不猜）。

表外一律拒绝，`action=reject`，`log` 里留 `fact.rejected_key`。
拒绝而不是放行，是因为**放行等于承认 key 可以无限长**：
key 一发散，"住哪"会被拆成十个槽，每个槽只有一条，永不冲突。

`card` 是这个设计里最关键的一列：

| card | 含义 | 例子 |
|---|---|---|
| single | 同实体同时只能有一个值 | city / employer / age / partner |
| multi | 可以并存多个 | diet / hobby / allergy / child |

矛盾检测只在 single 上有定义。"住在哪"只能有一个答案，
"不吃什么"可以有五个。把 diet 设成 single，第二样忌口进来就会顶掉第一样——
那是丢信息，不是更新。

## 三、值归一：这一节真正的坑

手册没写这件事。不做的话，"矛盾检出率"会靠**假矛盾**刷上去：

```
上海 / 上海市 / 沪          同值
字节 / 字节跳动             同值
清华 / 清华大学             同值（去掉"大学"）
三岁 / 3岁                  同值
北京（海淀） / 海淀          不冲突，同一个人的两种粒度
```

按 type 分开处理：

| type | 规则 | 为什么 |
|---|---|---|
| place | 剥行政后缀（省/市/区/县/街道）、括号拆成 facets、简称表（沪→上海） | "上海市浦东新区"与"上海"是粒度，不是搬家 |
| org | 剥机构后缀（公司/集团/大学/学院） | "清华大学"≡"清华" |
| number | 中文数字转 int、去单位 | "三岁"≡"3岁" |
| text | **一个字都不动** | "张伟"和"张伟明"差一个字，是两个人 |

`more_specific` 只对 place/org 开放，用**前缀包含**判定（中文地名和机构名
都是"大在前、小在后"），并且加了一条通名守卫：

```
字节 ⊂ 字节跳动        → 细化，对
北京 ⊂ 北京银行        → 另一家机构，错（remainder 含"银行"→ 不算包含）
王建国 包含 王建       → 两个人，text 类型根本不参与
```

第三条守卫是写的时候临时想到的：没有它，用户从北京银行跳到北京某公司，
系统会判成"还是原来那家，只是说得更细"，`valid_from` 不更新，
"你什么时候换的工作"直接答错。

## 四、六种结局，没有"其他"

判定抽成纯函数 `facts.decide_fact(key, existing, value, confidence)`，
store 只负责执行。这样它能被穷举测试，而不是靠开库试。

| action | 触发 | 后果 |
|---|---|---|
| reject | 空值 / key 不在词表 | 不写，记日志 |
| same | 归一后同值 | 只抬 confidence；**只有更具体时才改写库里的写法** |
| refine | 粒度不同 | 就地换成更具体的，`valid_from` 不变 |
| replace | single 槽值不同且 conf ≥0.6 | 关旧开新，旧值留痕 |
| doubt | single 槽值不同但 conf <0.6 | 不写 facts，问一句 |
| insert | 没有 active，或 multi 槽 | 新开一条 |

`refine` 单独存在是因为它不该被记成"变化"：用户先说我住北京、
后来说我住海淀，中间**没有搬家**。走 replace 的话 `valid_from` 会变成
说海淀那天，"你什么时候搬的家"就答错了。

## 五、约束放进数据库

008 迁移加两列（`card`、`key_raw`）和一个部分唯一索引：

```sql
CREATE UNIQUE INDEX idx_facts_single_active
    ON facts(session, coalesce(entity_id, 0), key)
    WHERE valid_to IS NULL AND card = 'single';
```

三个细节：

1. `valid_to IS NULL` 是部分索引，历史行不参与唯一性。
2. `coalesce(entity_id, 0)`：SQLite 认为 NULL 互不相等，
   不加这个，"用户"的 city 可以插两条。0 不是合法 rowid，不会撞车。
3. 建索引前先清掉已有重复（保留 id 最大的，其余用 `valid_to` 关掉而非删除）。
   删是"这段记忆不存在过"，关是"历史仍可查"，两者不能混。

`card` 是从 YAML 抄下来的冗余列。冗余换来的是**约束能被 SQLite 执行**，
读的时候也不依赖 YAML 在不在。

## 六、验收

| # | 手册验收 | 预期 | 实测 | 结论 |
|---|---|---|---|---|
| 1 | 同值幂等 | 仍 1 条 active | `test_same_value_is_idempotent` + `test_multi_key_dedup` | 达标 |
| 2 | 异值触发矛盾流程 | 旧条 valid_to 非空 | `test_different_value_closes_old` | 达标 |
| 3 | 未知 key 被拒 | 降级为 event | `action=reject`，库里 0 条（见 §八.1） | 达标（有保留） |
| 4 | key 表可控 | 实际使用 ≤40 | 表 30 个；真机 16 个不同 key，越界 0 | 达标 |
| 5 | （新增）值不许是句子 | — | 真机平均值长 3.5 字，>12 字 0 条 | 达标 |
| 6 | （新增）同槽不许两个 active | — | 真机 0 例；有数据库索引兜底 | 达标 |

真机结果（`tools/eval_m8.py`，14 窗口）：

```
模型 mimo-v2.6-flash  窗口 14  耗时 156.3s  成本 ¥0.026084
模型输出 fact 28 条   落库 28 条（active 28 / historical 0）
key 分布 {'diet': 4, 'district': 3, 'commute': 3, 'city': 2, 'employer': 2,
          'age': 2, 'health': 2, 'mortgage': 2, 'occupation': 1, 'hobby': 1,
          'sleep': 1, 'pet': 1, 'pet_name': 1, 'pet_age': 1, 'partner': 1, 'child': 1}
表外 key：无
平均值长 3.5 字   超 12 字 0 条   句子级 0 条
重复 active：无
```

改前 8 窗口 11 条 fact / 11 个 key / 平均 20+ 字；改后 14 窗口 28 条 / 16 个 key / 3.5 字。
**fact 密度提高了，key 的种类反而收敛了。**

## 七、成本

prompt 里多了一张 30 行的 key 表（约 300 token），在固定前缀里，
命中缓存后按 ¥0.02/M 计，每次调用约 ¥0.000006。可忽略。
单窗口成本 ¥0.00186（M7 是 ¥0.00188），没有变化。

## 八、这节没做到的

1. **"未知 key 降级为 event"这条其实没有"降级"动作。** 事实和事件是同一批
   抽出来的，key 被拒时那条事件早就在了——不会丢信息，但也没有"转成事件"
   这一步可以观测。我在报告里把它写成"拒绝 + 事件本就在"，不假装做了降级。
2. **`card` 的默认值是 single。** 老库里的 diet 记录会被暂时当 single 处理，
   如果同一实体同一 key 已经有多条 active，迁移会关掉旧的。
   目前没有真实老库，风险为零；有了之后要按 key 回填 card。
3. **key 表是"够用"不是"够全"。** 30 个覆盖了语料里出现的 16 个，
   但"收入""车牌""星座"这类没进表，会被拒。
   扩表是改 YAML，不改代码——这是故意的。
4. **值长度只靠 prompt 约束。** 代码层不做截断：截断会造出半句话，
   比长句子更糟。真机上 0 条超 12 字，但换个模型可能就破了。
