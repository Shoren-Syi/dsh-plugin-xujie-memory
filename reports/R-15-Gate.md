## 二、这一轮最重要的三个数

### 1. 手册的相似度公式在任何阈值下都分不开两类样本

在 40 个候选对内（30 应合并 / 10 禁止合并），打分分布是**交错**的：

```
应合并 30 对：min 0.12   中位 0.30   max 1.00
禁止   10 对：max 0.20   中位 0.15
              ↑ 重叠区 [0.12, 0.20]
```

| 阈值 | 命中应合并 | 误报禁止 |
|---|---|---|
| 0.75（手册） | 6/30（20%） | 0 |
| 0.34（低到荒谬） | 12/30（40%） | 0 |

**这不是"阈值定高了"，是公式没有分辨力。** 降到 0.34 也只能拿回 40% 的召回，
再往下降误报就会起来。改判据（覆盖率 + 小样本要求完全包含）之后同一份数据
重复率压到 4.9%、误合 1.4%。

### 2. 时间窗 7 天只够跑出 31%

| 时间窗 | 话题内已合并对 | 跨话题簇 |
|---|---|---|
| 7 天（手册） | 31% | 0 |
| 15 天 | 49% | 2 |
| **30 天** | **53%** | 2 |
| 60 天 | 53% | 2 |

30 天是饱和点，不是随便放宽。手册那句"时间差 <7 天"会让近一半的话题被切断
（16 个话题里 7 个跨度超过 7 天，最长 28.2 天）。

### 3. 误合并全部来自弱判据，不在强判据

同一份 142 条内存数据，做一次受控 A/B（只跑强判据 vs 两层都跑）：

```
只有强判据（cov_strict）：9 簇，合并 13 条，跨话题簇 0
加上弱判据（kw_cov）    ：14 簇，合并 23 条，跨话题簇 2
```

（这组数走的是内存里的 `DupRow`，用来隔离变量。全链路的 §一 那组
4.9% / 1.4% 走 SQLite，关键词经过一遍 `clean_keywords`，簇数会差一两个，
不影响结论。）

两处跨话题簇的 `strong` 都是 `False`，`score` 都是 0.00。也就是说：
**强判据一次都没合错，错的全是弱判据放行的。** 这条对 M16/M17 有用——
如果以后要收紧，收弱判据（`CHAR_THR`）比动强判据有效，代价也更清楚。

## 三、`CHAR_THR` 的取舍曲线：没有一档能同时达标

| CHAR_THR | 合并后重复率 | 跨话题误合 | 判定 |
|---|---|---|---|
| **0（默认）** | **4.9%** | **1.4%** | 重复率 ✓ 误合 ✓ |
| 0.10 | 5.6% | 1.4% | 重复率 ✗ |
| 0.25 | 8.5% | 0.7% | 重复率 ✗ |
| 0.35 | 9.2% | 0.7% | 重复率 ✗ |
| 0.50 | 9.2% | 0.0% | 重复率 ✗ |

严格讲，0 这一档两个 DoD 都过了（4.9% < 5%，1.4% < 2%）。但它**贴着两条线上限**，
误差一点就掉出去。而提高门槛立刻让重复率超标——这说明当前构造正好卡在
词面方法的边界上，不是"还有余量可以调"。

默认 0 的理由是成本不对称：

- 重复率是**每轮都在付**的成本（多占 prompt 名额），且不可撤销。
- 误合并是一次性的，且 `hippo unmerge` 能撤销。

旋钮留在代码里，注释里写清曲线和"想更保守调到 0.25"。

## 四、几个口径必须在收口处说清

### 1. 「体积降 ≥20%」在小库上考的是 schema 开销

空库（0 条事件）就有 **220KB / 55 页**——全是 schema、索引、触发器。所以:

```
可降比例的上限 = 1 - 220KB / 总体积
```

- 120 条 / 308KB：上限 28.6%，实测 -26%（贴上限）
- 200 条 / 332KB：上限 33.7%，实测 -27.7%
- 真机库塞 300 条短文本 / 344KB：只降到 290KB（-15.5%）

手册预期结果里那个 `142MB → 108MB`（-24%）才是这条线设计的规模。
**看归档效果应该看"活数据降了多少"，不是文件降了多少**——`hippo stats --disk`
现在三个数一起报（活数据 / 空闲页 / 归档库）。

### 2. 归档是物理搬走，跨库自动召回**不做**

手册 M15.3 自己前后矛盾（先说要 DELETE，又说标 `archived=1` 只留瘦身版）。
后者在 schema 上做不到：`raw NOT NULL` + `CHECK(length(raw)>0)` + `trg_events_raw_immutable`。

选物理搬走，并把「归档事件仍可检索」落成**显式询问** `recall --deep`，
而不是每轮自动 ATTACH 归档库。理由：让 99% 的查询为 1% 的可能性付磁盘 IO 不划算。

### 3. `recall_count` 取 max 不取 sum（手册写的是"簇内总和"）

求和等于把"啰嗦"当"重要"：一句忌口说了 8 次、合并后 `rc=8`，半衰期直接顶到
×2.25 上限；而真正重要的事往往只说一次（"我妈确诊了"），拿不到任何加成。

## 五、真机库的误合并：一处仍在，但结论是可接受

44 条扫出 6 簇、合并 9 条，5 个"禁止合并"对全部挡住。但有一簇是错的：

```
[3] 强  3:答应了，但我其实有点怕猫，从小被挠过一次
        2:近多了，走路二十分钟。对了老王说他下周要去深圳出差，让我帮他喂猫
       39:老王倒是无所谓，他常飞
```

三件事：我怕猫 / 帮老王喂猫 / 老王常飞。被合在一起，起因是共享"老王""猫"。

**查过治不治得了，结论是治不了：**

- **df 门控是负收益。** 真证据恰恰是高频词——模拟数据里真合并共享的
  "搬家"df=3、"海淀"df=4；而误合并共享的"忌口"df=2，比它们都"稀有"。
  按 df 把高频词判成泛词，会把真证据一起废掉。
- **实体词表也不行。** 这里共享的是"老王"（真人名）和"猫"，在任何词表里都不是泛词。
- **强判据没参与。** 这条簇是强的（`cov_strict=0.67`），因为 2 号原文里
  "帮我喂猫"和 3 号"我怕猫"确实共享 `猫` + `老王` 两个词、且 3 词里共享 2 个。

能治的只有"原文语义"，那就要模型参与聚类——成本从 ¥0.003/轮 变成每轮几十次调用。
按约束⑤（成本必须低），不做。

**实际损失有多大，量过了：** 摘要重生成会把三件事如实分开写：

```
"因老王下周去深圳出差而答应帮他喂猫，虽怕猫且小时候被挠过一次，
  但猫离得近走路二十分钟；老王对此无所谓，他常飞。"
```

三件事都在，没有失真，只是挤在一条记忆里。而且 `hippo unmerge --id 3` 一键拆开。
所以判定：**这是效率损失，不是信息损失**，可接受。

## 六、留给 M16 的三句话

1. **摘要质量已经够用了，别在 M16 里再动它。** 6 簇均分 4.5、零编造，
   扣分项都是"读起来不干净"（代词不清、有冗余），不是"写错了"。
2. **误合簇的摘要会误导注入，但方向是"多给"不是"给错"。** 上面那簇在 hot 档
   注入 60~90 token 时会把三件事挤在一段里，读起来像一件事。M16 按 tier 分档时，
   如果发现某条记忆的摘要里出现了多个不相关的主语，宁可降一档用关键词形式注入。
3. **`recall_count` 的口径改过了（max 不取 sum），M16 的排序如果用到它，
   要知道它代表"最多被想起过几次"，不是"一共被想起过几次"。**

另外，M14-Gate 留给 M15 的五条交代，第 1、2 条已落实（`recall_count` 用 max、
归档不按 `last_access` 裸判 NULL），第 3 条**垃圾实体**（27 个里 13 个是
`用户~6\x1f6` 这种合并残留）仍未处理——M15 按词面聚类不按实体聚类，没撞上，
但 M16/M17 只要往实体维度走就会撞上，届时优先处理。
