## 3. 关键实现决策

**1. 请求体不做 `model_validate` 再 `model_dump` 往返。**
Pydantic 往返会丢未知字段顺序、把 `None` 显式化、把 tuple 变 list——任何一个字节的变化都会让 DeepSeek 的**前缀缓存失效**（命中价约为未命中的 1/10）。
所以流程是：`json.loads` 原样读 → Pydantic 只做**校验**（不改写）→ 转发时对原始 dict 序列化。

**2. `extra="allow"` 是硬要求。**
客户端会带 `logit_bias`、`response_format`、`reasoning_effort`、各种私有扩展。少一个就 422，用户的第一反应是"这东西坏了"，而不是"我传错参数了"。

**3. api key 三级优先：请求头 > 配置 > 环境变量。**
请求头优先，是因为一个代理可能被多个客户端共用；各用各的 key 才不会被别人的额度串走。

**4. `/health` 的 SQL 放进 DAO。**
`Store.ping()` 而不是在路由里写 `conn.execute("SELECT 1")` —— M1.3 有一条静态检查守着"SQL 只在 core"，我第一次就是被它拦下来的。

## 4. 遗留问题

| # | 问题 | 影响 | 处理 |
|---|---|---|---|
| 1 | 非流式响应整包读进内存 | 大响应（>10MB）会占内存 | 角色对话不会到这个量级；M28 若做批处理再改流式转发 |
| 2 | 上游 `Retry-After` 等响应头未回传 | 客户端自己重试的退避策略会失效 | M24 心跳/重试时统一处理 |
| 3 | `X-Hippo-Session` 被显式排除在透传之外 | 若用户恰好用同名头给上游传业务数据，会被吞 | 名字可配；冲突概率极低 |
