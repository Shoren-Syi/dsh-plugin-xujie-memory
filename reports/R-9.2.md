> 里程碑：M9.2
> 日期：2026-11-05
> 数据：`tests/test_m9_2_timefilter.py`（21 例）
> 结论：**达标**，但改了一处手册的写法（D61），并顺带修了两个

## 一、三件事，不是一个 WHERE

这一节看着像"加两个条件"，实际要同时成立三件互斥的事：

| 要求 | 冲突点 |
|---|---|
| 默认只给还有效的 | 但历史值不能删，也不能默认出现 |
| 历史查询要能返回历史值 | 而 M8 真机语料里 `historical` 是 **0 条**，这条路没被日常覆盖 |
| "最近"要能过滤 | 但"老王最近怎么样"里的"最近"是问候语，不是时间条件 |

第二条最危险：**0 条历史数据意味着这条路径是死代码**。不写测试，它上线时就是坏的，
而坏了之后表现是"你以前住哪 → 不知道"，用户会认为它没记住，不会认为它查错了。

## 二、区间重叠，左闭右开

事件可能是区间（"去年冬天搬走了" = `[2025-12-01, 2026-03-01)`）。
判断命中不能用包含，要用**重叠**：

```sql
e.event_time < :t_end
AND MAX(COALESCE(e.event_time_end, e.event_time + 1), e.event_time + 1) > :t_start
```

三种写法各自会错在哪：

| 写法 | 错的场景 |
|---|---|
| `e.event_time >= t_start` | 区间事件的起点在查询区间之前就漏了 |
| `e.event_time BETWEEN t_start AND t_end` | 跨年事件（冬天）整体漏掉 |
| `e.event_time <= t_end` | 右端闭区间，3 月能命中"去年冬天" |

`MAX(...)` 那层处理零长区间：`event_time_end == event_time` 时，
`end > t_start` 恒假，事件从此不可检索——**一条在库里、但永远捞不到的记忆**。
模型给个点不给区间时就会写成这样，`test_zero_length_span_still_matches` 守它。

## 三、D61：把"最近"从硬过滤里摘出来

手册 M9.2 写：

> 命中"最近/这周/上个月" → 加 `event_time >= ?`

实测这条会错杀。真机库里：

```
问：老王最近怎么样
库：老王辞职了（2026-08-01，三个月前）
```

按 `[今天-30天, 今天)` 过滤 → 候选 0 条 → AI 答"不记得他近况"。
而库里明明有，也正是用户要问的那件事。

问题是这句话里的"最近"根本不是时间条件，是**问候语**——
"最近怎么样"和"吃了吗"是同一类句子。

**决策 D61：把有边界的和没边界的分开。**

| 词 | 有没有边界 | 处理 |
|---|---|---|
| 昨天 / 上周 / 上个月 / 去年冬天 / 2025年12月 | 有，`parse_span` 能算出区间 | 硬过滤（AT 模式） |
| 最近 / 这几天 / 这阵子 / 刚才 | 没有，30 天是拍的 | **只记 `soft_since`，交给 M10 加权** |

这不是"放宽标准"，是承认"最近"和"上个月"本来就不是一类东西。
手册把它们并列写，是个粗糙的地方。

```
test_recent_does_not_hard_filter      最近 → 三个月前的事件仍在候选里
test_explicit_month_still_hard_filters 上个月 → 照旧硬过滤，对照组
```

对照组是必须的：没有它，下次有人把 RECENT 也关掉，测试照样全绿。

## 四、言说动词：唯一一类"错杀且下游无法补救"

```
我上周说要搬家那事
  ├─ 时间词"上周" → 区间 [10-26, 11-02)
  ├─ "搬家"发生在 8 月
  └─ 按区间过滤 → 搬家事件不在候选集 → 关键词"搬家"再准也只能在候选集内排序
```

实体过滤错过，还能靠关键词兜；时间过滤错过，**下游一点办法都没有**。

判据：时间词前后 4 个字内出现"说/讲/聊/问/提/谈/告诉/回复/答应"，
这个时间词就是在修饰"说"这个动作，不是事件时间，不做过滤。

窗口取 4 是因为"我上周跟老王说要搬家"里，"说"离"上周"隔着 3 个字。
取 6 会开始误伤"上周去医院复查甲状腺"（"查"不在动词表里，但"问"在"问候"里）——
所以动词表里刻意没有收"查""看"这种既可以是言说也可以是动作的字。

## 五、facts 分支：我在这里改过一次主意

`l1_facts` 里有个容易写反的地方：按实体过滤时，要不要带上**用户本人**的事实？

第一版写的是"要带"，理由是：用户问完老王，下一句经常是"他离我远不远"。
按这个写了测试，测过了。

真机一跑就露馅：

```
问：老王最近怎么样
返回：18 条 facts
      city=北京  diet=不吃辣  diet=不吃香菜  sleep=晚11点睡早7点起
      occupation=后端开发  pet=猫  pet_name=年糕  pet_age=三岁
      partner=护士  health=甲状腺需复查  district=海淀  age=32
      mortgage=有房贷  child=孩子明年上小学  employer=现公司
      commute=步行  commute=飞机          ← 只有这一条是老王的
```

17 条无关。M13 的记忆预算是 600 token，这一下用掉一半。

**第二版：问谁给谁。** 用户问自己的事时（"我几点睡"）认不出任何实体，
走的是"无实体"分支，那时全部 facts 本来就都会给。所以这个规则是自洽的，
不是"少给了信息"。

留下的测试名从 `test_self_facts_kept_for_entity_query` 改成
`test_self_facts_not_mixed_into_entity_query`，docstring 里写清了这次反复——
下次有人想改回去，得先解释这 17 条怎么塞进 600 token。

`self_entity_ids()` 这个函数留着了：M13 渲染"我"的时候要用它，
但 L1 的过滤不用。

## 六、事故 56：合并实体撞碎了 M8 的索引

写 `eval_l1` 的会话归并时，`merge_entities` 直接抛：

```
sqlite3.IntegrityError: UNIQUE constraint failed: index 'idx_facts_single_active'
```

008 加的部分唯一索引是 `(session, coalesce(entity_id,0), key) WHERE valid_to IS NULL AND card='single'`。
两个"老王"各有一条 `employer` active，合并后成了同一实体的两条 active。

**建索引的时候没想到"合并"这条路**——因为合并是 M7 写的，索引是 M8 加的，
两者中间隔了一个里程碑。

修法不是删一条，是**旧的按 `valid_to` 收尾**：

```python
keep, drop = (src, dst) if src.valid_from > dst.valid_from else (dst, src)
UPDATE facts SET valid_to = <keep.valid_from> WHERE id = <drop> AND valid_to IS NULL
```

删了的话"老王以前在腾讯"永久消失，而历史查询正是要它。

## 七、事故 57：同槽位 trait 也不同文案

修完 facts 又撞：

```
UNIQUE constraint failed: card_traits.entity_id, card_traits.slot
```

M7 的合并逻辑按 `trait` 文案判重，而 007 的索引是按 `slot`。
两个"老王"的 job 槽写着"在字节做后端"和"后端工程师"——文案不同，
判重判成"不重复"，`UPDATE entity_id` 时撞索引。

修法：有 slot 时按 slot 判重，没 slot 时才按文案。
文案取置信度高的那条（用户只看得见一条），证据取并集。

两条都补了回归测试（`tests/test_m7_2_traits.py` 末尾）。

**这两条不是 M9 的 bug，是 M9 撞出来的。** 值得记的是它们的共同点：
都是"后来加的约束"和"先写的迁移代码"之间的缝隙，
而这条缝隙只在"真机上真的发生了合并"时才露出来——单测里没人会去合并两个实体。
