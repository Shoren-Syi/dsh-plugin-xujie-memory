# R-24.3 · 升级判定

**日期** 2026-11-06　**花费** ¥0

## 做了什么

`Escalator`——心跳唯一可能花钱的出口，三道闸全过才放行：

| 闸 | 判据 | 不过时的行为 |
|---|---|---|
| ① 白名单 | reason ∈ `plan / curiosity / user_message` | 返回 `not_whitelisted`，当天记一次 WARNING |
| ② 上下文 | `estimate_tokens(text) ≤ 300` | 按行砍（保留开头），单行超长按字符退 |
| ③ 日上限 | 今日调用 < 10 | 返回 `daily_cap`，当天记一次 WARNING，次日 0 点重置 |

放行后真正发请求时固定 `max_tokens=120`、`temperature=0.8`。

## 关键决定

- **白名单是常量不是配置**。`ESCALATION_REASONS` 写死在模块里，只能由人改。
  放进 yaml 的话，某天会有人加一条 `"summary"`，然后监控图表上多出
  每天 200 次调用，而没人记得是谁加的。
- **闸门不调模型**。`escalate()` 只判"该不该"和"记一笔"，真正的请求由
  宿主传 `call` 进来。好处有两个：测试不需要网；"怎么调"和"能不能调"
  彻底分开，改了调法不会动到额度逻辑。
- **失败不扣额度**。调用抛异常时 `used` 不变——失败了等于没花，
  扣了就变成"越失败越不敢试"，而失败往往恰恰是最需要重试的时候。
- **告警一天一条**。1440 轮 tick 每轮 WARNING 会把日志冲爆，最后没人
  超额这件事。用 `session_state['_sys']['hb_warned:<day>:<tag>']` 去重。
- **额度按自然日 reset**，不按"距上次调用 24 小时"。后者会让额度在一天里
  缓慢漂移，最后"今天还能调几次"没人算得清。

## 验收对照

| # | 要求 | 结果 |
|---|---|---|
| 1 | 只有白名单能升级 | 三个 reason 全放行；`summary/tick/consolidate/improve/空串` 全拒 |
| 2 | 单次 ≤300 token 输入 | 60 行 × 约 100 字压到 ≤300；5000 字单行同样压下来 |
| 3 | 日上限生效 | cap=10 时第 11 次返回 `daily_cap`；次日恢复 |
| 4 | 超额有日志 | WARNING 恰 1 条（6 次拦截），标记落库可查 |

## 一个副作用要记住

`Escalator` 目前**没有接进 `tick()`**。这是刻意的：M24 阶段没有任何
"该主动说话"的场景（计划是注入不是播报，好奇是 M25）。等 M25 接上
好奇发言时，调用路径应该是：

```
tick ⑥ curiosity → 额度够 → Escalator.escalate("curiosity", ctx, call=...)
```

而不是在 `tick()` 里直接 `await llm(...)`。这条留给 M25 的人看。
