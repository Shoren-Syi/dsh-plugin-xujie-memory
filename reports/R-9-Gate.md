## 二、这一节交付了什么

`hippo/core/retrieve.py`（约 330 行）+ `store.l1_filter` + `store.supersede_event`：

```
parse_query(text, session, store) -> Query(实体 / 模式 / 区间 / 信号)
l1_candidates(store, session, query) -> L1Result(ids / truncated / elapsed)
l1_facts(store, session, query)      -> list[Fact]
```

`Query` 是一个可以缓存的值——M12 话题切换要在"同一句话问两次"时复用解析结果，
所以它必须是无副作用的纯数据，不能拿着 store 不放。

CLI 三档：

```bash
hippo recall "老王最近怎么样" --explain   # 只解释这句话被读成了什么
hippo recall "老王最近怎么样" --l1        # 跑分类层，看砍到多少条
hippo recall "老王最近怎么样"            # L1 + 关键词（M10 雏形）
```

## 三、最重要的发现：L1 的压缩全靠实体

真机 21 条查询里，**只有 5 条认出了实体**：

| 查询 | 实体 | 候选 | 压缩 |
|---|---|---|---|
| 老王最近怎么样 | 老王 | 7 | 84% |
| 老板骂我那次 | 老板 | 2 | 95% |
| 我老婆是做什么的 | 老婆 | 1 | 98% |
| 小李怕坐什么 | 小李 | 4 | 91% |
| **我几点睡** | **无** | **44** | **0%** |
| **我能吃辣吗** | **无** | **44** | **0%** |
| **我在哪上班** | **无** | **44** | **0%** |

"我几点睡""我吃辣吗""我在哪上班"——这些是用户最常问的一类问题，
而它们一句都压缩不了。原因是库里**没有"我"这个实体**：
M7 建实体时只建"老王""年糕""老板"，用户本人不是实体。

后果不是"慢"（44 条也快），是 M10 拿着 44 条候选去做关键词排序，
等于没有分类层。**L1 在这些查询上是空转的。**

两条路，都没在这轮做：

1. **建 self 实体**（推荐）。`entities` 里一条 `canonical='用户', type='person'`，
   所有涉及用户本人的事件都挂上它。改动小（M7 的 `resolve_entity` 加一个特例），
   收益是所有"我……"的查询立刻能砍到"用户本人的事"。
   风险是它会变成"超级实体"——用户本人参与的事件本来就是大多数，
   压缩率可能只有 50%，而不是 95%。
2. **不建，靠 M10 的关键词倒排**。44 条候选做关键词匹配本来就够快，
   分类层在这里没有增量价值。

先按 2 走，M10 的 50 条标注查询跑完，看 top-8 命中率。
如果"我……"类查询的命中率明显低于"老王……"类，再回来做 1。
**现在做 1 是凭感觉，M10 跑完再做是有数字的。**

## 四、顺带撞出来的两个索引冲突

`merge_entities`（M7）与后加的两个唯一索引（M7.3 的 `idx_traits_slot_active`、
M8 的 `idx_facts_single_active`）不兼容，一合并就抛 `IntegrityError`。

- 事故 56：facts 同 key 两条 active → 旧的按 `valid_to` 收尾，不删
- 事故 57：traits 同 slot 不同文案 → 按 slot 判重，文案留置信度高的

两条都补了回归测试。**共同点是"后加的约束"与"先写的迁移代码"之间的缝隙**，
而这条缝隙只在真机上真的发生合并时才露出来——单测里没人会去合并两个实体。

## 五、跨会话实体分裂（缺陷 22）的现场

`eval_l1` 第一次跑出来候选 = 全库，压缩率全线失败。原因：

15 个窗口是 15 个 session，而 `entities` 是 `UNIQUE(session, canonical)`，
同一个"老王"在 narrative 和 multiperson 里是两条记录。
在 multiperson 会话里问"老王最近怎么样"，实体认不出来 → 不加实体条件 →
**返回该会话全库，而且不报错**。

评测装置里加了一次会话归并（合并 13 个重复实体）才量出真实的 2.5%。
这说明缺陷 22 不只是"角色卡有重复"，它会**让检索静默退化**。
M12（话题切换）会直接踩到，M15（长期摘要）会更严重。

## 六、留给 M10 的三句话

1. **kw_index 是唯一能命中 2 字中文词的通道。** L1 把候选压到 7 条之后，
   在这 7 条里做关键词匹配，"老王""年糕""香菜"这些词能不能命中，
   全看 M6.1 的清洗规则留没留下它们。
2. **`soft_since` 还没人用。** L1 只负责把它算出来，M10 的排序要真的拿它加权，
   否则 D61 就只是"少了一个过滤条件"，而不是"多了一个排序信号"。
3. **候选里没有正文。** `L1Result` 只有 id，M10 要自己 `get_events()`。
   别在 L1 里顺手把 raw 带出来——那不是快，那是让 L1 的耗时从 0.94ms 变成 3ms，
   而 M13 pack 之后这个数字会被乘以每轮调用次数。
