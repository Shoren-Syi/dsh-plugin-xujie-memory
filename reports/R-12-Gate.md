## 二、这一轮唯一的实质发现：**词面判据判不了话题**

手册给的 Jaccard，在 99 轮真实对话上恒为 0。不是实现错了，是语言：

```
"老王不是让你帮他喂猫"  →  {喂猫, 老王}
"对，他下周去深圳出差"  →  {深圳, 出差}      用户说"他"，不重复"老王"
```

换成覆盖率（分母只算本轮）后有了区分度，但误触发 26%——那 18 条全是
**同一话题的新侧面**：

```
"我搬家了"     →  "房租涨了多少"
"房租涨了两千" →  "那边通勤怎么样"
```

一个共同的词都没有，但是同一件事。这是对话的本质：**每一句都在给新信息**。

四种判据都试过了（Jaccard / 覆盖率 / +指代省略 / +共现扩展），
**都在 45% 附近停住**。这不是调参能到的地方。

所以我的判断是：**M12 的能力边界就是"高召回、中精度"**。它保证不漏
（13%），代价是 45% 的轮次会重新检索。而检索本身只要 0.4ms、0 token——
钱花在"注入"上，那由 M13 管。

68 值得单独说：那条测试是 M1 写的，六百多个测试跑下来第一次红。
它拦住的正是"为了方便，顺手在业务层写条 SQL"——**这种滑坡在任何项目里
都会发生，区别只在于有没有一道测试在门口站着**。

## 四、这一轮的账

- 两节实现 + 一节标定，614 测试全绿，9 项验收 7 项达标
- **最大的产出是量出"词面判据的天花板"**，而不是"调出一个好看的阈值"。
  这件事必须在 M13 之前知道——如果 M13 按"触发率 27%"设计缓存预算，
  上线后发现实际 45%，成本模型会直接崩
- 一条没做的事：**没有为了让表好看去改 fixture**。标注错了 1 条（属于
  修数据），判据一条没动
- 新增 `session_state` 表，M13 的 pack 复用、M18 的存疑冷却都要用

## 五、留给 M13 的话

1. **45% 的触发率不等于 45% 的成本**。M13 必须做**结果级复用**：
   新检索出的 8 条和上次的 8 条重合度高 → 直接复用上次的字节，缓存命中。
   这是唯一不看语义、只看事实的判据
2. **`save_keywords` 必须在 pack 之后调用**，否则下一轮永远 `cold_start`，
   每轮全量检索 + 缓存全废。这是 M13 最容易漏的一步
3. **`tr.deep=True` 时要调 `drill`**。M12 只给信号，M11 才拉原文，M13 负责串起来
4. **`memory_tokens=600` 只用了 175**（M11 量的）。剩下 425 token 是空着的，
   M13 要么多装几条，要么把摘要写长——这是两个不同的方向，先量再选
