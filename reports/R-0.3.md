## 3. 关键数据

| 指标 | 值 |
|---|---|
| 一条日志的序列化开销 | < 0.05ms（`json.dumps` 短 dict） |
| 写日志是否 flush | 每条 flush（崩溃时最后一条不丢，代价约 0.02ms） |
| metrics 单行写入 | 短线开库 + 插入，约 0.1ms |
| 成本计算（smoke 实测） | ptok=100 / hit=80 / ctok=10 → **¥0.00016** |

成本公式与实测对照：

```
miss = 100 - 80 = 20
cost = 20 × 2.0/1e6 + 80 × 0.5/1e6 + 10 × 8.0/1e6
     = 0.00004 + 0.00004 + 0.00008 = 0.00016   ✅ 与落库值一致
```

## 4. 与手册的三处偏差

| 偏差 | 原因 |
|---|---|
| 不用 `TimedRotatingFileHandler`，自写 `DailyFileHandler` | 它的 `namer`/`suffix` 只作用于**归档**文件，当前文件永远叫 `hippo.log`，与手册约定的 `hippo-YYYYMMDD.jsonl` 对不上；且跨天依赖定时器，进程被 kill -9 时切分点不确定。自写 40 行后行为完全可预测 |
| 不用 `respx`，改用 `httpx.MockTransport` | respx 是额外依赖，而 MockTransport 是 httpx 自带的 transport 钩子，能力等价。少一个依赖 = 少一个版本冲突源 |
| `t0~t3` 存毫秒，`metrics.ts` 存秒 | 毫秒是为了看清"组包到底花 1ms 还是 200ms"（秒级精度全是 0）；ts 用秒是为了和 events/plans 对得上时间轴。已在 `telemetry.py` 文档注释里写死 |

## 5. 遗留问题

| # | 问题 | 影响 | 处理 |
|---|---|---|---|
| 1 | 日志按天切，但**长期运行的进程**跨天时要等下一条日志才切文件 | 无（下一条日志会立即切） | 已知行为，不修 |
| 2 | cassette 的 key 只取 `model/messages/tools/temperature/top_p/max_tokens/response_format/stream` | 若将来依赖 `logit_bias` 等罕见参数做实验，两盒不同请求会撞 key | 撞 key 时会出现"回放内容不对"，表现明显；M5 若需要再加字段 |
| 3 | 录制文件按 messages 哈希命名，**prompt 一改全部失效** | 调 prompt 时必须重录 | 这是刻意的：逼人看一眼新 prompt 的输出，而不是拿旧结果自我安慰 |
