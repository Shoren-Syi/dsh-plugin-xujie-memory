# R-10.2 排序与截断

> 里程碑：M10.2
> 日期：2026-11-05
> 数据：`tests/test_m10_2_rank.py`（15 例）、`tools/eval_retrieve.py`（50 条标注 + 20 条留出）
> 结论：**达标**。标注集 hit@8 = **0.96**，留出集 **0.95**，手册要求 0.85。
> 但这两个数必须和对照组一起看：**只按 weight 排也有 0.38**。

---

## 一、为什么必须先有一个对照组

手册的 DoD 是"50 条人工标注查询，top-8 命中率 ≥85%"。

这句话单独看没有信息量。一个"按 weight 取前 8"的实现，在这份语料上
能到 0.38——因为语料是 15 个窗口的真实对话，**用户反复提到的就是重要的事**，
weight 排序本身就有一定命中率。

所以 `eval_retrieve.py` 带 `--naive`：

```
L2：       hit@8=0.96  mrr=0.87  avg_tokens=96   降级 2/50
对照组：   hit@8=0.38  mrr=0.16  avg_tokens=160
```

**差的那 0.58 才是关键词检索的贡献。** 如果哪天 L2 掉到 0.60，
而对照组还是 0.38，说明关键词层坏了；如果两个一起掉，
说明语料或 L1 候选集变了。分开看才知道该修哪里。

## 二、打分：为什么不用"本次结果内归一化"

**决策 D63：`kw_score = 1 - 0.5 ** hit`，不是 `hit / max_hit`。**

手册写的是 `0.55 × normalize(kw_hit)`。如果 `normalize` 指"除以本次命中的最大值"，
同一条事件在不同候选集里会得到不同分数：

```
查询 A 命中 {3, 3, 3}   → kw 分都是 1.0
查询 B 命中 {3, 3, 1}   → 前两条 1.0，第三条 0.33
```

更要命的是**不可复现**：候选集稍微变一点（cap 从 800 调到 801），
排序就可能翻。测试写不了，M26 调参也建立不起因果——
"把 weight 权重从 0.25 调到 0.30，命中率变了 2 个点"，你没法知道是不是噪声。

饱和函数只依赖这一条事件自己：

| hit | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| kw | 0.50 | 0.75 | 0.875 | 0.9375 |

代价是"命中数和相关性不是线性关系"。但那本来就是对的：
命中 3 个词和 4 个词的差别，远小于 0 个和 1 个的差别。

## 三、四因子 + 一项

```
score = 0.55 × kw_score
      + 0.25 × weight
      + 0.10 × recency       # 0.5 ** (age_days / half_life[tier])
      + 0.10 × pinned
      + 0.05 × in_recent_window
```

前四项是手册给的。第五项是 M9 留下的活。

### 第五项：D61 的落点

M9 的 D61 把"最近"从**硬过滤**降级成**软信号**：用户问"老王最近怎么样"，
老王三个月前辞职那条不能被砍掉（那正是要回答的事），但也不该和一年前的事同权。

M9 只负责算出一个 `soft_since` 并挂在 Query 上，**没人用它**。
如果 M10 也不接，那 D61 的净效果就只是"少砍了一批候选"——
用户问"最近"和问"以前"会拿到同样的 8 条，只是顺序偶然不同。

所以这里把它做成一个独立的正向项：事件时间 ≥ `soft_since` 得 0.05。
权重小是刻意的：它只该在**其他条件打平**时起作用，不该盖过相关度。

测试 `test_soft_since_actually_changes_ranking` 守着这条。

### recency 的未来事件

抽取器会把"孩子明年上小学"记成 2027 年，`event_time > now`。
这里算 `age_days = max(0, now - event_time)`，即未来事件的新近度是 1.0。
不在排序层再罚一次——"时间不对"这件事 M8.3 已经用 `time_guessed` 标了，
排序层没有资格再判一次，否则同一个错误会被罚两遍。

## 四、截断：两层预算，装填不是 break

```
单条 ≤ 80 token      （RankCfg.summary_max_tokens）
总 ≤ 360 token       （PackCfg.memory_tokens 600 × 0.6）
```

360 而不是 600：手册要求"总 token 不超 memory_tokens × 0.6，剩下留给 raw"。
剩下的 240 是 M11 原文下钻的预算。

**装填遇到装不下的长条目时是 `continue`，不是 `break`。**

这条看着琐碎，但 break 的后果很具体：前 3 条都是 200 token 的长摘要时，
第 4~8 个位置全空——而库里还有几十条 20 token 的短记忆可用。
`test_short_entries_fill_in_when_long_ones_do_not_fit` 守这条。

### 摘要截断按标点断

`_clip()` 用二分找"估算 token 不超标的最长前缀"，然后**回退到最近的标点**
（只在标点位于 60% 之后时回退，否则回退太多）。

不回退的话，"…他辞职了因为"这种半句会被当成完整信息喂给模型，
而模型会顺着这个半句编。这是"摘要截断"最贵的错误——
它不是少给信息，是给了一条**读起来完整但意思反了**的信息。

## 五、pinned：不受预算约束

```
for it in [pinned...] + [其余...]:
    if it.pinned: 直接装，不检查预算
    elif used + it.tokens > budget: continue
```

钉住的不是"更重要的记忆"，是用户明确说"这个必须记得"的东西。
预算不够时该挤掉的是别的，不是它。

代价：用户钉了 10 条 200 token 的记忆时，这一轮会超预算。
接受——但这种情况下超预算是用户的显式选择，而不超才是 bug。

## 六、降级：关键词 0 命中时按 weight 兜底

M9 量出来 21 条真机查询里 16 条认不出实体。其中"我几点睡""我吃辣吗"
这类连关键词都命中不了（库里存的是"晚11点睡""不吃辣"）。

如果 L2 返回空，AI 只能说"不记得"——而事实就在库里。

所以命中为 0 时按 `weight DESC` 从 **L1 候选集**里取（不是全库）。
不是"降级"，是承认这次没找到线索，那就按重要性给点东西。结果上标
`degraded = "no_keyword_hit"`，`recall --explain` 会打出来。

50 条查询里 2 条走了这条路（"我用什么语言写代码"、"被老板骂的时候什么感受"）。

## 七、验收

| # | 手册要求 | 结果 |
|---|---|---|
| 1 | 50 查询 top-8 命中率 ≥85% | **0.96**（对照组 0.38） |
| 2 | 排序确定性，100 次同输出 | ✓ `test_order_is_deterministic_100_times` |
| 3 | token 不超预算 | ✓ `test_token_budget_never_exceeded` |
| 4 | pinned 必进 | ✓ `test_pinned_always_included_even_if_irrelevant` |

**留出集的作用。** 上面 0.96 是在这份标注集上反复调过的（看到失败项后补过
两组同义词）。所以另外写了 20 条查询，跑的时候**不许再改词表**：

```
留出集：hit@8=0.95  mrr=0.75  avg_tokens=106
```

0.96 vs 0.95，差一个点。这是"轻微过拟合但泛化正常"的形状。
如果留出集掉到 0.70，那就说明词表是照着测试集写的。

（诚实记录：留出集跑了三轮。第一轮 0.90，发现问题后改的是**分词器的 bug**
（见 R-10.3 事故 60）和**兜底顺序**（事故 61），没有再动词表。
第二轮 0.90、第三轮 0.95 之间只动了这两处。严格说这已经不是"只跑一次"，
但它改的是实现缺陷而不是测试集答案，信息量还在。）

## 八、剩余的两个失败

| 查询 | 原因 | 归属 |
|---|---|---|
| 我用什么语言写代码 | 库里存 `推荐系统 召回 Go`，"语言"和"Go"没有任何字面或同义关系 | 无法用规则解，需要模型侧的查询改写 |
| 被老板骂的时候什么感受 | L1 实体过滤只给了 2 条候选（"老板"实体），答案（第 12 条）没挂这个实体 | M9 的实体过滤设计，见 R-10-Gate |

第二条值得单独说：**L2 再强也救不了候选集里没有的答案**。
M9 的实体过滤是硬 AND，而抽取器不会给每条含"老板"的描述都挂 `老板` 实体。
这是 M9 的已知边界，M12 话题切换会重新碰到它。
