## 二、DoD 是"逐字一致"，那就逐字比

手册 §5.3 给了三个样例。测试直接把它们的原文抄进断言，一个字符都不改：

```python
assert format_event(_ev(tier=1)) == (
    "[记忆 · 2026-03-14 · hot]\n"
    "关键词：花生 过敏 急救\n"
    "摘要：用户对花生严重过敏，曾过敏性休克送医，随身带肾上腺素笔。")
```

warm 同样逐字对上。**cold 有一处差异，必须说明：**

```
手册：  [记忆 · 2024-06-xx · cold]
实现：  [记忆 · 2024-06 · cold]
```

`xx` 是"不知道具体哪天"的占位符。我们的 `time_precision` 已经是 `month`，
`_fmt_time` 写出 `2024-06`——比写 `2024-06-xx` 更短，也比编一个具体的日子诚实。
这是唯一一处与手册字面不同，差的就是那个占位符本身。

## 三、这一轮真正的产出：把两处渲染合成一处

开工时同一条记忆有两个渲染器：

```
pack._memory_block   →  [记忆 · 日期 · hot]  换行 关键词：…  换行 摘要：…
drill.format_event   →  [原话 · 日期 · 用户] "…"
```

两套并存的症状是**CLI 预览看着对、真进 prompt 的不对**——而且只有把两边
逐字比对才看得出来。这类 bug 的共同点是：不报错、不崩溃，只是慢慢分叉。

现在：

```
format_event(e, summary=…, body=…)   ← 唯一定义处
    ├── pack._memory_block   只负责"排好、加标题"
    ├── CLI 注入预览         同一个函数
    └── drill 下钻           同一个函数
```

`test_pack_block_equals_format_event` 钉这一条：pack 拼出来的 D 段必须
逐字等于 `format_event` 的输出。顺手删掉了 `pack._day`——它是 `_fmt_time`
少了"区间"和"猜测问号"的版本，正是会分叉的那种副本。

## 四、token 预算怎么算：整块，不是正文

M11 的 `max_tokens` 只卡正文。结果是：

```
摘要 80（卡满）+ 关键词 8 个（约 20）+ 头部（约 11）= 111
```

而 hot 的上限是 90。**超出去的正是"包边"**，而且没人记账——L2 那边算
`it.tokens` 用的是裁剪后的摘要，D 段突然变长，预算直接爆。

改成"整块上限"：头部和关键词先记账，剩下的才给摘要。三个连带决定：

### 1. 摘要让位原文

warm 一档 70 token。加一行原文后只剩不到 10 token 给摘要，裁出来是
"用户下周从字…"。半句摘要比没有摘要更糟——模型会以为摘要本身就残缺。
所以规则是：

```python
if room >= (MIN_SUMMARY_WITH_RAW if piece else 10):   给摘要
elif not want_raw:                                    退化成只有关键词
```

有原文时，摘要的额度门槛是 20（约 10 个汉字）；没有原文时是 10。
`test_cold_drilled_gives_raw_not_summary` 钉住冷事件被下钻时的形状：
关键词 + 原文，不给现裁的摘要（"当时怎么说的"问的是原文，给摘要是答非所问）。

### 2. `estimate_tokens` 的 1.3 安全系数要除掉

`estimate_tokens` 故意偏高 30%（宁可高估，见 turns.py 的注释）。它是为
**窗口预算**服务的；而 §5.3 的 60~90 说的是"模型看到的 token"。

直接拿估算值去比 90，hot 档实际只用掉 2/3 的额度——"看起来达标"，
其实一直欠着。所以内容预算统一除以 1.3 再比：

```python
def _real(text): return estimate_tokens(text) / 1.3
```

换算之后三个样例分别是 **65 / 65 / 19**，全部落在区间内。这个换算写进了
模块注释，否则下一个人看到 `_real` 会以为是多余的封装。

### 3. pinned 允许超 90，但不超过 130

手册说"hot 60~90，pinned 再加原文"——这两句本身就意味着 pinned 会超。
所以 pinned 时上限放到 `90 + 40`，多出来的 40 是 `RAW_QUOTE_TOKENS`
（一句引文，不是整段 raw）。

数量上的失控不由这里管，由 M16.2 的 C 段 200 token 提醒兜住。

## 五、对 §5.3 加的一个字段（非用户来源）

§5.3 的头部只有三个字段。用户视角严格照做；但**非用户来源仍然追加**：

```
[记忆 · 2026-03-14 · hot]          ← 用户说的
[记忆 · 2026-03-14 · hot · AI]     ← AI 自己说过的
```

理由是 M11 测试里那句注释：模型要靠来源区分"用户说的"和"它自己说的"。
全去掉之后，"你上次说你想辞职"可能是它自己上一轮的推测，却被当成用户事实。
§5.3 的样例全是用户视角，所以三种格式仍然逐字一致。

## 六、M11 的格式测试整体重写了

17 个失败，全是旧的单行格式断言。**这不是"过时了所以放宽"**，是格式换了。
每条断言原来的性质都还在，只是落点变了：

| 原断言 | 新断言 |
|---|---|
| `· 用户]` 在末尾 | 用户视角头部恰好三个字段，`"用户"` 不出现 |
| `] "正文"` | `原文："正文"` |
| `[关键词 · …]` | `[记忆 · … · warm]` + `关键词：` 行 |
| 换行要拍平 | 块内**每一行**内部不许有换行（块本身是多行的） |

`_fmt_time` 的六种精度、跨年区间、半开边界、问号标记，断言原样保留，
只是去掉了尾部的来源字段。
