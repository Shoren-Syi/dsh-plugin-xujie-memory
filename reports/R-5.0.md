## 1. 为什么插在 M5 之前

M4-Gate 记了两笔债，其中一笔是**会持续污染数据**的：

```sql
-- 001 时代
SELECT id FROM events WHERE entities LIKE '%3%'
```

`entities` 是 JSON 数组文本，`LIKE '%3%'` 对实体 3 的匹配结果是
`3`、`13`、`23`、`30`、`33`、`43` ……

**这不是"查询不精确"，是"记忆挂错人"。** 一旦 M7 角色卡上线，
老王会看到小李的经历，用户会立刻发现，且无法解释为什么。
M5 开始建实体、写事件，正好是这条路的入口——现在不改，后面每条记忆都带毒。

## 4. 性能

| 操作 | 耗时 |
|---|---|
| 200 次重复 `link_entities`（全部被 IGNORE） | 1.6ms（8µs/次） |
| 200 次 `events_of_entity` | 1.2ms（6µs/次） |
| **3000 事件**下反查 limit=200 | **1.87ms** |

最后一行是唯一值得盯的数字。慢在 `ORDER BY e.weight DESC` 的临时排序上：
`idx_ee_entity` 能快速定位 3000 行，但排序要全排一遍。

目前可接受：角色卡是**按需构建**（M7），不是每轮。如果 M14 之后发现它进了热路径，
正确的解法是给 `events` 加 `(session, entity_id, weight)` 覆盖索引，
或者在 `event_entities` 里冗余一份 weight——但那是反范式，等真需要再说。

## 5. 两个设计决定

### 5.1 为什么留 `events.entities` 冗余列

两个真相源必然不一致——这是常识。但我还是留了，理由：

1. `event_entities` 是**真相**，`events.entities` 是**缓存**。关系明确，不是"两个都算数"。
2. 渲染记忆块时要拿"这条事件涉及谁"，走 JOIN 要多一次 IO；走 JSON 列一次 SELECT 就够。
3. 归档导出格式已经定了（M24），改格式等于改归档协议。

代价是必须保证一致性。用触发器保证，不靠调用方自觉——
**"每个写事件的地方都记得同步关联表"这句话，在写了 40 个 DAO 方法之后一定会失效。**

### 5.2 为什么把 `transaction(self.conn)` 全改成 `self.tx()`

M5.3 要求"entities→events→traits→facts→plans→doubts 一个事务写完"。
但每个写方法内部自己就开事务，直接嵌套会报
`cannot start a transaction within a transaction`。

两条路：
- 把 20 个写方法各拆成"带事务/不带事务"两份 → 方法数翻倍，调用方要记住用哪个
- 让事务可重入 → 20 行

选了后者。判据是 `conn.in_transaction`：`isolation_level=None` 时单条语句自动提交，
语句结束后它必然是 False，所以外层没开事务时行为与改动前完全一致。

**这一改动让 138 个旧测试全绿**（只改了 2 条 schema 断言：表多了两张、版本从 1 到 3）。

## 6. 新增：extract_runs

`turns.extracted_at` 只回答"抽没抽过"，回答不了"抽成什么样"。
M5 之后必然被问到的三个问题都需要后者：

1. 成功率多少？（degraded 不算成功）
2. **这个窗口为什么一条记忆都没出？**（空数组 / 解析失败 / 全被锚定校验丢弃——三种完全不同的故障）
3. 钱花在哪了？

用日志也能答，但日志按天滚。这张表几万行才几 MB，能一直留着。

`UNIQUE(session, start_idx, end_idx)` + `ON CONFLICT DO UPDATE`：
同一窗口重跑只留最后一次。不留历史是有意的——重跑通常是为修 bug，
留一堆旧记录反而干扰判断。
