## 一、六段与三个字段

```
[ctx-v73a7]                      ← 版本号（A/B/C 的内容哈希前 4 位）
# 我是谁                          ← A 人设
...
---
# 我认识的                        ← B 角色卡
老王：怕坐飞机；常出差
---
# 一定要记住的                    ← C 钉住
已知：age=32；city=北京；...
---
# 我记得的                        ← D 记忆块
[记忆 · 2026-11-04 · warm]
关键词：搬家 朝阳 海淀 房租
摘要：用户昨天下午从朝阳搬到海淀，房租涨了两千
[原话 · 2026-11-04 · 用户] "我昨天下午搬家了..."
---
[想问] 「那边」指哪里？            ← E 动态
---
[现在 2026-11-05 14:28]          ← 时间锚（永远最后）
```

分隔符固定 `\n---\n`，没有空行，没有随机顺序。

## 二、决策 D81：版本号用内容哈希，不用自增计数器

手册写的是"内容变化时递增 n"。自增要持久化一个计数器，而计数器**一旦丢失**
（换机器、清库、并发写），所有客户端的缓存同时失效，而且看不出来为什么。

改用 `sha1(A+B+C)[:4]`：

- 内容一样 → 版本一样（跨进程、跨重启都成立）
- 内容变了 → 版本变了
- 不需要任何状态

代价：它不是"递增"的，看不出改了几次。但版本号的用途是"观测缓存失效点"，
不是"计数"——真正需要计数时看 git 历史。

**版本号只算 A/B/C，不算 D。** D 段每轮都变，算进去的话版本号每轮都变，
就没法用它观测"稳定段什么时候被改动了"（`test_version_ignores_memory_block`）。

## 三、时间锚的位置：一个我推错过的结论

第一版我把时间锚单独插成一条 system，放在最后一条 user 之前。后来以为
这会"截断历史前缀"，改成并入最后一条 user 的内容里。

**实测两种做法几乎一样：93% vs 94%。**

因为锚无论如何都在"历史之后"——前缀在锚处断开，前面的 head 和历史照样命中：

```
turn N   : head | 历史 1..N | 锚N | userN
turn N+1 : head | 历史 1..N+1 | 锚N+1 | userN+1
                ↑ 到这里都一样
```

真正致命的是把锚放到**最前面**：那会把后面所有内容（head 主体 + 全部历史）
都推出缓存。§5.2 那句话说的是这个。

最终选并入 user：少一条 message，而且"现在几点"紧挨着用户这句话，读起来自然。

这条记在施工记录里，因为**推错的推理过程比结论更值得留**。

## 四、inject 的三条约束

1. **返回新列表，不改调用方对象**。代理那边 `payload` 是从用户请求 `dict()`
   出来的，改它的嵌套结构会影响后续读 `raw` 的地方。
2. **客户端已有 system 时合并，不新增**。两条 system 会让模型不知道听谁的。
   合并后 head 在前、客户端的人设在后——我们的 A 段是"底层设定"，
   客户端的是"这次的角色"，后者更具体，放后面更合理。
3. **注入失败必须能降级**。代理里整段包在 try 里，pack 抛异常就当没装
   （模型照常答，只是不记得事）。**记忆坏了不该让人连聊天都聊不了。**

## 附：一处被改掉的旧测试

`test_m2_1_route.py::test_messages_not_rewritten` 原来断言"转发时 messages
一个字节都不能改"，那是 M2 阶段的约束（当时 pack 是空操作）。

M13 之后必然要改，但**不能改成"随便改"**。新的口径是：

```python
dialog = [m for m in sent if m["role"] != "system"]
assert dialog == [m for m in msgs if m["role"] != "system"]   # 对话逐字逐序不变
assert sent[0]["content"].endswith("你是阿岚。")               # 客户端 system 被保留
```

**允许前置注入，不允许改写对话。** 这条界限比"全都不许改"和"随便改"都难，
但它是唯一正确的——用户说的话被改了一个字，整套系统的可信度就没了。
