# R-11.1 下钻条件

> 里程碑：M11.1
> 日期：2026-11-05
> 产出：`hippo/core/drill.py`（`wants_detail` / `drill`）
> 数据：`tests/test_m11_1_drill.py`（14 例）、`tests/fixtures/drill_queries.jsonl`（100 条）、
> `tools/bench_retrieve.py --layer3-rate`
> 结论：**达标**。判据触发率 **19%**（手册 ≤25%），误触发 2/19，漏检 1/18。
> 但"下钻率 5%"这个数必须和"命中 47 条里 5 条"一起读，见第四节。

## 一、三道闸门，以及为什么第二道最难写

```
1. 排进 top-2         → 排在后面的，用户根本没看它在说什么
2. 用户在问细节       → 没人问细节时拉原文是纯浪费
3. 剩余预算 ≥ 200     → 拉了装不下，等于没拉
```

第 1、3 道是算术，好写。第 2 道是判据，而判据一定会错——
所以这一节真正的活不是"让它能触发"，是**让它少误触发**。

## 二、决策 D69：判据分两档，弱标记要配疑问语境

手册给的是 5 个子串：`怎么说的 / 原话 / 具体 / 细节 / 当时`。

直接子串匹配会把**陈述句**当成提问：

| 输入 | 子串匹配 | 实际含义 |
|---|---|---|
| 当时我不在家 | 命中「当时」→ 下钻 | 在陈述，不要原话 |
| 具体地址我忘了 | 命中「具体」→ 下钻 | 在陈述，不要细节 |
| 细节不重要，结果怎么样 | 命中「细节」→ 下钻 | 在说"不重要" |

这类误触发不报错、不崩溃，只让原文悄悄多拉一次。三条闸门里，
它是唯一会让成本无声上涨的一处。

所以标了两档：

```
强标记（命中即触发）
  原话 / 原文 / 一字不差 / 原原本本 / 怎么说的 / 说了什么 / 具体说 / 详细说 / 展开说

弱标记（要和"这句话在问东西"同时出现）
  具体 / 细节 / 当时 / 怎么说 / 详细 / 展开
```

疑问语境 = 句子里有 `？ 吗 呢 什么 哪 几 多少 怎么 为什么 是否 有没有 告诉我 说说 讲讲`。

"告诉我原话"命中的是强标记，不需要疑问词；"具体地址我忘了"两样都不沾。

### 100 条上的结果

`tests/fixtures/drill_queries.jsonl` 是手写的 100 条口语：

| 类别 | 条数 | 说明 |
|---|---|---|
| 明确要细节（强标记） | 10 | "把我说过的原话给我" |
| 弱标记 + 疑问 | 8 | "当时是什么情况" |
| 陷阱：陈述句带弱标记 | 12 | "具体地址我忘了" |
| 普通事实提问 | 40 | "我搬到哪了" |
| 寒暄/无关 | 15 | "嗯嗯" |
| 补充事实 | 15 | "我存了多少钱" |

```
判据  19/100 (19%)   precision 0.89   recall 0.94
```

三个错的，一条不漏地列出来：

| 输入 | 期望 | 实际 | 为什么错 |
|---|---|---|---|
| 详细一点，别只说搬家 | 触发 | 没触发 | 没有疑问词。"详细"是弱标记，被挡在门外 |
| 细节不重要，结果怎么样 | 不触发 | 触发 | "怎么样"是疑问词，但问的是结果不是细节 |
| 具体多少钱我给忘了 | 不触发 | 触发 | "多少"是疑问词，但整句是"我忘了" |

**没有为这三条改规则。** 规则是先设计的，fixture 是后写的，跑出来什么就报什么。
如果为了 100% 去加"遗忘词黑名单"（忘了/记不清/不重要），
"我忘了当时怎么说的，你提醒我"这类真需求会被一起挡掉——
用一个洞换另一个洞，还多一层要维护的逻辑。

19% 落在手册预期的 18% 附近，纯属巧合：手册的 18% 是 100 轮真实对话里
真的问细节的比例，我们这 100 条是手写的、刻意压低了正例密度。
两个数不能互相印证，只能说"同一个量级"。

## 三、决策 D70：预算门槛只管"开闸"，不管每一条

手册的条件 3 是"剩余 token 预算 ≥ 200"。字面实现会让**第二条永远进不来**：

```
memory_tokens      600
L2 用掉（ratio .6） -360   ← _fill 会一直装到 360
                    ----
剩                  240
第一条原文           -41
                    ----
剩                  199  < 200 → 第二条被挡
```

于是 `max_raws=2` 永远用不上。这不是配置问题，是门槛的粒度问题：
**"这轮值不值得拉原文"是个大决定，"第二条还装不装得下"是个小决定。**

改成：

```python
gate = raw_min if not out.drilled else MIN_RAW_TAIL_TOKENS   # 200 / 60
if left < gate: skip
```

60 的依据：`estimate_tokens` 下 60 token ≈ 30 个汉字 ≈ 一句话。
低于一句话的原文，信息量还不如一条 80 token 的摘要——那就让位给摘要。

改完真机上变成 `[1条×1 2条×4]`，`max_raws=2` 真的生效了。

**手册的 240 装不下两条 312 这个数，本身不自洽**（600×0.4=240 < 312×2）。
我们在真机上量的 raw 平均只有 33~41 token，所以 240 装两条绰绰有余。
详细对账见 R-11-Gate 第二节。

## 四、决策 D71：`degraded` 时不下钻（施工中发现）

这一条不在手册里，是跑 CLI 时撞出来的。

```
$ hippo recall "我当时怎么说的来着？" --raw
候选 44 条 → 命中 0 条 → 装 8 条 / 341 token（预算 360）
降级：no_keyword_hit
原文层：2 条 / 88 token（可用 259）
  1. [0.283 kw=0] 用户今天被老板当众骂了一顿，老板说他方案做得像垃圾
      原话 "今天被老板当众骂了一顿，说我方案做得像垃圾"
  2. [0.272 kw=0] 被骂时整个组十几个人在场，用户脸烧起来恨不得钻地缝
```

用户问"我当时怎么说的"，系统答的是"老板骂我"的原话。**两句话毫无关系。**

原因：关键词一个都没命中时，L2 走 `weight + recency` 兜底（M10 的
`degraded="no_keyword_hit"`）。兜底出来的 8 条是"这个库里的重要事件"，
不是"这句话相关的事件"。给它们贴 `[原话]` 标签，比不贴更糟——
模型看到"原话"三个字，会把它当成答案的依据。

修法：`res.degraded` 非空时一律不下钻，`pinned` 除外
（钉住的事件本来就与"这次问什么"无关，给原文是对的）。

代价：下钻率从 19% 掉到 5%。但这 14 个点的差额，本来就是**在拉无关原文**。

## 五、验收

| # | 要求 | 手册预期 | 实测 | 结论 |
|---|---|---|---|---|
| 1 | 触发率 ≤25% | 18% | **19%**（100 条判据） | 达标 |
| 2 | 预算不足时不下钻 | 0 超支 | **0 轮超 600**（5 轮下钻，L2+L3 平均 175/600） | 达标 |
| 3 | top-3 之后永不下钻 | 0 次 | **0 次**（`test_only_top_two`） | 达标 |

```
$ python3 -m pytest tests/test_m11_1_drill.py
14 passed in 0.31s

$ python3 -m tools.bench_retrieve --layer3-rate --db reports/data/eval_l1.db
库 44 条事件    session=main
判据  19/100 (  19%)   下钻   5/100 (   5%)   有候选 100/100   [1条×1 2条×4]
原文 33 token/条（max 48，min 20）  L2+原文 平均 175 / 600 token
命中 47 条里下钻 5 条（11%）  ← 判据只是上限，真下钻还要检索命中
未下钻 not_detail:81 / degraded:14
PASS

$ HIPPO_RETRIEVE__RAW_MIN_BUDGET=400 python3 -m tools.bench_retrieve --layer3-rate --db reports/data/eval_l1.db
判据  19/100 (  19%)   下钻   4/100 (   4%)   有候选 100/100   [1条×1 2条×3]
原文 31 token/条（max 48，min 20）  L2+原文 平均 134 / 600 token
未下钻 not_detail:81 / budget:15
PASS
```

最后一条是把门槛抬到 400：15 轮被判据触发、被预算挡住。**门槛真的会挡**，
不是写完就没人走过的一条 `if`。

耗时（真机库 44 条，重复 50 次取 best）：

| 操作 | 耗时 |
|---|---|
| `wants_detail` | 0.6 µs |
| L2 单独 | 0.47 ms |
| L2 + L3（无下钻） | 0.47 ms |
| L2 + L3（下钻 1 条） | 0.59 ms |

原话层本身的开销可以忽略；真正的成本是**多出来的 token**，不是 CPU。
