## 一、四类难例对应四条不同的机制

```
synonym  同义      "住处" vs "居住"      → data/synonyms.yaml（48 组）
abbrev   简称      "字节" vs "字节跳动"  → kw_search 的前缀范围兜底
typo     错别字    "老汪" vs "老王"      → 编辑距离兜底（等长替换）
trad     繁简      "貓" vs "猫"          → 212 个字的繁简表
```

分开测的理由很简单：合成一个"中文召回 78%"，下一轮不知道该改哪一块。
分开之后，`trad=0.60` 就是在说"字表漏字"，`typo=0.10` 就是在说
"这条路径根本没实现"——后者是信息，不是失败。

## 二、同义词：为什么是"组"，不是"映射表"

常见做法是一张 `查询词 → 库词` 的表。它在本机语料上分数好看，但：

- 库里的措辞会变（换个抽取模型，"工作"就写成"任职"）
- 查表是单向的，用户反过来问就失效
- **最坏的是错得看不见**：查不到就是降级，降级就是"不记得"，
  没人会发现是词表漏了

所以用等价组，组内任意两词互相扩展：

```yaml
- [上班, 工作, 公司, 单位, 职业, 打工, 干活]
- [睡, 睡觉, 睡眠, 入睡, 作息, 休息]
```

### 触发方式：字符包含，不是词匹配

"我几点睡"里没有"睡觉"这个词，只有"睡"。

如果拿切出来的 token 去查表，这个"睡"永远不会被切出来
（单字不进 token 集，见 R-10.1 的 `MAX_KEYWORDS` 逻辑）。
所以方向反过来：**看组里的词是否出现在查询原文里**。

单字触发词因此变得关键，也最危险。"住"出现在"记住""住院"里，
"猫"出现在"猫粮"里。所以：

- 单字触发词只在**短查询（≤12 字）** 时启用
- 长句里单字误触发概率高，而长句本身有足够的 2-gram 可用

权衡是明确的：误触发只多几个 token，排序时被"命中数"压住；
漏触发则是整条查询落空。

### 三条自我约束

1. **组是双向的**，不是"查询词 → 库词"
2. **按生活类别分组**，不按具体事件（写"搬家"组是因为人一生会搬很多次，
   不是为了命中某一条记忆）
3. **宁可少一组，不要宽一组**（"吃"和"喝"不能同组——合并后
   "我能吃辣吗"会把所有饮食事件都捞上来）

## 三、繁简：212 个字，一个都没多

**不引 opencc**：它是 C++ 扩展，装不上就把整个插件拖死，
而"即插即用"是用户的硬约束。

字表按"两个字一对"连续书写：

```
個个 們们 這这 說说 時时 麼么 來来 對对 會会 學学 國国 ...
```

**为什么不用 dict 或 YAML**：这张表要手改。YAML 里一行 `金 錢钱`
这种"单字 + 字对"混排，会让"按 2 字切"错位半步，之后所有字都往后挪一位。

而错位的症状是：**繁体查询全都命中不了**。看起来像"繁简没生效"，
实际是解析错了。所以第一版把"臺灣"（4 个字）当成一对写进去时，
`len(map)` 完全正常，测试也是绿的。

修法不是"下次注意"，是把坏条目做成**可测的**：

```python
def _t2s_parse() -> tuple[dict[str, str], tuple[str, ...]]:
    """(映射表, 坏条目)。"""
    ...
    return out, tuple(bad)


def test_t2s_map_is_well_formed():
    assert t2s_bad_pairs() == ()
```

只收**在简体里只有一个对应字**的字。"乾"（乾隆/干净）、"著"（著作/显著）
这类多对应字不收——猜错了会把整句改歪，比不转更糟。

## 四、错别字：为什么"编辑距离 ≤1"不够

第一版按教科书写：查 `kw_index` 的词表，找编辑距离 ≤1 的词。

`typo` 从 0.40 直接到 1.00，但**别处掉了**：

```
留出集 0.95 → 0.90
```

原因查出来了：

```
$ python -c "..."
纠错 被骂 -> 被挠
```

"组里多少人看到我被骂"被纠成了事件 3 的"被挠"，把正确答案（事件 12）
挤出了 top-8。

**决策 D66：加两条约束。**

**① 只允许等长替换，不允许插入/删除。**

中文错字绝大多数是同音替换（老汪/老王、甲壮腺/甲状腺、香采/香菜），
而插入删除型的误纠最多。

**② 首字是虚词的片段不纠。**

"被骂/被挠""给他的/给他的"是"虚词 + 实词"结构，纠错改的是虚词那一半，
而虚词没有区分度。规则一行：

```python
if t[0] in STOPWORDS:
    continue
```

加完这两条，`typo` 保持 1.00，留出集回到 0.95。

## 五、顺序：exact → prefix → fuzzy，不能换

**事故 61。** 三档兜底谁先谁后，一开始我没当回事（fuzzy 排在了 prefix 前面）。结果：

```
$ python -m tools.eval_zh_recall
synonym=0.80  abbrev=0.80  typo=1.00  trad=1.00
                      ↑ 掉了 0.10
```

`abbrev` 里"年终"这一条查不到，而库里有 `年终奖`——前缀匹配本该命中。

真正的原因在 `_kw_run` 的结构里：

```python
if prefix_fallback and not merged:      # fuzzy 先跑
    fuzzy...
if prefix_fallback and len(merged) < 3: # prefix 看到 merged 非空，跳过
    prefix...
```

"年终"被纠成"年龄""年糕"（都是等长、首字相同、差一个字），命中 5 条，
`merged` 一非空，prefix 阶段就跳过了。

**fuzzy 是最后一道，必须排在 prefix 之后，条件必须是"前面全落空"。**
这个 bug 之所以难发现，是因为它**只影响"能前缀匹配但也能纠错"的词**——
而这类词在测试集里正好只有一两个。

## 六、还有一个不是"中文"的问题：大小写

"Go" 这一条怎么都查不到。库里 17 号事件的关键词是 `推荐系统 召回 Go`，
用户输 `go` 命中 0 条。

根因不在查询侧——`lexicon.query_tokens` 已经把整句小写了。是**写入侧没归一**：

- `events.keywords` 存原文（对的，要显示）
- `kw_index.token` 也存原文（错的，它是索引键）

后果比"多一条命中不了"更麻烦：`AI` 和 `ai` 是两条互不相干的倒排项，
同一条事件在两个键下各占一行。总量看不见，检索会莫名其妙地漏。

`clean_keywords` 里早就写着"小写去重：AI / ai 在 kw_index 里是两条
互不命中的倒排项"——那句话只在**清洗阶段**生效，落库时没做，意图没落地。

**决策 D67：迁移 009 重建 `kw_index`，键统一 `lower()`，并加 CHECK。**

```sql
CHECK (token = lower(token))
```

CHECK 把"索引键必须小写"变成结构性保证，而不是每个写入点各自的自觉。
代码里的自觉在 M7 已经出过一次事（`type` 被整列丢掉，300 个测试没抓到）。

### 剩下的 4 条失败

| 查询 | 类别 | 原因 |
|---|---|---|
| 我干的活是什么 | 同义 | "干的活"不连续，含不着"干活"；该组缺"活"这个单字触发 |
| 我养的小动物叫什么 | 同义 | 组里没有"小动物" |
| 我伴侣做什么职业 | 同义 | 组里没有"伴侣" |
| 我用什么语言写代码 | 简称 | "语言"和"Go"没有可规则化的关系 |

前三条都是"词表覆盖不足"，加词就能过。**我刻意没加**——它们是在
测试集上迭代出来的，加进去会让 0.73 变成 0.80，但那个 0.80 不说明任何事。
词表该按真机使用中遇到的漏词来补（M26 的活），不是按测试用例补。

## 八、这套机制的边界

1. **同义词表是开放的**。48 组只覆盖日常生活，专业领域（"召回/推荐/排序"）
   一个都没有。真机上第一周就会遇到。
2. **错字兜底不处理"错两个字"**。"甲壮线"（应为"甲状腺"）纠不出来。
   放宽到编辑距离 2 会让误纠率指数上升——见第四节，距离 1 都需要两条约束才压住。
3. **首字不同的错字不会纠**。"老王"打成"老王"（对）和"王老"（错位）——
   后者首字变成"王"，分桶就找不到。中文里这种错法少见，接受。
4. **繁简只做字，不做词**。"乾"这类多对应字不收，所以"乾隆"能转对，
   但"乾净"（应为"干净"）转不了。这类字在日常生活里少。
