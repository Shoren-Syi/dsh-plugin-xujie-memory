## 3. 唯一一处故意偏离手册：超时不重试

手册 M5.2 写"超时可重试，注入 31s 延迟 → 重试后成功"。**我没做，理由有三条。**

1. **超时说明上游已经过载。** 再发一次请求，等于在别人排队时插队，把一次抖动放大成三次。DeepSeek 的 429 通常就是这么来的。
2. **抽取是后台任务，晚 10 分钟没人感知。** 而重试要占一个连接 30 秒，代理连接池是 16 个 keepalive，一分钟内 30 个超时就会把池占满，**聊天会跟着变慢**。
3. 手册的验收场景（"注入 31s 延迟"）在真实世界里很少见。真实超时是"网络断了"，重试也断。

替代方案：超时 → `status=degraded` → 写 raw 兜底事件 → 标记已抽。原文保住，下次聊天时 M21 心跳可以从 raw 事件离线重抽。

`httpx.HTTPStatusError`（4xx/5xx）同样不重试，原因不同：4xx 是配置问题（key 错、余额不足），5xx 交给上游熔断。

**只有一种情况重试：JSON 解析失败。** 那时上游是健康的，只是模型没听话，重试一次有真实收益（实测能救回 60~70%）。

## 4. 成本账

按固定前缀 2774 字符 / 对话 600 字符 / 输出 400 token 估算（1.5 字符 ≈ 1 token）：

| 场景 | 输入 miss | 输入 hit | 输出 | 合计 |
|---|---|---|---|---|
| 无缓存 | 2250 tok × 2 元/M = 0.0045 | — | 400 × 8 元/M = 0.0032 | **0.0077 元** |
| 有缓存（89% 命中） | 400 × 2/M = 0.0008 | 1850 × 0.5/M = 0.0009 | 0.0032 | **0.0049 元** |

按 `every_n_turns=5`：

```
一次抽取 0.0049 元 / 5 轮 = 0.001 元/轮
100 轮/天 → 0.1 元/天 → 3 元/月
```

加上主对话本身的费用（那是用户原本就要付的），记忆的边际成本约 **1%**。

**这 36% 的差距全靠 prompt 结构**——固定部分（规则+格式）必须排在最前面，可变部分（人物表+对话）排最后。第一版我把人物表放最前，前缀只有 166 字符，永远不命中缓存。

> 注意：以上是**估算**，不是实测。真机才有真实 usage。端到端演练里那 0.0028 元用的是桩返回的假 usage，不能当证据。

## 5. 降级：原文永不丢

```python
def persist_degraded(store, session, window, tokens=()):
    return store.add_event(
        session=session, raw=window.text(), summary="",   # ← 空是有意的
        keywords=tokens[:8], tier=3, w0=0.15, kind="raw",
    )
```

三个细节：

**summary 留空。** 用模型编的摘要冒充原文，比没有摘要更糟——M6 会把它当"已摘要事件"渲染进记忆块，用户看到一句自己没说过的话。

**keywords 用实体命中结果。** 不是随便切词。这样三个月后搜"老王"，这条 raw 事件能被 kw_index 捞出来，而不是只能靠 trigram 全表扫。

**tier=3 / w0=0.15。** 它大概率不会被检索到，这是对的——它存在的意义是"十年后你能回填"，不是"现在就出现在对话里"。

## 6. 幂等

三层：

| 层 | 机制 | 保证 |
|---|---|---|
| turn | `extracted_at` | 已抽的 turn 不再出现在 `pending_turns` |
| 窗口 | `extract_runs` UNIQUE(session,start,end) | 重跑只留最后一条记录 |
| 任务 | `app.state.extract_running` 集合 | 同一 session 不会同时跑两个抽取任务 |

第二层值得说：`UNIQUE` 不是为了防重复写，是为了"重跑时覆盖而不是追加"。调 prompt 时你会对同一个窗口跑 10 遍，留下 10 条记录只会让 `run_stats` 失真。

## 7. 事故：`status` 的初值恰好等于成功值

```python
@dataclass
class EncodeOutcome:
    status: str = "ok"      # ← 这个默认值让整个降级逻辑失效
```

`encode()` 末尾的收口是：

```python
if out.status != "ok":
    out.status = "degraded"
```

初值就是 `"ok"`，所以**这个条件永远不成立**。两次 JSON 解析都失败、`out.result` 是 `None`，但 `status` 还是 `"ok"`，`degraded` 分支永远不进，`persist_degraded` 永远不调用。

表现出来：抽取失败时，**什么都不发生**。没有 raw 兜底，没有日志（`extract.degraded` 也在那个分支里），`extract_runs` 记一条 `ok` 但 `n_events=0`。

我是被 `test_degrade_after_two_failures` 抓住的：

```
E   assert 'ok' == 'degraded'
```

如果那条断言写的是 `assert out.attempts == 2`（只验重试次数），这个 bug 会活到线上，症状是"偶尔聊完天，那几轮记忆就没了，也不报错"。

**教训：状态机字段的初值必须是一个"不可能被误认为成功"的值。** 现在用 `"pending"`。
