# R-8.2 矛盾检测

> 里程碑：M8.2
> 日期：2026-11-05
> 数据：`tests/fixtures/contradictions.jsonl`（35 用例）、`reports/data/eval_contradiction.json`、`tools/probe_contradiction.py`（真机 / ¥0.0039）
> 结论：**达标**。18/18 检出，0 误报；对照组（M8 之前的朴素实现）在同样语料上误报 11/15。真机端到端跑通了"北京 → 上海"的替换。

---

## 一、指标为什么不能单独报

手册的验收是"15 组矛盾对，检出率 ≥95%"。这个数字单独看**没有约束力**：

- 把每条新事实都判成矛盾 → 检出率 100%
- 判成矛盾然后关掉旧值 → "检出"甚至是有害的

所以语料里矛盾对和非矛盾对必须一起放，两个数字一起报。
误报的代价更不对称：漏一条矛盾只是记忆里留着旧值（下次还会被纠正），
误报一条会把"我搬到了海淀"记成"你搬家了"，并把旧值的 `valid_to` 写死，
之后查"我以前住哪"给出一个从未结束的区间。

## 二、语料构成

35 条，六类：

| kind | 条数 | 期望 | 说明 |
|---|---|---|---|
| contradiction | 15 | replace | 搬家、跳槽、转岗、晋升、结婚、换宠物（single 槽） |
| same | 9 | same | 上海/上海市/沪、字节/字节跳动/全称、清华/清华大学、三岁/3岁 |
| refine | 3 | refine | 北京→北京（海淀）、上海→上海浦东新区、字节→字节上海分公司 |
| multi | 3 | insert | 不吃辣 + 不吃香菜、跑步 + 游泳、花粉 + 海鲜 |
| guard | 3 | replace | 北京银行→北京、张伟→张伟明、北京→北海 |
| low_conf | 2 | doubt | conf 0.4 / 0.5 的改口 |

`guard` 这一类是专门为"前缀包含"设的陷阱：`字节 ⊂ 字节跳动` 成立，
`北京 ⊂ 北京银行` 不成立。如果守卫写错，前者会被判成搬家（漏报），
后者会被判成"说得更细"（误报）。两头都要挡住。

## 五、时间点查询

"旧值留痕"和"旧值可查"是两件事。只写 `valid_to`、查询却不支持时间点，
等于留了痕但谁也看不见。`fact_as_of(session, key, ts)`：

```sql
valid_from <= ts AND (valid_to IS NULL OR valid_to > ts)
```

左闭右开。用闭区间会让两段重叠——`valid_to` 恰好等于新值的 `valid_from`，
同一个时间点会查出两个答案。

```
北京 [1000, 2000)  上海 [2000, )
as_of(500)→None  as_of(1000)→北京  as_of(1500)→北京  as_of(2000)→上海
```

## 六、真机：改口在端到端链路上成不成立

单测走的是 `set_fact` 直连，中间还隔着模型。`tools/probe_contradiction.py`
造了一段 10 轮对话：前 5 轮住北京/在字节，后 5 轮说"上个月搬到上海了""现在在腾讯"。

**第一次跑，没触发替换。** 因为两个窗口被切在了一起（5 轮一个窗口），
模型看到"搬到上海"后只输出 `city=上海`，根本不写北京那条。
它把**归纳**做在了自己那边。这不是 bug，是一个必须知道的行为：
**同一窗口内的改口不会产生矛盾记录，矛盾只在跨窗口累积时出现。**

于是把改口挪到第 8 轮，隔开一个窗口重跑：

```
库里的事实：
  #1  用户  city      北京    single  11-05 → 10-01
  #2  用户  employer  字节    single  11-05 → 11-05
  #3  用户  occupation 后端开发 single  11-05 →  -
  #5  用户  pet       猫      multi   11-05 →  -
  #8  用户  city      上海    single  10-01 →  -
  #9  用户  employer  腾讯    single  11-05 →  -
```

`city` 的 `valid_from` 是 **10-01**——"上个月"，来自事件时间而不是写入时间。
这一条把 M8.2 和 M8.3 连起来了：没有区间解析，"上海从 10-01 开始"就无从谈起。

## 七、真机抓出的 bug：负区间

第一次跑出来是这样的：

```
#1  city  北京  valid_from=11-05  valid_to=10-01
```

**结束早于开始。** 成因：北京那条没有时间线索，`valid_from` 按写入时间算；
上海那条带了"上个月"，`valid_from` 是 10-01。替换时 `valid_to = 新值开始`，
于是区间变成 `[11-05, 10-01)`——任何按时间点的查询都查不到它。

真相是：我们**知道它什么时候结束，不知道它什么时候开始**。
修法是把这种旧值的 `valid_from` 置 0（表示"早于所有记录"），
区间变成 `[0, 10-01)`，问"去年 12 月你住哪"能答对。

```python
UPDATE facts SET valid_from = 0, valid_to = ?
 WHERE id = ? AND valid_to IS NULL AND valid_from >= ?
```

并加了一条全域不变量测试：任何历史事实都不许出现 `valid_to < valid_from`。
这个 bug 是**只有真机才会暴露**的——单测里我给两个值都传了显式 `when`。

## 九、这节没做到的

1. **真机语料里没有矛盾。** 14 窗口 28 条 fact，`historical=0`。
   矛盾路径靠 `probe_contradiction` 单独造对话验证，那毕竟是我编的。
2. **同一窗口内的改口不留痕。** 模型会自己归纳成最终状态，
   系统看到的是"用户一直住上海"。这是模型行为，不是代码选择——
   想改变只能要求它"同时输出被推翻的旧值"，而那会让输出更长、更贵。
   目前接受这个行为，登记为已知限制。
3. **`doubt` 的清洗没做。** 低置信度冲突会写一条 doubt，
   同一个槽反复改口会反复写。M12 做疑问调度时要合并同类 doubt。
4. **没有"矛盾确认"入口。** 用户看到 doubt 之后怎么回答"到底哪个对"，
   现在只能靠下一轮对话自然说清。M12 之前没有主动提问通道。
