## 一、规则只有一条

**内部全部是 UTC epoch，只在展示时转本地。** 听起来是常识，但中文项目里
最常见的错法是"用 UTC 天数做加减"：

```python
# 错：UTC 的 00:00 是北京的 08:00，"明天"和"今天"在这里重叠了 8 小时
datetime.utcfromtimestamp(ts) + timedelta(days=1)
```

`timeparse` 从 M5 起就用 `ZoneInfo` 的本地时间做天数运算，本轮的测试把它
钉成了契约而不是运气：

```python
def test_china_day_boundary_is_not_utc_day_boundary():
    # 北京 11-06 00:30 = UTC 11-05 16:30
    # 如果哪一层把 epoch 转成 UTC 日期再用，"11月6日凌晨"会被记成 11月5日
```

## 二、实测数据

| 场景 | 本地 | UTC | offset |
|---|---|---|---|
| 北京 8:00 | 2026-11-06 08:00 CST | 2026-11-06 00:00 | +8 |
| 纽约冬令时 8:00 | 2026-11-06 08:00 EST | 2026-11-06 13:00 | −5 |
| 纽约夏令时 8:00 | 2026-07-06 08:00 EDT | 2026-07-06 12:00 | −4 |
| 伦敦 8:00 | 2026-11-06 08:00 GMT | 2026-11-06 08:00 | 0 |
| DST 跳变日（3/7 说"明天"） | 2026-03-08 08:00 EDT | 12:00 | **−4，自动换** |
| DST 回拨日（10/31 说"明天"） | 2026-11-01 08:00 EST | 13:00 | **−5，自动换** |

同一句话"明天早上8点"在北京和纽约解析出的 epoch 相差 **13 小时**
（都是本地 8 点，+8 与 −5 相加）。如果实现里硬编码了 +08:00，
这条测试会红——而"8 点"这个本地时刻在两边看起来仍然一样，
光看展示发现不了。

## 三、一个手册没提的边界：不存在的本地时间

2026-03-08 02:00~03:00 在纽约**不存在**（时钟直接跳到 3 点）。用户偏说
"那天凌晨两点半"，`zoneinfo` 的处理是映射到跳变后的 03:30 EDT。

我们不修正、只接受，测试断言"不崩 + 日期仍是 3 月 8 日 + 时刻在合理集合里"：

> 用户说"凌晨两点半"时指的就是那个被跳过的时间点，挪半小时比报错
> 或挪一天都更接近他的意思。

## 四、非法时区的降级

`tz="Mars/Olympus"` 这类配置错误不能让写入链路挂掉——`_now` 的既有兜底
（`except Exception: datetime.now()`）覆盖了这条路径，本轮补了测试。
降级到系统本地时间并不完美，但**"记忆没存进去"比"时间差一小时"严重得多**。

## 五、展示层顺手收掉的欠账（M16 → M17）

M16 的 Gate 里留过一条："`2024-06-xx` 的日期不详表达还没做，现在是 `2024-06`"。
本轮收掉了 fuzzy 精度的展示：

| 内容 | 旧展示 | 新展示 |
|---|---|---|
| 小时候（1999~2009） | `1999-01-01~2008-12-31?` | **`约1999~2008?`** |
| 疫情（2020~2023） | `2020-01-01~2022-12-31` | **`约2020~2022`** |
| 前几天（7 天窗） | `2026-10-30~11-04?` | `2026-10-30~11-04?`（不变） |

旧格式的问题是 **1 月 1 日这个日子是编的**——编出来的精度比粗粒度更糟，
模型会拿"1999-01-01"去精确比较。"约"字是格式的一部分，不是修饰：
它告诉模型这个时间只能算量级（"十年前"），不能精确比。

## 六、config 侧

`Config.timezone`（M 早期就有，默认 `Asia/Shanghai`）现在被完整消费：
extractor → persist（解析）→ drill / pack（展示），全链路同一来源。
没有第二处硬编码时区。
