## 必须说清楚：这个"召回率"是什么

**它测的不是模型，是记忆通路。**

环境里没有可调用的大模型（全程预算 ¥0），所以抽取用 **gold**：语料自己
标了 50 条针，评测按标注直接写库。这样做的代价是抽不出来——那是 M5 的
事，M26 不管；好处是**变量只剩一个**：同样的记忆，能不能在需要的时候
被找回来。

"召回"因此定义为**上下文可达率**：第 200 轮后逐针提问，走正常 `pack`，
答案值是否出现在这段上下文里。

它不是"模型答对率"，但它是答对率的**上界**——上下文里没有的东西，
任何模型都答不出来。要测真正的答对率得打模型，属预算外，M26 用上界
替代，并在报告里标明。

## 成本口径

手册示例表里 none=1.0x、hippo=1.15x，暗含的基准是"一次普通对话"。
这里实测口径：

```
none   549 token/轮   人设 + 最近 5 轮
full  4412 token/轮   人设 + 全部 200 轮（超 8000 token 从头部截）
hippo  576 token/轮   pack 五段（A/B/C/D/E）
```

- **相对不装插件 1.05x**——比手册的 1.15 还低一点
- **相对全量重读 0.131**——这才是 DoD 说的"≤15% 基线"

基线必须带人设，否则没有可比性：只带 5 轮原始对话是 195 token，而 pack
里光人设就 300。拿这两个比，等于说"不装插件就不用写系统提示"。

## TTFT 口径

真实首字延迟要打模型，测不了。这里测**装配耗时**（pack 的 p50 毫秒），
它正是代理相对直连的可归因增量：网络和模型时间两边一样，差的就是这一坨。

1.4ms 这个数偏乐观——它不含 tokenize 上游的请求体、不含写回
`last_pack_d` 的状态。但量级是对的：D 段检索是一次倒排聚合（`EXPLAIN`
显示走 `kw_index` 主键），加上五次 SQL 读，没有全表扫描。

## 可重复性

DoD 要求"同语料结果稳定 ±2%"。两次独立跑，逐字节一致：

```
none  recall 0.06 / 0.06   tok 548.6 / 548.6   same_misses True
full  recall 1.00 / 1.00   tok 4412.2 / 4412.2 same_misses True
hippo recall 0.96 / 0.96   tok 576.4 / 576.4   same_misses True
```

确定性来自两处：检索排序用 `(-score, -time, -id)` 三级键（M12 定的），
评测里没有任何随机采样。

## 评测器自己修掉的三处偏差

做评测最容易犯的错是"把评测器的 bug 记在系统头上"。这轮修了三处：

### 1. 中文数字没归一（会让"答对"记成"没答"）

```
norm("三月十四") = "3月14"     ← 修之前是 "3月14" vs "三月十四"，判不等
norm("三十岁")  = "30岁"
norm("二十万")  = "20万"
```

语料里用户说"三月十四生日"，事实值存的是 `3月14`。不归一的话，
这一针永远不命中，而原因和记忆系统毫无关系。

### 2. 50 个问题互相污染（最隐蔽）

第一版提问阶段在同一个库上连着跑。每次 `pack` 都会 `touch_events`
抬权重、写 `last_pack_d`——于是第 19 个问题看到的是"被前 18 个问题
改动过"的记忆。

实测：P19（我爸现在做什么）单独问命中，排队问到就漏。它跟问题本身
毫无关系，只跟"它排第几"有关。

**这种偏差最坏的地方是它稳定**：重跑一百次结果一样，看着"可重复"，
其实测的是提问顺序。修法是每条提问前 `sqlite3.backup` 克隆一份库。

### 3. gold 关键词粒度太粗

第一版拿摘要按逗号劈开当关键词，得到的是"我挺喜欢吃川菜"这种**整句**。
检索打分对关键词是二值命中（`1-0.5^hits`），整句和查询永远碰不上：

```
整句关键词  → score 0.20，50 条记忆里 26 条捞不回来
短词关键词  → score 0.47，同样的库，只漏 5 条
```

真实抽取器给的就是 2~4 个短词。语料里补了 `kw` 字段（35 条非 fact 针），
评测用它，而不是从摘要里切。

## 评测抓到的三个真 bug

### 1. `parse_due` 把"下个月十号"解析成明天

见 R-26.1。影响所有远期计划，会提前一个月触发提醒。

### 2. 话题延续判断把"具体事实问句"吞了

`should_retrieve` 的判据是"和上一轮 jaccard ≥0.25 就继续话题，不检索"。
问"我约的胃镜复查是什么时候"时，因为"复查"两个字上一轮刚聊过，
jaccard=1.0 → 判 continue → **不检索**，转而复用上一轮的 D 段。
而上一轮 D 段是按**上一句**检索的，未必含这个值。

实测这条问题的 l2 结果排第一（0.603），但 pack 里一条记忆都没有。

修法：加一组 `FACT_MARKERS`（什么时候 / 哪天 / 几点 / 多少 / 哪个 / 叫什么 /
是谁 / 在哪），命中即检索。**放在"同实体"判断之后**——"老王什么时候回来"
问的是未来，只因为句子里有"什么时候"就去翻库，等于每句问句都检索一次。

代价：每轮 token 从 567 涨到 576（+1.6%）。

### 3. 实体别名漏了"我妹"

P42（妹妹什么时候结婚）的实体是"妹妹"，而事件摘要写的是"我妹明年五月结婚"。
`_entity_of` 只认"妹妹"，于是这条事件没有实体，L1 按实体过滤时被排除在
候选外——检索层再好也捞不回来。

修法：别名表加"我妹/我妈/我爸"，映射到规范名。

## 剩余两个失败，以及它们该记在谁头上

### P23「我平时看哪个医生？」— 记在 **M10（倒排检索）**

查询分词产出 `医生`，库里存的是 `陈医生`。`kw_search` 是精确匹配
（带前缀兜底 `token LIKE '陈医%'`），**没有后缀兜底**：

```
精确 '医生'    → 0 条
后缀 '%医生'   → 1 条   ← 能命中，但没实现
前缀 '陈医%'   → 1 条   ← 已实现
```

中文里"陈医生 / 王医生 / 李大夫"这类"姓+职业"的构词极常见，用户问的时候
只会说"医生"。补一个后缀兜底就能解决，但它会让 `kw_index` 的 BINARY 索引
失效（`LIKE '%x'` 走不了索引），8000 条事件的库上要全表扫。

**没有在这次修**：M26 是评测，不是重构检索。记在 M27（性能与成本）——
那时候正好要压测索引，可以在"加后缀兜底 + 建 trigram 辅助表"之间做选择。

### P50「我以前养过什么动物？」— 记在 **M12（语义检索的固有边界）**

库里存的是"狗 金毛 大福"，查询说"动物"。这是上位词，字面检索天然够不着。
同义词表里没有"狗→动物"这条。

**这类失败不该靠加词表解决**——加得完"动物"，加不完"宠物/小动物/毛孩子"。
真要解决得走向量检索，那是另一个量级的成本。当前设计明确选择了
"字面检索 + 用户会说的具体词"，这条失败就是这个选择的代价，如实记着。
