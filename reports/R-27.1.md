# R-27.1 · 并发压测

**日期** 2026-11-06　**花费** ¥0　**产出** `hippo/tools/loadtest.py`

## 结论

| # | 要求 | 预期 | 实测（20 并发 × 100 请求） |
|---|---|---|---|
| 1 | 错误率 <1% | 0.3% | **0.0%**（三次全零） |
| 2 | P95 TTFT <1.2s | 1.03s | **68–71ms**（假上游固定 6×20ms） |
| 3 | 内存峰值 <400MB | 287MB | **76MB** |
| 4 | 无 database locked | 0 | **0 次** |

三次连跑（每次独立建库、独立进程）：

```
run   pack p50   pack p95   proxy p50   proxy p95   p99    errors  rss
1     12.84ms    19.28ms    59ms        69ms        72ms   0       76MB
2     13.12ms    19.34ms    59ms        68ms        70ms   0       76MB
3     13.28ms    20.26ms    51ms        71ms        79ms   0       76MB
```

直连同一批请求是 p50 27ms / p95 30ms。**代理增量 p50 +32ms、p95 +39ms**，
其中 pack 占 13ms，其余是记账（turn/metric/状态三个小事务）与请求转发的开销。

## 这不是"1.03 秒达标"，是"上游时间没算进来"

手册的 P95 1.2s 含模型生成。这里用假上游（每块 20ms，共 6 块），
所以量到的是**插件自己**的延迟。真实场景是 `500ms 首字 + 70ms`，
结论仍然成立，但报告里不能写成"我们只要 70ms"。

## 一、M26 的遗留项：1.4ms 是假的

M26 报的 pack 1.4ms 是**内存库 + 300 条事件**测的。换成文件库 + WAL +
8000 条事件后：

| 口径 | p50 | p95 | p99 |
|---|---:|---:|---:|
| 重新检索（`use_cache=False`） | 12.8ms | 19.3ms | 23.0ms |
| 复用 D 段（同话题连聊） | 12.4ms | 14.2ms | 18.8ms |
| 内存库（M26 的数字） | 1.4ms | — | — |

**差 9 倍。** 差值不在"读页"上，在检索：L1 过滤 6.2ms（扫 8000 条）、
关键词倒排 5ms、钉住查询 2×3ms。

### 顺手砍掉的两笔

`cProfile` 显示每轮 22ms 里有两笔纯浪费：

1. **`count_pinned` 无条件先数一遍**（4.1ms，占 20%）。它只服务一条
   "你钉太多了"的提示，而提示的前提是 C 段超预算。把查询挪到
   `pinned.tokens > budget` 里面，语义不变，正常用户一次都不再付。
   20.9ms → 16.2ms。
2. **`pinned = 1` 没有索引**。`l2_search` 和 pack 各查一次，每次扫 8000 行。
   加部分索引 `WHERE pinned = 1`（只存钉住的行，通常个位数）：
   16.2ms → **12.4ms**，`EXPLAIN` 确认走 `idx_events_pinned`。

两笔加起来 **-41%**。这不是"优化"，是"原来的查询在为不存在的数据付钱"。

## 二、M26 的另一项遗留：后缀匹配，做了

M26 留的话是"先用 8000 事件测代价再决定"。测了：

| 方式 | 31k 行倒排上的耗时 | 存储增量 |
|---|---:|---:|
| 精确（`IN`） | 0.004ms | 0 |
| 前缀（范围扫描，走索引） | 0.002ms | 0 |
| **后缀（`LIKE '%x'`，全扫）** | **1.60ms** | **0** |
| 后缀（`substr`，全扫） | 1.90ms | 0 |
| trigram 辅助表 | — | 约 2.3× 倒排行数 |

结论：**不加表，加一档 `LIKE` 兜底**。它只在精确和前缀**全空**时跑
（一次查询最多一次），常态不付这 1.6ms。P23 的"看哪个医生"→"陈医生"
当场命中。完整 A/B 见 R-26 基线与 R-27.2。

顺手记一个坑：第一版把 `request_queue_size=128` 写在 **handler** 类上，
压测的 p95 一直是假的 1000ms（SYN 重传）。`ThreadingHTTPServer` 的
第二个参数是 handler，backlog 是 **server** 的属性。

## 三、瓶颈不是写锁，是"在事件循环里同步读"

手册预判"瓶颈通常在 SQLite 写锁，WAL + 单写队列可解"。实测 **0 次 locked**，
写根本不是瓶颈——压测里每轮只写 3 个小事务（turn / metric / 状态）。

真正的瓶颈是：**pack 是同步的，跑在事件循环线程上**。20 个请求同时到，
它们的 pack 只能一个接一个执行。所以延迟随并发**线性**涨：

| 并发 | 直连 p50 | 经代理 p50 | 经代理 p95 |
|---:|---:|---:|---:|
| 20 | 27ms | 59ms | 69ms |
| 50 | 67ms | 138ms | 169ms |
| 100 | 139ms | 336ms | 373ms |

100 并发仍在 1.2s 内，但斜率约是 3.4ms/并发（(336-59)/80）——**单进程的实际上限在 300 并发左右**。
要再往上，得把 pack 挪到线程池（每线程一条只读连接），或者按 session 分片。
这一轮不做：个人插件的真实并发是 1–3，为一个不会发生的场景改架构，
换来的复杂度比收益大。**写在这里，是为了下次有人问"能不能扛一千人"时，
答案是有数字的。**

## 四、包里多了什么

```
db 4.6MB / 8001 事件
RSS 76MB（启动 72MB）   →  压测期间只涨 4MB
```

RSS 峰值靠 `/proc/<pid>/status` 的 `VmHWM`（内核记的峰值），不是采样。
另外起了一个 50ms 的采样线程，两者取大——`VmHWM` 只在进程活着时可读，
而"含启动"的峰值会掩盖压测期间的泄漏。

## 已知偏差

1. 假上游固定 120ms 总时长，比真实生成短；它只影响"总时长"，
   不影响"代理增量"。
2. 灌库数据是合成的（16 个话题 × 40 个人物），关键词分布比真机均匀，
   L1 的压缩率比真实偏高。延迟结论不受影响（扫的行数一样）。
3. `pack` 的 8000 条里没有 traits/facts 的海量数据，`_pinned` 只测到 2 条。
   真机上钉住多了会线性涨，已有单独上限（C 段 200 token）。
