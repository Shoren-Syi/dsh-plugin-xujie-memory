## 一、为什么有这一轮

R-5-Gate §4 挂着五项"没有 API key，所以全是空的"。其中 U-2（raw 锚定通过率）写着：

> 如果真实模型只有 70% 能锚上，意味着 30% 的记忆被丢弃，而 M6 之后所有质量指标都建在这个基础上。

在拿到 key 之前，M6 的任何工作都是在这个风险上继续加码。所以先停下来，把这块地基测实。

**上游不是 DeepSeek。** 用户给的是小米 MiMo 的 key（`sk-...`，OpenAI 兼容协议，`https://api.xiaomimimo.com/v1`）。这意味着：

- 原来的全部参数假设（`temperature=0.2`、`response_format`、缓存字段名）都要重新验证
- 这恰好是好事：**一个只在单一上游成立的实现不算实现**，换一家就暴露了所有隐式依赖

## 三、四个核心指标

| 指标 | 结果 | 判定 |
|---|---|---|
| **U-1** schema 合法率 | **100%**（10/10） | ✅ 但是结构性的，见 §5.1 |
| **U-2** raw 锚定通过率 | **100%**（44/44） | ✅ 真结果，这是最关键的一项 |
| **U-3** 真实成本 | **¥0.00096/窗口，¥0.00019/轮** | ✅ 低于预算 |
| **U-4** 缓存命中率 | **97.79%**（17408/17801 token） | ✅ D13 成立 |

### 3.1 为什么 U-2 = 100% 这次可以信

M4 有过一次 `P=1.000` 假象：负样本太温顺，指标满分但毫无意义。所以这次特意做了区分度：

**14 个窗口，其中 4 个是负样本**（第一版没有，10 个窗口每条 user 消息都值得记，于是"每条都记"恰好全对——等于什么都没测到）：

| 窗口 | 内容 | 期望 | 实际 |
|---|---|---|---|
| `chitchat` | 早/吃了吗/哈哈/今天天气不错/嗯 | 不记 | ✅ 预筛挡掉 |
| `chitchat2` | 哦/原来这样/有道理/懂了/谢谢 | 不记 | ✅ 预筛挡掉 |
| `aitalk` | 用户只问算法题，AI 长篇讲解 | 不记（AI 的话不进记忆） | ✅ 预筛挡掉 |
| `halfanswer` | AI 问，用户答"不知道""忘了" | 不记 | ✅ 预筛挡掉 |

这 4 个窗口 **0 成本、0 延迟**，一次模型都没调。

剩下 10 个窗口 44 条事件，**全部锚定成功**。mimo 确实遵守了规则 1"逐字复制"，没有润色、没有合并。

### 3.2 但 U-1 = 100% 不是质量指标

`response_format: {"type": "json_object"}` 在 mimo 上是**强制**的——不合法就不给你返回。所以 U-1 恒为 1.0 是结构决定的，不是"模型很听话"。

真正的风险转移到了 U-2：JSON 一定合法，但内容可能是编的。而 U-2 也 100%，所以这次两层都过了。

**报告里必须写清这一点**，否则下一个人会以为 U-1 能当质量看。

## 四、三个反直觉的发现

### 4.1 成本 97% 是输出 token，不是输入

这是最重要的一条。实测拆分：

| 项 | token | 单价 | 小计 | 占比 |
|---|---|---|---|---|
| 输入（命中） | 17408 | ¥0.02/M | ¥0.00035 | **2.6%** |
| 输入（未命中） | 393 | ¥1.00/M | ¥0.00039 | **2.9%** |
| **输出** | ~6550 | ¥2.00/M | **¥0.0131** | **97.4%** |

**含义**：D13"固定前缀排前面省 36% 成本"是对的，但它省的是那 2.6% 里的一部分。**即使把输入成本降到 0，总成本也只降 5.5%。**

真正该优化的是**输出 token**：当前每窗口 655 token 抽 5 条事件 ≈ **130 token/条**。要降成本只有三条路：

1. 减少抽出的条数（但会丢记忆）
2. 压缩 JSON 结构（去掉 `summary`？但摘要层是三级表示的核心）
3. 换更便宜的模型 / 用批量推理（mimo 批量推理输出价 ¥1.00/M，**正好是一半**）

**第 3 条是最大的杠杆**：批量推理（Batch API）价格是实时推理的 50%。抽取是后台任务，天然适合批量。这一条登记为 M6 的候选优化。

### 4.2 开启"深度思考"会让抽取变差，不只是变贵

mimo-v2.6 系列**默认开启深度思考**，而文档写明"开启深度思考时不支持自定义 temperature（强制 1.0）"。我们抽取要的是 `temperature=0.2`（稳定，不要创意）。

实测对比（同一段对话，各跑 2 次）：

| | 关思考 | 开思考 |
|---|---|---|
| 均 events | 4.3 | 5.5 |
| **raw 锚定失败** | 0/12 | 0/12 |
| 均推理 token | 0 | 429 |
| 均耗时 | **15.4s** | 29.1s |
| 均成本 | ¥0.00145 | ¥0.00219 |
| 稳定性 | 5/5, 4/4, 4/4 | **7 条 / 10 条**（同窗口！） |

看起来"开思考多抽 1.2 条"，好像更全。但把输出打开看就明白了：

```
关思考：event[0].raw = "我昨天下午搬家了，从朝阳搬到海淀，房租涨了两千，累死了"
开思考：event[0].raw = "我昨天下午搬家了"
        event[1].raw = "从朝阳搬到海淀"
```

**开思考是在切碎句子，不是抽得更全。** 而且：

- 同一段对话跑两次，一次 7 条一次 10 条（关思考稳定 5 条）
- 有一次 3000 token 用满，**JSON 被截断**，直接降级
- 耗时 78 秒（关思考 16.9 秒）

**结论：抽取默认 `thinking: disabled`。** 理由不是省钱，是**稳定性**——抽取要可重复，不要"想得更深"。

这条也修正了一个隐含假设：我们原来以为"更强的模型 = 更好的抽取"，实际上抽取是**结构化转录任务**，不是推理任务。想得多反而会自作主张地拆分。

### 4.3 缓存是真命中了，但推理路径和我以为的不同

第一版评测跑出来 `cached_tokens = 0`，我一度以为 D13 的假设是错的。查下来是两层问题：

1. **真的 0 是我读错了**：打印是 `(6976/0)`，我按 `(prompt/cached)` 读，实际格式是 `(cached/prompt)`
2. **但 `prompt_tokens` 确实是 0** —— 这是个真 bug，见 §6.2

修完后实测：

| 调用 | cached | 占比 |
|---|---|---|
| 冷启动 | None | 0% |
| 同 prompt 再来一次 | 1664/1719 | 96.8% |
| 不同对话、前缀相同 | 1024/1723 | 59.4% |
| 同上再来一次 | 1664/1723 | 96.6% |

**前缀缓存确实按前缀匹配，不要求全文相同。** 但首次见到一个新 prompt 时只命中到某个分块边界（1024），第二次才到 96%。

TTL 实测：**225 秒后仍命中**。所以抽取虽然低频（每 5 轮一次），只要间隔在几分钟内就能享受缓存。

在真实评测里（10 个窗口串行、间隔 15–22 秒）命中 **97.79%**。

## 六、修掉的四个 bug

### 6.1 预筛的 `answer` 规则漏成筛子（M4 遗留）

```python
if r.answer_to_question and prev_assistant and _is_question(prev_assistant, r):
    return PrescreenResult(True, "answer")   # ← 只要 AI 上一句带问号，用户说啥都放行
```

真机跑出来：`chitchat` 窗口五句寒暄，唯一漏网的是 `今天天气不错`——它恰好跟在 `有什么想聊的吗？` 后面。

修法是加一道"无信息句"闸（纯评价/纯天气/纯应承），**但刻意不做语义判断**：规则法做语义判断的上限在 M4 已经撞过（留出集 R 卡在 0.72）。承认做不到，比假装做得到好。

修的过程中还踩了一个小坑：正则里只写了全角 `，`，而 `_normalize` 做 NFKC 后逗号已经是半角 `,` 了——**照输入的字面样子写正则，就是"看着对、跑起来永不命中"**。改用 `[\s\W]`。

### 6.2 `extract_runs` 的 token 列从来没被写过（M5 埋的）

`_record()` 调用 `record_run()` 时**没有传 `prompt_tokens` 和 `completion_tokens`**，因为 `RunResult` 里压根没有这两个字段。于是 `extract_runs.prompt_tokens` 一直是 0。

为什么一直没发现：`cost` 是从 `EncodeOutcome` 另一个路径算的，所以**成本报表看着完全正常**。直到要算缓存命中率，才发现分母是 0。

> 这是"指标看着有、实际全零"的典型。它比没有指标更危险：没有指标你会去找，有指标你会直接用。

现在 `RunResult` 带上三个 token 字段，并加了测试 §`test_run_result_carries_token_counts` 锁整条链（EncodeOutcome → RunResult → record_run → run_stats）。

### 6.3 老库不迁移 + `except: pass`，让抽取统计整段消失

收工前顺手核对 `hippo stats`，发现 `extract_runs` 有 3 条记录，
但"抽取"那一整段没打印。

真实错误是 `no such column: cached_tokens` —— 老库还停在 v3，没跑 004 迁移。
而 M5.4 写的 `except Exception: pass` 把它吃掉了，表现成"这个库没抽过"。

两层修：

1. **`Store.open()` 顺手迁移**。不是图方便：用户 `pip install -U` 之后
   不会记得敲 `hippo migrate`，而"升级完包功能静默变少"比崩溃难查。
2. **`except` 改成打印原因 + 提示**。

加了两条测试锁行为：老库（v3）打开后必须 ≥ v4 且 `run_stats()` 可用；
新库反复 open 不重复迁移。

> 这条的讽刺之处：它是在"检查自己有没有犯错"的那一步被发现的，
> 而错误类型正是同一份报告里刚批评过的那种。

### 6.4 `extract.timeout = 30` 会超时

30 秒是照 DeepSeek 的经验设的。实测 mimo 关思考要 15–22 秒，网络抖一下就到 30。改成 90 秒。

超时的代价不是"慢"，是"这一窗记忆降级成原文"——比多等 60 秒贵得多。

## 七、prompt 的两处修正（已验证生效）

### 7.1 事实归属

第一版抽出来的：

```
fact  用户/宠物 = 养猫
```

而原文是"老王让我帮他喂猫"。模型把"帮别人喂猫"记成了"用户养猫"。

这是**最危险的一类错误**：event 至少有原文可查，fact 是直接喂给模型的"既定前提"，它会当成事实用。三个月后 AI 会笃定地说"你家那只猫"。

在 prompt 里加了三组反例（帮别人做事 / 怕不等于养 / 考虑不等于发生），改后：

```
fact  用户/对猫的态度 = 怕猫，小时候被挠过一次     ← 正确
fact  用户老婆/职业   = 护士，常上夜班            ← 归属正确
fact  小李/出行方式   = 怕坐飞机，从不坐飞机      ← 多人场景归属正确
```

44 条事件、若干条 fact 里，**没有再出现归属错误**。

### 7.2 过度切分

规则 4 原来写"一句话里有多件事就拆成多条"，举例"我搬家了，从朝阳搬到海淀，房租涨了两千 → 3 条"。这条直接鼓励了切碎。

改成"主题不同才拆，同一件事的细节不拆"，判断标准是"拆开之后某一条单独存在还有没有意义"。

## 八、新发现的缺陷

| # | 缺陷 | 严重度 | 计划 |
|---|---|---|---|
| 8 | **成本 97% 在输出 token**，输入优化收益上限 5.5% | **高** | M6 评估批量推理（-50%） |
| 9 | 同一件事重复说 N 遍 → N 条 event，无去重 | 中 | M15 巩固 |
| 10 | `correction` 窗口两条矛盾事实都入库（"我住在朝阳" / "是海淀"） | 中 | M8 事实层 |
| 11 | `preference` 窗口 trait 说"不吃辣"、fact 说"能吃微辣"，自相矛盾 | 中 | M7 置信度 |
| 12 | `下周日` 解析成下个自然周的周日，中文口语常指"即将到来的周日"（差一周） | 中 | M19（提醒前需二次确认） |
| 13 | `hippo init` 生成的配置是 DeepSeek 默认端点，换上游要手改；且 `serve --dir` 优先读它 | 中 | M9 前加 `hippo use <provider>` |
| 14 | 聊天延迟 24–29 秒/轮（mimo 默认开思考，且回复极长） | 低 | 上游特性，文档说明 |
| 15 | `plans` 里"下周三交报告"默认落到 09:00，`guessed=1` 但无人消费这个标记 | 低 | M19 |

第 8 条要展开：这直接改变 M6 的优先级。原计划 M6 做三级表示（关键词/摘要质量），那是**质量**优化。但既然成本 97% 在输出，M6 应该先做一次"输出 token 解剖"——看 655 token 里哪些是必要的。

## 九、这份评测不能证明什么

必须写清边界，否则下一轮会拿它当泛化证据：

1. **样本量小**：14 个窗口、44 条事件、单模型（flash）。不足以支撑"抽取准确率 X%"这种结论。
2. **语料是我自己写的**：我知道每句话里有几件事，写的时候潜意识就写得"好抽"。真实用户的省略、指代、错别字没覆盖到。
3. **没有人工标注的"应抽条数"**：所以只能算"锚定率"（raw 对不对），算不了"召回率"（该抽的抽到没有）。
4. **单上游**：mimo 的 `response_format` 是强制的，DeepSeek 未必。换上游要重测 U-1。
5. **只测了关思考**：开思考那次截断了，样本不足以下"开思考一定更差"的强结论，只能说"在这个任务上没看到收益，且不稳定"。

**下一步如果要真正评测质量，需要的是"人工标注 50 个窗口的标准答案"**，那是 M7 之后的事。

## 结论

**M5 可以结项。** 四个未验证指标全部有了数字，两个真 bug 修掉，prompt 的两处结构性缺陷验证修复。

**但 M6 的优先级要改**：原计划做关键词/摘要质量，现在应该先做输出 token 解剖——因为成本 97% 在那里，而输入侧已经优化到头了（97.8% 命中）。

**最大的技术债务不是代码，是评测方法**：没有人工标注就无法算召回率，而没有召回率，M6 之后所有"记忆变好了"的判断都只是感觉。
