## 二、pack 是"全场唯一出口"，这句话现在是真的

M1–M12 的所有产物（实体、卡片、事实、记忆、存疑、计划、情绪）在这一个
文件里汇合，走同一条预算和同一套格式出去。三条纪律：

1. **只有这里能决定"什么进 prompt"**。检索层给候选，不给格式；
   抽取层写入库，不管注入。
2. **只有这里能决定"丢什么"**。裁剪顺序按"没了它这段对话还成不成立"排，
   不是按分数排。
3. **只有这里能保证字节稳定**。不拼 dict、不放浮点、时间锚到分钟。

第 3 条最容易破。一个人为了调试方便 `f"{score:.3f}"` 写进 prompt，
缓存就全废，而且**不会有任何报错**。

## 三、两个上游数据问题被 pack 兜住了

**① 同一个 key 三条 active 事实**（`commute` 有飞机/步行/高铁）。
C 段按 key 去重取最新。这是降级不是修复——真正的修法是 facts 带 entity
并在写入时消歧，留给 M14。

**② 客户端的 system 和我们的 A 段冲突。** 合并成一条（我们前、它后），
而不是两条 system。两条 system 会让模型不知道该听谁的，而且它**不会报错**，
只会让回复风格飘。

## 四、P2 Gate 的裁决：缓存这一项"无法判定"

手册：**M13.3 命中率 <40% 不许进 P3**。

实测：离线 **95%**（我们的前缀设计成立），真机 **17%**（mimo 不累积历史）。

对照实验（绕过我们的代码直接调 API）：

```
169 token → 0 / 128
319 token → 0 / 0
469 token → 0 / 448
```

同样的请求，命中率在 0/76%/96% 之间跳。**问题在上游，不在我们。**

所以我的判定是：

- **不按"未通过"处理**。成本模型的设计前提（稳定前缀 → 前缀命中）成立，
  证据是离线 95% 和字节确定性 100%
- **不按"通过"处理**。真实命中率没验到，手册的 72% 没有被证实
- 记录为"**设计成立、实测待换上游**"，并留下 `probe_cache` 让它随时可验

硬按 17% 判不通过，下一步该做的是换上游，而不是改 pack——把这两件事
分清，比一个 pass/fail 有用。

**P2 其余六项（M10.1 主干、M11、M12、M13.1 主干、M13.2）全部达标，进入 P3。**
